## 1. 目标

在 `api/routes.py` 上新增 4 个端点，把已经测好的 `transcript_store` / `ingest` 接到 HTTP 上，
使**前端"文稿核对"页面的完整动作链**（读全篇 → 看哪些要人工看 → 改一段 → 批量放过高置信的）

```

GET  /meetings/{id}/transcript       看全篇；counts 告诉你"还有 87 段没看"

GET  /meetings/{id}/transcript       再看一眼 → pending 从 387 降到 87
```

### 2.2 `GET /meetings/{meeting_id}/transcript` —— 取转写分段

**为什么必须分页，而且必须告知"截断了"**

`list_segments(limit=None)` 会返回**全篇**。一份 3 小时会议的转写稿动辄上千段，
一次全塞给前端不现实；但更危险的是**默默截断**——前端拿到 500 段就渲染 500 段，
用户以为"这会议就说了这么多"。

所以：

```python
TRANSCRIPT_DEFAULT_LIMIT = 500     # 默认页大小
TRANSCRIPT_MAX_LIMIT = 2000        # 硬上限（与 AUDIT_MAX_LIMIT 同理：不给"拉全库"的口子）
```

响应里 `data`：

```json
{
  "meeting_id": "m-xxxxxxxxxxxx",
  "segments": [ { ...SegmentRow.to_dict()... } ],
  "page": { "limit": 500, "offset": 0, "returned": 500, "total": 1247, "has_more": true },
  "counts": { "total": 1247, "reviewed": 860, "pending": 387,
              "low_confidence": 121, "no_confidence": 0 },
  "truncated": true
}
```

- `page.total` 用 `store.count()`（**不是** `len(segments)`——那是本页的条数）。
  数过：`list_segments` 返回的是切片，拿它当总数会得出"这会议只有 500 句"。
- `counts` 直接用 `counts_by_review_state()` 的 5 个键，**原样返回、一个都不改名**。
  `no_confidence` 必须单独在——它表示"引擎没给分，无法用分数分流，得全人工过"，
  把它并进 `low_confidence` 会让这个数虚高。
- `truncated` = `offset + returned < total`。**显式给一个布尔**，
  别让前端自己算（前端算错就是用户看漏了）。
  有截断时 `message` 也要说人话：「本次返回 500 段（共 1247 段），还有 747 段未显示」。

**参数**（都是 query）：

| 参数 | 默认 | 说明 |
|:---|:---|:---|
| `limit` | 500 | clamp 到 `[1, 2000]` |
| `offset` | 0 | `>= 0` |
| `min_seq` / `max_seq` | None | 按段序区间过滤（"只看第 100–200 段"） |
| `only_review_needed` | `false` | **端点层过滤**，见下 |

**`only_review_needed` 是本卡新增的一个过滤维度，不是 `store` 的能力。**
`list_segments` 没有"按复核状态筛"的参数，硬塞进去会让仓储层长出一个
只有界面才关心的概念。做法：先取一页，再在端点里用 `row.review_flags`
（`SegmentRow` 的属性，合并了 `low_conf` 与 `silence`/`overlap`/其他 flag）过滤。
⚠️ **过滤发生在分页之后**，所以 `page.returned` 可能小于 `limit`——
这时`truncated` 与 `returned` 会互相矛盾，必须在 `message` 里说清
「已按『待人工核对』筛选，本页 500 段中有 132 段命中」。
（如果将来真要"只翻待复核的页"，得在仓储层加参数重做分页，本卡不做。）

**空会议不是错误**：一段都没有时返回 `segments: []` + `counts` 全 0，
`message` 说「尚未生成转写稿」。会议刚建、还没 `/start`，这是一个**正常的中间态**，
不该弹红框——与 `/record` 端点的既有约定一致。

### 2.3 `PATCH /segments/{segment_id}` —— 就地编辑某段

请求体：

```json
{ "text": "改好后的正文", "operator": "张三", "flags": ["overlap"] }
```

- `text` **必填且非空白**。空字符串不是"删段"——`edit_segment` 会 `ValueError`。
  端点在调 store 之前自己先拦一道，翻成 **E1001**，文案说人话：
  「分段正文不能为空。逐段校对是改错字；要删整段请用别的操作。」
- `flags` **可选**：给了就整体替换，不给就 `None`（store 语义：不动）。
  传 `[]` 与不传**不是一回事**——`[]` 是"把标记清空"，`None` 是"别碰"。
  端点必须把这个区分原样传下去（`flags = payload.get("flags")`，**不要**写
  `payload.get("flags") or []`——那会把"不传"变成"清空"，静默抹掉 `silence`/`overlap` 标记）。
- `operator` 缺省 `DEFAULT_OPERATOR`。

响应 `data`：

```json
{
  "segment": { ...编辑后的 SegmentRow... },
  "changed": true,
  "before_text": "原来的错字",
  "version": 3,
  "warnings": []
}
```

**`changed=false` 是正常返回，HTTP 200，不是错误。**
用户点开一段、看了一眼、原文没动就保存，是极常见的操作；
把它当错误会让界面弹红框。这时 `warnings` 里会有
「正文没有变化，仍记了一次校订」，端点把这条 warning 原样带出去。

**404 与 403 的处理**：

- `segment_id` 不在库里 → `edit_segment` 抛 **`KeyError`**（不是 `MmwfError`！）。
  端点必须显式 `except KeyError` → 翻成 `FileMissingError`
  （E1002）并给明确 `user_message`。
  ⚠️ **不接就是 E9001**——`KeyError` 掉进 `@app.exception_handler(Exception)`，
  用户看到"程序遇到一个未预期的问题"，而这明明是"这个分段不存在"。
  **T1-14 的坑 10 就是同一类**（`GlossaryFormatError` 不是 `MmwfError` 子类）。
- **`PATCH /segments/{seg_id}` 的路径里没有 `meeting_id`**（SAD 原文如此）。
  而 `TranscriptStore` 是**按会议构造**的。所以端点必须**先从库里反查这个
  segment 属于哪个会议**，再用那个 `meeting_id` 构造 store。
  反查走 `SELECT meeting_id FROM transcript_segment WHERE segment_id = ?`。
  查不到 → E1002。
  ⚠️ 反查这一步**必须存在**，不能"拿 segment_id 去所有会议里碰运气"——
  见下方坑 5。

**审计**：`edit_segment` 内部在事务**提交之后**写 `segment_edit`。
端点必须给 store 注入 `AuditLogger(db_path)`，否则 store 只打 warning、
**完全不留痕**（而"逐段改动"是审计的最低检查项之一）。同时 `operator`
要从请求体一路传到 store——审计的核心是"谁做的"，落到 `"system"` 就等于没记。

**幂等性说明**：`PATCH` 重放**不幂等**——同一个 `text` 再调一次，
`version` 会从 3 变 4，并**再写一条** `segment_edit` 审计。
这是**刻意的**：审计要如实记录"用户又保存了一次"。
代价是重试要谨慎；但保存这个动作用户会亲眼看到，不存在静默重试。

### 2.4 `POST /meetings/{meeting_id}/review/accept` —— 批量接受高置信分段

请求体（全部可选）：

```json
{ "operator": "张三", "threshold": 0.9, "segment_ids": ["m-x:00012", "m-x:00013"] }
```

- `threshold` 缺省用 `ACCEPT_MIN_CONFIDENCE = 0.85`。
  给了就**校验范围** `0 < threshold <= 1`，越界 → E1001（否则 0.0 会让整篇被接受）。
- `segment_ids` 缺省 `None`（整篇）；给空数组 `[]` → store 直接返回全 0，
  不是错误。
- `operator` 缺省 `DEFAULT_OPERATOR`。

`accept_high_confidence` 的**两条判据都要满足**才接受（这是它的核心价值）：

1. `confidence >= threshold`（分数够高）
2. `flags` 里**不含**任何异常标记

只看第 1 条是错的——引擎对"两人抢话"往往给出很高置信度（它很确定自己听见了字），
但内容是叠在一起的废数据。这正是 `flags` 存在的理由。

响应 `data` 就是 `AcceptResult.to_dict()`：

```json
{ "accepted": 300, "skipped_reviewed": 12,
  "skipped_low_confidence": 75, "segment_ids": ["..."] }
```

⚠️ **`segment_ids` 可能很长**（整篇接受 1000 段就是 1000 个 id）。
本卡**不截断**——前端需要它来高亮"哪几段被放过了"。
但它确实让响应体变大；如果将来发现是问题，加一个 `include_ids=false` 开关，
**不要**现在偷偷砍掉（砍掉会让前端功能静默失效）。

`message` 要**报数**：「已接受 300 段；12 段此前已复核，75 段因置信度不足或有异常标记保留人工核对」。
三段数（`accepted` / `skipped_reviewed` / `skipped_low_confidence`）合起来才是全量，
只报第一个数会让用户以为"剩下 87 段系统忘了处理"。

**审计只写一条**（`accept_high_confidence` 内部就是这样）：批量接受 300 段写 300 条
`segment_edit` 会把审计冲垮，真正需要留意的逐段改动会被淹没在噪音里。

**一次接受多少段要不要设上限？** 本卡**不设**。理由是这是本地单机、用户自己
看着进度条点的一次批量操作，且 `UPDATE ... WHERE segment_id IN (...)` 在 SQLite 上
300 段是毫秒级。若真出现"一次接受 5 万段"的会议，那说明会议本身超出了本系统设计边界
（SAD 的规模假设）。

### 2.5 `POST /meetings/{meeting_id}/audio` —— 追加音频

请求体：

```json
{ "audio_paths": ["D:/录音/后半场.mp3"], "operator": "张三" }
```

- `audio_paths` **必填非空**，空或缺失 → E1001（文案：「请至少给一个音频文件路径」）。
- 走 `IngestService.ingest_batch`，**一个失败不影响其他**（批量语义见 T1-06），
  逐条结果原样返回在 `data.audio`。

响应：

```json
{
  "meeting_id": "m-x",
  "audio": [ { "ok": true, "original_path": "...", "chunk_count": 6, ... },
             { "ok": false, "original_path": "...", "error": "..." } ],
  "succeeded": 1, "failed": 1, "chunk_count": 6,
  "warning": "D:/录音/坏文件.wav: 文件为空（0 字节）"
}
```

- **全批失败也返回 200**（`ok: true` 信封），失败明细在 `data.audio` 里。
  理由：批量入口的语义就是"尽力而为"，返回 4xx 会让前端把"一个文件坏了"
  显示成"这次操作失败"，而实际上另一个文件已经成功落盘了。
  ⚠️ 这与单个文件投递的错误语义相反，是刻意的——**批量接口不该被其中一个成员拖垮**。
- 但 `audio_paths` **整体为空**是调用错误，那是 E1001（见上）。

**"追加"到底追加了什么？——本卡必须诚实地说明能力边界**

SAD §9.1 写的是"追加音频文件"。本卡的实现是：

1. 用 `IngestService.ingest_batch` 走**完整的接入流程**：格式校验 → 存在性/大小检查
   → `ffprobe` 探时长 → 出切分计划 → 落盘到该会议的 store；
2. **不写 `audio_file` 表**（见下）；
3. **不触发转写**，也**不合并 `transcript/segments.json`**。

第 2 点要专门解释：`audio_file` 表的 `audio_id` 是主键，而现有代码里
**没有任何地方生成或写入过 `audio_id`**——`create_meeting` 也没写。
也就是说这张表目前是**空的**，且没有既定的 id 生成约定。
本卡**不去替它发明一套**（那会是一张表两个出处，日后必然打架）。
等有一张专门的"音频登记"卡时，把 `POST /meetings` 和本端点**一起**改。

第 3 点更要紧：**追加的音频不会被转写**。
`transcribe` 节点读的是会议最初的 `audio_paths`，本端点不改状态机输入。
所以用户追加了后半场录音后，必须**重新投递/重跑**才能让它进转写稿。
这是本卡的一处**真实功能缺口**，**必须在端点 docstring 与响应 message 里写明**，
不能让用户以为"追加完就自动转写了"。
建议 `message`：

> 已接收 1 个音频文件（6 个切分块）。⚠️ 追加的音频**不会自动转写**，
> 需要重新发起处理才会体现在转写稿中。

⚠️ **状态约束**：会议已进入 G2/G3 之后追加音频，会让"转写稿"与"刚追加的录音"
不一致（文件在，稿子里却没有）。本卡**不阻断**（用户可能是想补料重跑），
但当 `meeting.status` 不在 `{created, failed, cancelled}` 里时，
在响应里加一条 `warning` 提示这一点。**不阻断的理由**：本卡没有任何"重跑"入口，
阻断就等于把用户堵死在没有出口的地方。

### 2.6 API 层不得 import `sqlite3` —— 为什么必须先有 `transcript_store.py`

`tools/check_layers.py` 的 `FORBIDDEN_IN_API` **含 `sqlite3`**。
这意味着：端点**不能**直接 `connect_ctx` 去读写 `transcript_segment`。

这正是 T1-14 把 `infra/transcript_store.py` 单列出来的原因——
本卡 4 个端点里 3 个是**纯读写分段**，如果 API 层自己写 SQL，
分层检查会红，而且"段落的校验规则"会散在 API 层。

⚠️ **反例（现有代码里已经有的、本卡不要学）**：`routes.py` 里的
`_require_meeting` / `list_meetings` / `create_meeting` / `_load_recent_segments`
**都是直接 `connect_ctx` 写 SQL 的**（T1-11 时定下的做法）。
本卡**不回头改它们**（改是另一张清理卡的活），但**新代码一律走仓储层**：
`_transcript_store(meeting_id)`。这样至少不再增加面积。

## 3. 验收标准

### 3.1 端到端（`tools/accept_t1_15.py`，9 项）

| # | 标准 | 判据 |
|:--|:---|:---|
| 1 | 端点清单 21 → 25 | 从 `build_router(cfg)` 反查，4 条新路径都在；总数 25 |
| 2 | `GET transcript` 分页正确 | 造 12 段，`limit=5&offset=5` → 返回 5 段且 `seq` 连续、`page.total=12`、`has_more=false` |
| 3 | `GET transcript` 截断必告知 | `limit=5&offset=0` → `truncated=true`，且 `message` 里出现总段数 12 |
| 4 | `GET transcript` 复核计数正确 | 造 3 段低置信 + 1 段 `silence` 高分 + 其余高分 → `counts.low_confidence=3`、`counts.no_confidence` 单独计 |
| 5 | `PATCH` 真改动 + 审计 | 改一段 → `changed=true`、`version` +1、`reviewed=true`；审计表多一条 `segment_edit` 且 detail **不含正文** |
| 6 | `PATCH` 无改动不报错 | 提交原文 → HTTP 200、`ok=true`、`changed=false`、`warnings` 非空 |
| 7 | `PATCH` 不存在的段 → E1002（**不是 E9001**） | 响应 `code=E1002`，且 `raw` 里无 `Traceback` |
| 8 | `review/accept` 只接受"高分且无异常" | 高分无标记 3 段、低分 1 段、高分带 `overlap` 1 段、已复核 1 段 → `accepted=3`、`skipped_low_confidence=2`、`skipped_reviewed=1` |
| 9 | `POST audio` 走真接入流程 | 造一个可用替身音频 → `ok=true`、`chunk_count>0`；并**反证**空 `audio_paths` → E1001 |

**附加 A —— 用户填错不出现 E9001**（沿用 T1-14 的做法，本卡必做）：
对 4 个端点各喂一组恶意/畸形输入（`text=""`、`threshold=0`、`flags="字符串"`、
`limit="abc"`、`segment_ids="不是数组"`、`audio_paths=[]`），
断言**没有任何一条**返回 `E9001`。这一项是本卡最可能抓到真缺陷的地方
（T1-14 靠它抓到两个）。

**附加 B —— 分层与依赖**：`tools/check_layers.py` 与 `tools/check_deps.py` 都过。

## 4. 常见坑

> 前 8 条是**本项目实施过程中真实踩过**的，不是假想。

### 坑 1 ★★ `KeyError` / `GlossaryFormatError` 这类"非 `MmwfError` 的异常"会变成 E9001

**症状**：用户传一个不存在的 `segment_id`，看到「程序遇到一个未预期的问题，请把下面的
追踪号提供给运维」，而实际原因只是"这个分段不存在"。

**根因**：`main.py` 挂的是 `@app.exception_handler(MmwfError)`。任何**不是**
`MmwfError` 子类的异常（`KeyError`、`ValueError`、`TypeError`、
`GlossaryFormatError`）都掉到 `@app.exception_handler(Exception)`，统一成 E9001。

**本卡的三个已知触发点**：
1. `edit_segment` 查不到行 → **`KeyError`**；
2. `edit_segment` 收到空 `text` → **`ValueError`**；
3. `parse_aliases` 收到不支持的类型 → `GlossaryFormatError`（T1-14 已修，本卡不涉及但同源）。

**做法**：**在端点里显式接住**，翻成业务错误码（E1001 / E1002）并给 `user_message`。
不要依赖全局处理器——它只会把所有意外都归成一个码。

### 坑 2 ★ 同一个异常，写在 `try` 里和写在 `try` 外，是两个错误码

T1-14 实测：`_build_entry` 只把 `GlossaryEntry(...)` 的构造包进了 `try`，
而 `parse_aliases()` **写在 `try` 之前**。于是：

| 输入 | 抛点 | 结果 |
|:---|:---|:---|
| `category="乱写"` | `try` 内 | E1001 ✅ |
| `aliases=12345` | `try` **外** | E9001 ❌ |

两个分支的代码**长得一模一样**，但结果差一个数量级。

**本卡做法**：`PATCH /segments/{segment_id}` 里，**把"校验 + 解析 + 调 store"
整段包进同一个 `try`**，不要只包最后一行的调用。

### 坑 3 ★ `PATCH` 路径没有 `meeting_id`，但 store 是按会议构造的

SAD §9.1 就是 `PATCH /segments/{seg_id}`。而 `TranscriptStore(meeting_id, db_path)`。
所以必须先反查 `meeting_id`：

```python
with connect_ctx(db_path) as conn:
    row = conn.execute(
        "SELECT meeting_id FROM transcript_segment WHERE segment_id = ?", (segment_id,)
    ).fetchone()
if row is None:
    # ⚠️ 用 MmwfError 基类，**不要**用 FileMissingError —— 后者会把
    # user_message 吞进 context，文案落回「找不到要处理的**文件**」。
    # 详见坑 13。
    raise MmwfError(
        code="E1002",
        detail=f"segment_id={segment_id!r} 不存在",
        user_message="找不到这一段转写稿。可能是它已经被删除，或者会议重新转写过。",
    )
meeting_id = str(row["meeting_id"])
```

⚠️ **不要偷懒**成"遍历所有会议试一遍"（错误信息会变成
"在会议 A 里没找到、在会议 B 里也没找到…"，而正确答案是"这个 id 根本不存在"）。

### 坑 4 ★ `TranscriptStore.get_segment` 校验 `meeting_id`——反查不能省

`get_segment(segment_id)` 的 SQL 是 `WHERE segment_id = ? AND meeting_id = ?`。
这是**刻意的**：分段 id 在各会议间虽不重复，但**不校验会议**就意味着
"知道任意一个 segment_id 就能读到它"，将来一旦有跨会议视图（比如"最近改动"),
这会变成一个越权面。

⚠️ 本卡因此**不能**写"用 `get_segment` 判断存在性"——它需要先有 `meeting_id`，
是**循环依赖**。用坑 3 的裸 `SELECT meeting_id` 反查（只取会议归属，不取内容），
再用 `meeting_id` 构造 store 做真编辑。

### 坑 5 ★ `flags` 的"不传"与"传空数组"是两个语义

`edit_segment(flags=None)` = 不动 flags；`edit_segment(flags=[])` = 清空 flags。

端点里**绝不能**写 `flags = payload.get("flags") or []`——这把"不传"变成了"清空",
静默抹掉 `silence` / `overlap` 标记,于是那一段从此"看起来没问题"，
而它其实是两人抢话的废数据。这类错误不会报错，只会让复核判断失准。

正确写法：`flags = payload.get("flags")`（`None` 原样传下去）。

### 坑 6 ★ `counts` 的 5 个键一个都不要改名、不要合并

`counts_by_review_state()` 返回 `total / reviewed / pending / low_confidence / no_confidence`。
`no_confidence` 是**单列**的（引擎没给分，无法用分数分流，必须全人工过）。
把它并进 `low_confidence` 会让"低置信 121 段"变成"低置信 121 + 无分 0 段"这种
含义不明的数；反过来把 `None` 当 0 算，则整篇都会被判低置信。

端点**原样透传**，前端直接用。

### 坑 7 ★ `page.total` 必须来自 `count()`，不是 `len(segments)`

`list_segments` 返回的是**切片**。用 `len()` 当总数 → 前端算出 `has_more=false`
→ 用户以为看完了全篇。这是"静默少显示"，比报错更危险。

同理 `truncated` 要显式给布尔，别让前端算 `offset + len < total`
（前端一旦算错，用户一样看不到后半篇）。

### 坑 8 ★ 验收脚本自己的断言陷阱（T1-14 记下的四条，本卡继续防）

1. **别假设响应有包装层**。T1-14 里 `GET /audit/logs` 的 report 是
   **平铺在 `data` 上**的（不是 `data.report`）。写断言前先 `print(raw)` 看一眼。
2. **别用未注册的审计 action**。`AuditLogger.log()` 对不在 `ACTIONS` 里的 action
   **直接抛 `AuditError`**。造数据要用注册过的（`export` / `import_text` / `segment_edit`）。
3. **"没有新文件"要排除 SQLite 的 `-wal` / `-shm`**。它们会因为任何一次写入而出现，
   不是"系统偷偷落盘了"。
4. **别"断言不含某个字"就了事**。T1-14 断言 `"缺" not in message`，
   而正确的文案是「**不可作为『字体缺失』的依据**」——含"缺"但**否定**它。
   正确做法是断言"具体字体名没被点名"，而不是断言某个字不出现。

### 坑 9 ★ 本环境的端点清单**不能**从 `app.routes` 反查

FastAPI 把 `include_router` 的结果包成 `_IncludedRouter`，**它没有 `.path`**。
遍历 `app.routes` 得到空集，然后断言报"清单里的端点全都不在路由表里"
（一大串，看不出真漏了哪条）。

正确做法：`build_router(cfg)` 拿原始路由器（它**不加前缀**，前缀在 `main.py` 的
`include_router(prefix=API_PREFIX)` 那步），路径自己拼 `API_PREFIX` 再比。

### 坑 10 `--collect-only` 与 `--junit-xml` 不能连用

要**数一个文件有多少用例**，用 `pytest <file> --collect-only`（**不加 `-q`**——
`-q` 会把用例列表吞掉）再 `grep -c "::"`。
⚠️ `--collect-only --junit-xml=...` 产出的是**空 XML**（`tests="0"`）——
收集阶段不填用例。

### 坑 11 全量 pytest 在**前台会被 SIGTERM**，且最后一行 `N passed` 会被吞

WorkBuddy 的 `sitecustomize.py` 在 atexit 里做批量删除防护，会 `SystemExit: 1`。

做法：`run_in_background=true` 跑，并**一律加 `--junit-xml=<绝对路径>`**，
跑完**解析 XML** 取结论，不信终端最后一行。
⚠️ **不要加 `--basetemp=C:/tmp/...`**（会与沙箱策略冲突）。

### 坑 12 `python` 必须用项目 venv 的解释器

```
cd /path/to/mmwf
PYTHONUTF8=1 .venv/Scripts/python.exe -m pytest ...
```

venv 是 **Python 3.13.14**；`pyproject.toml` 的 `requires-python = ">=3.11,<3.14"`。
**不要**用托管 Python 直接跑项目的 pytest。

⚠️ 跑**一次性脚本**（冒烟、验收）时还要加 `PYTHONPATH=src` ——
`pyproject.toml` 里的 `pythonpath = ["src"]` **只在 pytest 生效**，
直接 `python xxx.py` 会 `ModuleNotFoundError: No module named 'mmwf'`。
（`accept_t1_15.py` 自己在文件头 `sys.path.insert(0, SRC)`，所以不需要。）

### 坑 13 ★★ `FileMissingError` 会**吞掉** `user_message`（实施时才踩到）

`domain/errors.py` 里：

```python
class FileMissingError(MmwfError):
    def __init__(self, detail: str = "", **ctx: Any) -> None: ...
```

`**ctx` 把**所有**关键字参数收进 `context` —— 包括 `user_message`。
所以下面这句看起来完全合理，实际**文案没变**：

```python
raise FileMissingError("找不到这段", user_message="找不到这一段转写稿")   # ❌
```

`e.user_message` 仍然是 E1002 的默认值
「找不到要处理的**文件**。请确认文件没有被移动或删除。」
→ 用户去翻硬盘找文件，而这里根本没有文件。

**要覆盖文案必须用 `MmwfError` 基类显式构造**：

```python
raise MmwfError(code="E1002", detail="...", user_message="找不到这一段转写稿")   # ✅
```

这与 T1-14 的坑 10 同源（`GlossaryFormatError` 不是 `MmwfError` 子类）。
**共同教训：这个错误体系里，子类不重写 `__init__` 就改不动文案；
要自定义文案，一律回退到基类。**

### 坑 14 ★★ "调用没通过"的代码，改掉第一层错误后会**露出第二层**

`create_meeting` 里的音频接入这条路**从来没有被真正执行过**。
顺着修下去，一层一层地冒：

| 轮次 | 错误 | 表现 |
|:--|:---|:---|
| 1 | `make_ingest_service(meeting_id, cfg)` —— 只收 1 个位置参数 | `TypeError` → E9001 |
| 2 | `for r in results` —— `ingest_batch` 返回 `BatchResult` 对象不是列表 | `TypeError: not iterable` → E9001 |
| 3 | 没传 `chunk_dir` —— 切分一步不做，但 `chunk_count` 照报 | **静默假报数** |

**教训**：一处"主路径整个跑不起来"的代码里，往往叠着**多个**独立错误。
只修第一个就宣布修好，等于**没有验证**——第二个错误会立刻再炸一次。
判断标准不是"错误信息消失了"，而是**"这条路径真的从头跑到尾了"**。

**推论**：验收脚本里凡是涉及这段的用例，都必须**真跑到落盘**，
不能只断言"响应 ok=true"。

### 坑 15 ★ `chunk_count` 数的是**计划**，不是落盘文件

```python
@property
def chunk_count(self) -> int:
    return len(self.chunk_plan)      # ← 计划长度
```

`ingest_one` 的切分是有条件的：

```python
if not self._probe_only and chunk_dir is not None:
    result.chunk_files = self._cut_all(src, plan, chunk_dir)
```

**`chunk_dir=None` 时一个文件都不切，`chunk_count` 依然报 6。**
用户在投递那步看到"已接收 6 个切分块"，磁盘上却是空的 ——
等到转写阶段才发现没有输入，而那时人早走了。

**做法**：API 层调 `ingest_batch` **必须传 `chunk_dir`**，
目录约定与 `ingest` 节点（`graph/nodes/ingest.py` 的 `CHUNK_DIR`）一致：
`{data_dir}/{meeting_id}/audio/chunks`。
验收脚本要**断言真盘上有文件**，不能只信 `chunk_count`。

### 坑 16 ★ `flags` 传字符串会被**逐字符**入库，且完全不报错

`_dump_flags()` 原来是 `[str(f) for f in flags if str(f).strip()]`。
**字符串是可迭代的** —— `flags="silence"` 静默存成
`["s","i","l","e","n","c","e"]`：

- 不报错（类型注解拦不住运行时）；
- 不告警（`_dump_flags` 不知道什么是合法标记）；
- **后果**：那一行的 flags 从此谁也不匹配（`REVIEW_FLAGS` 里没有单个字母），
  于是"两人抢话"的分段**看起来干干净净**，复核直接放过。

这与 T1-14 的坑 12（`parse_aliases({'a':1})` 静默迭代出 `('a',)`）
是**同一个形状**。修法照抄其结论：
**用白名单（只接受明确的序列类型），不要用黑名单（排除字符串）。**
黑名单在这个场景必漏：`bytes` 可迭代、`dict` 可迭代（且迭代出 key，更隐蔽）。

### 坑 17 ★ "无改动也写审计"——先看**文案与行为**有没有互相打脸

`edit_segment` 原实现：

```python
changed = before_text != text
if changed:
    self._log_edit(...)                                    # 只在改动时写
return EditResult(..., warnings=[] if changed else
                  ["正文没有变化，仍记了一次校订"])         # 文案说"记了"
```

文案说"仍记了一次校订"，实际**什么都没记**。

**谁错了？文案是对的，条件错了。** 三条理由：

1. `edit_segment` 无论内容变不变，都真的改了 `version` / `reviewed` /
   `reviewed_by` —— **它就是一次真实的写操作**，审计的职责就是记录写操作；
2. 这个动作有业务含义：用户点"这段没问题"。**"我确认过第 37 段"比
   "我改了一个错字"更需要留痕**（前者是判断，后者是纠错）；
3. AUD-08 关心"逐段校对有没有被复核"。若只有改动才留痕，
   那"全部复核完但一字未改"的会议在审计里**看起来像没复核过**。

修法：`_log_edit` 无条件调用，`changed` 通过 `reason="no_text_change"`
带进 detail，让查阅者能区分"改了字"与"只是确认"。

**通用做法**：当**文案/注释**与**代码行为**互相矛盾时，
不要默认"代码是对的、文案写错了"。**两边都要论证**——
本卡的答案是文案对（它描述的是应有的语义）。

### 坑 18 ★ 验收脚本里"每项标准各用一个独立子目录"

第一版把所有 check 都传同一个 `tmp`，而 `Session` 以
`tmp/"data"/"mmwf.db"` 为库 —— 于是第 2 项开始就撞
`UNIQUE constraint failed: meeting.meeting_id`（每项都造同 id 的会议）。

**症状极具误导性**：8 项全红、每项都报"唯一约束失败"，
看着像**产品**的造数据逻辑坏了，实际是**脚本自己**把两次独立会话
指到了同一个库上。

**做法**：`for num, ..., fn in checks:` 里给每项 `tmp / f"std{num}"`。
**验收脚本的自身缺陷和产品缺陷长得一样**（都是"断言失败"），
所以脚本结构上要主动消除这类串扰。

### 坑 19 造数据后**先对总数**，再算期望值

标准 8 第一版把 `accepted` 期望写成 3，实际 4 ——
因为数"高分无标记"时**漏了 seq=7**。这是**脚本错，不是产品错**，
但症状是"断言差 1"，极容易被当成产品的边界 bug 去改产品。

**做法**：造完数据先断言 `counts.total`，再算各项期望。
差 1 类的错误，先怀疑自己的算术。

### 坑 20 ★ 给模块级名字打替身时，替身**签名必须与真身相容**

标准 9 第一版的替身只有无参 `__init__`，而 `make_ingest_service` 是按
`FFmpegAdapter(tools, timeout_seconds=...)` 调它的 → `TypeError` → **E9001**。

**这是"替身与真身签名不一致"造成的假故障**：看起来像产品炸了，
实际是测试装置自己不合格。

另外还要注意 **注入点在哪**：
- `routes._ingest_service` 是 `build_router` 里的**闭包**，不是模块属性 ——
  `setattr(R, "_ingest_service", ...)` 报 `AttributeError`；
- 真正可注入的是 `mmwf.app.services.ingest.FFmpegAdapter`（模块级名字）
  以及 `mmwf.adapters.audio.ffmpeg.locate`（本机没 ffmpeg，它会先抛）。

**好处**：走模块级名字注入，**端点代码一行都不用改**，
测的是真接线（路由 → service → adapter）。

### 坑 21 ★★ 改了**行为**，就必须同时改**断言该行为的旧测试**（本卡回归时踩到）

坑 17 把 `edit_segment` 的审计改成**无条件写**，但 T1-14 时期留下的

```python
def test_unchanged_edit_writes_no_audit(self, store, db):
    """没改就不留痕 —— 否则用户反复点保存会把审计冲垮。"""
    ...
    assert query(db, AuditQuery(action="segment_edit")) == []
```

还在断言**旧行为**。于是全量回归 `1 failed, 2146 passed` ——
**唯一的红点就是我自己这次改动打脸的那条旧测试**。

这不是产品的错，也**不该把测试删掉了事**：那条测试的 docstring 说的是
真话（"反复保存会把审计冲垮"），只是它把"顾虑"和"断言"绑成了一条。
**正确处理是把两者拆开**：

| 它说的 | 对不对 | 怎么处理 |
|---|---|---|
| 「无改动不该留痕」 | ✗ 错（构成缺陷 22） | 断言改成"**也留痕**" |
| 「否则反复保存会把审计冲垮」 | ✓ 对 | 不靠"不记"解决，靠**记时带 `reason="no_text_change"`** 让查阅者能区分 |

所以新用例名字改成 `test_unchanged_edit_still_writes_audit`，
并**补一条对照用例** `test_changed_edit_has_no_reason_marker`，
两条一起把"改了字"与"只是确认"钉死在测试里。

**通用做法**：回归跑出 1 个红点时，先问"**这个红点是我这次改出来的吗**"。
是 → **别急着改产品去迁就测试**，先论证哪边对（见坑 17），
再把错的那边改掉，并**补对照用例**防止它再翻回去。

**顺带一个细节坑**：`audit.py:740` 写的是 `if reason: detail["reason"] = reason`，
所以 `reason=None` 的结果是**键缺失**而不是"键在值为 null"。
对照用例第一版写成 `assert records[0].detail.get("reason") is None` ——
**这个断言在两种情况下都成立**，等于没验。改成 `assert "reason" not in ...` 才验得住。

> 坑 10 / 11 / 12 已在上方（`--collect-only` 与 `--junit-xml` 不能连用、
> 全量 pytest 前台被 SIGTERM、必须用项目 venv 的解释器），此处不重复。

### 已知缺口（本卡明确不做）

- 追加的音频**不会自动转写** —— `transcribe` 节点读的是会议最初的
  `audio_paths`，本卡不改状态机输入。端点 message 已显式告知。
- **不写 `audio_file` 表** —— 该表的 `audio_id` 从来没有代码生成过，
  本卡不替它发明一套 id 约定（那会是一张表两个出处）。
- `GET /meetings/{id}/transcript` 的 `only_review_needed` 过滤发生在
  **分页之后**，所以 `page.returned` 可能小于 `limit`。要在仓储层
  重做分页才能做到"只翻待复核的页"，本卡不做（那是界面偏好，
  不是数据语义）。
