### 1.3 ★ 数据形状缺口（**前置勘查发现，必须裁决**）

施工文档 §T2-01 的伪代码写的是**按 segments 分块**：

```python
def chunk_segments(segments, target_chars=1500, overlap_chars=200) -> list[Chunk]:
    for seg in segments:
        boundary = (seg.speaker != segments[seg.seq - 1].speaker) \
                   or ... or (seg.gap_after_ms or 0) > 1500
```

但**实际契约对不上**，两处：

| # | 施工文档假设 | 代码实际 | 裁决 |
|:--|:---|:---|:---|
| **①** | `seg.gap_after_ms` 字段 | **全代码库不存在**（`grep` 实测为空） | 从相邻 segment 算：`gap = next.start_ms - cur.end_ms`，末段为 `None` |
| **②** | `extract` 拿到 `segments` | `S.INPUT_FIELDS[NODE_EXTRACT] = ("record_markdown",)` —— **拿到的是 Markdown 字符串** | 见下 **裁决 D1** |

**裁决 D1：extractor 的签名保持 `(record_markdown: str) -> dict`，内部把 Markdown 反解成 segments。**

理由：
- T1-10 承诺过"二期把领域实现插进来，**图不用改一行**"，注入点签名就是 `Callable[[str], dict]`。
  改签名就要动 `state.py` 的 `INPUT_FIELDS`，那会波及检查点兼容与一期已验收的编排测试。
- 反解**已有现成实现**：`graph/nodes/extraction.py::_split_sentences` 已经在做
  "时间码 → `start_ms`" 和"剥说话人前缀"。本卡把它**提升**为
  `domain/extraction/segmentize.py`，让朴素实现与真引擎**共用同一份解析**
  （避免两套解析各自漂移 —— 那会导致"朴素路径能溯源、真引擎路径溯不到"这种诡异差异）。
- 副作用：Markdown 里没有 `speaker_conf`、没有原始 `flags`。**分块只需要 speaker + 时间 + 文本**，
  够用；缺失的信息在纪要生成里本来也用不到。这个取舍记在这里，别当它永远成立。

> ⚠️ **D1 的代价**：反解是**有损**的 —— 若记录稿里某行没有时间码，那个 segment 的
> `start_ms` 就是 `None`，`gap` 也就算不出来，分块会退化到"只按字符数"。
> 这不是 bug，是记录稿本身信息不全；`segmentize` 要把这种段落数出来并**告警**。

## 2. 契约（逐条可对照）

### 2.1 SAD §10.1 分块规则

| 边界优先级 | 判据 | 出处 |
|:---|:---|:---|
| ① 说话人切换 | `cur.speaker != prev.speaker` | SAD §10.1 Step 1 |
| ② 话题转折词 | 段首 10 字内含 `那么/接下来/第二个议题/下面/另外/关于` | 施工卡 T2-01 给的表 |
| ③ 长静音 | `gap_after_ms > 1500` | SAD §10.1 Step 1 |
| ④ 字符数达标 | `buf_chars >= target_chars`（1500） | 同上 |

**关键语义**：边界是 `(buf_chars >= target_chars) AND (任一语义边界)` ——
即"**攒够字数之后，遇到第一个语义边界才切**"，不是"遇到边界就切"。
这个 `and` 极易写成 `or`，写成 `or` 的后果是块会碎成一句一块（见 §7 坑 1）。

### 2.2 块大小约束（U-EX-04）

| 约束 | 值 | 来源 |
|:---|:---|:---|
| `target_chars` | 1500 | `config/extraction.yaml` |
| `min_chars` | 1000 | 同上 |
| `max_chars` | 2000 | 同上 |
| `overlap_chars` | 200 | 同上 |
| 末块豁免 | 末块可以 `< min_chars` | U-EX-04 "（除末块）" |

**单段超长怎么办**：若**一个 segment 自身**就 > `max_chars`（实测记录稿里罕见但可能，
例如某人一口气说了 3000 字且无标点），必须**强制切分**该段 —— 否则块大小约束直接失守。
强制切点选最近的句末标点（`。！？；`）；找不到就硬切在 `max_chars` 处并告警。

### 2.3 模式约束（SAD §10.2，**逐字照抄字段，不得自创**）

### 3.2 分块（`chunker.py`）

```python
TURN_WORDS = ("那么", "接下来", "第二个议题", "下面", "另外", "关于")
LONG_SILENCE_MS = 1500

@dataclass(frozen=True)
class Chunk:
    index: int
    segments: tuple[Segment, ...]
    text: str
    char_count: int

def chunk_segments(segments, *, target_chars=1500, max_chars=2000,
                   overlap_chars=200, long_silence_ms=LONG_SILENCE_MS) -> list[Chunk]:
    """按语义边界切块。边界优先级见施工卡 §2.1。
    ★ 切块条件是 (攒够字数) AND (遇到边界)，不是 or。
    """
```

**重叠怎么实现**：切块后，把**本块尾部约 `overlap_chars` 字**对应的 segments
作为下一块的**起始**。⚠️ 重叠是按 **segment 边界**对齐的，不是按字符硬切 ——
硬切会把一句话劈成两半，导致 `source_quote` 在原文里匹配不上（见 §7 坑 2）。

### 3.3 并行抽取（`extractor.py`）

```python
def extract_minutes(record_markdown: str, *, llm, settings) -> dict:
    """Step1 分块 → Step2 并行抽取 → Step3 归并 → Step4 补全 → 精确溯源。"""
```

- 并行用 `concurrent.futures.ThreadPoolExecutor`（LLM 调用是 **I/O 密集**）。
- `max_workers` **默认 2，不是 4**（施工卡明写：并行调用本地模型抢显存，默认值保守取 2）。
- **单块失败不拖垮全局**：某块抽取抛错 → 记一条 issue，其余块照常归并。
  整块失败 ≠ 整个任务失败（否则一块超时就让 2 万字白跑）。

### 3.4 归并（`merge.py`）—— **本卡最容易出错的地方**

```python
def merge_chunks(chunk_results, *, topic_threshold=0.82, dedup_threshold=0.90) -> dict:
    """议题聚类 / 议定去重 / 重叠区裁决。"""
```

三条硬规则：

| 规则 | 判据 | 处置 |
|:---|:---|:---|
| 议题聚类 | 名称+讨论 相似度 ≥ `0.82` | 合并为同一议题 |
| 议定去重 | 内容相似度 ≥ `0.90` **且** `source_quote` 区间重叠 | 合并为一条 |
| 重叠区裁决 | 同一 quote 在两块都出现 | 保留**信息量更大**的一条 |

**★ `source_refs` 必须取并集，不是覆盖。** 施工卡原文点名："同一议题在多个块出现时，
`source_refs` 要取并集而非覆盖，否则溯源会丢。"

**相似度实现**：SAD §10.1 允许"本地 embedding 或字符 n-gram Jaccard"。
本卡选 **字符 n-gram Jaccard（n=2）** —— 理由：**不需要模型**，纯离线可测，
且对中文短文本足够（embedding 需要额外模型权重，而本机没有，见 §2.4）。
阈值 `0.82` / `0.90` 从配置读，**写死在代码里会让 U-EX-08（阈值可配）失败**。

### 4.1 ★ 标准 10 的测法（**把"管道丢信息"与"模型质量"拆开**）

T2-01 验收原文是"**召回率 ≥ 95%**"。本机无模型，直接跑不了。但如果因此**整项记 UNSUPPORTED**，
就等于**放弃了本卡唯一能证明的核心命题**——"分块+归并不会丢信息"。

**拆法**：

| 变量 | 怎么验 | 结论 |
|:---|:---|:---|
| **管道是否丢信息**（分块/归并/溯源） | `FakeLlmClient` 对每块**返回该块内全部**议定事项（全知、无损） | 期望召回 **100%**。低于 100% = **管道的 bug**，本卡必修 |
| **模型抽取质量** | 需要真 LLM | **UNSUPPORTED**（§2.4 已实测） |

这个拆法的价值：**若管道是漏的，任何模型都救不回来**。先用全知 fake 把管道钉死，
剩下"模型好不好"才是模型的事 —— 那是目标机型上的验收项，不是软件缺陷。

> **诚实标注**：标准 10 在验收脚本里输出的是
> **"管道无损 100%（fake）" + "真模型召回 UNSUPPORTED"** 两行，
> **不写成"召回率通过"**。前者是跑出来的，后者没跑。

## 7. 常见坑（前置预判 + 实施后补录）

### 坑 1 ★ 切块条件的 `and` 写成 `or`

施工卡伪代码是 `if buf_chars >= target_chars and boundary:`。
写成 `or` 的后果：**每个语义边界都切一块** —— 说话人一换就切，
2 万字文稿会碎成几百块，每块都调一次模型（耗时爆炸），且块内上下文过短（抽取质量崩）。
**判据**：正常 2 万字文稿的块数应落在 **10—20 块**。若跑出 100+ 块，就是这个 `and` 写错了。

### 坑 2 ★ 重叠按字符硬切 → `source_quote` 匹配不上

`_tail_overlap` 若按**字符数**取尾部 200 字，会把一句话劈成两半。
后果是那句被劈开的文本作为 `source_quote` 时，**在原文里精确匹配不到** ——
于是"溯源失败"，而真因是分块时把句子切坏了。
**正解**：重叠**按 segment 边界**对齐（多取一整个 segment，宁可超 200 字）。

### 坑 3 ★ `source_refs` 覆盖而非并集

施工卡点名警告。同一议题跨块出现时若用 `dict.update` 式覆盖，
**只有最后一块的依据留下** —— 前几块的溯源信息静默丢失。
表现是"议题看着完整，但点溯源只跳到会议末尾"。**必须 `union`。**

### 坑 4 ★ 阈值写死在代码里

`0.82` / `0.90` 若写成字面量，U-EX-08（阈值可配）必挂。
必须从 `settings.extraction.merge` 读。

### 坑 5 ★★ 「环境不具备」这次要**取证**，不能推断

T1-17 的坑 19 是"凭推断说没环境，结果有"。本卡反过来要防**另一种错**：
把"我懒得接模型"写成"环境不具备"。
**规矩**：声称"环境不具备"必须附**探测命令 + 输出**（本卡 §2.4 那 6 条）。
**没有探测记录的 UNSUPPORTED，等同于没做。**

### 坑 6 ★ 单块失败拖垮全局

并行抽取里若 `future.result()` 直接抛，一块超时 → 整个 2 万字任务失败。
**正解**：逐块 `try/except`，失败块记 issue 并跳过，其余块正常归并。

### 坑 7 空输入要返回空结果，不是异常

U-EX-10 明写"空文本不崩溃，返回空结果"。
`chunk_segments([])` → `[]`；`extract_minutes("")` → 六维空数组 + 不抛。
**别用 `assert`** —— 空记录稿是合法输入（比如会议只有 5 秒）。

### 坑 8 提示词模板里的 `{chunk_text}` 注入

提示词用 `.format()` 时，**原文里的 `{}` 会炸**（会议记录里出现花括号很正常，
比如"预算{调整}方案"）。**正解**：用 `.replace("{chunk_text}", text)`，
或把模板拆成前后两段拼接。**不要用 `.format()` 直接套用户文本。**
