阶段 0 修复：现象是 macOS/Linux 上 `C:/Windows/System32` 未被文件仓储拒绝，跨平台根路径回归用例失败；根因是 `Path` 使用宿主平台语义，POSIX 将 Windows 盘符路径识别为相对路径；修法是在 `FileStore.resolve` 中同时检查 `PurePosixPath` 与 `PureWindowsPath` 的根与盘符语义，保留原异常及目录穿越兜底，并补齐反斜杠盘符、盘符相对路径和两种 UNC 写法的参数化回归用例。

> **T1-13 本轮范围**：`api/system.py`（四项自检：**网络行为 / ASR 质量 /
> 字体可用性 / 审计链完整性**）＋ `GET /system/selfcheck` 端点
> （形状照 SAD §9.2）＋ `HTTP_PROXY` 外发告警（SAD §11.1 第 5 项）＋
> 自检自身留痕（AUD-08）。新引一个依赖 `psutil`（system extra）。
>
> **本轮最要紧的一条设计约束**：`outbound_connections` **只统计本进程**。
> 第一版把"全机器所有进程的连接"也算进来，实测本机浏览器/更新器有 **52 条**
> 到 443 的连接，直接把验收项 `== 0` 打红 —— 而**语义也错了**：
> 本项目的合规主张是"**我这个程序**不发外部请求"，别进程连不连外网与本程序无关。
> 修正后：判定字段只认本进程，全机器概况另放 `machine_outbound_processes`
> 作现场信息、**不参与判定**。
>
> **验收方式说明（防假绿）**：这张卡的核心风险是"一个永远返回 0 的函数也能过"。
> 所以 `tools/accept_t1_13.py` 把第 ③ 条（"自检能检出真外发"）做成**三重重反验证**：
> ③-a 单元层假进程注入 / ③-b 集成层真 socket 注入 / ③-c 端到端真发请求。
> 其中 ③-b 是硬证据：它证明 `0` 是**探测得出的**而不是**写死的**。
> 另外标准 1（物理断网）无法自动验，明确列为「需人工复核」，**不混进通过数**。
>
> **验收实测踩到的一个真问题（记下来免得后人重踩）**：照施工卡字面
> `httpx.get("https://example.com")` 然后立刻自检 —— **检不出**。
> 因为请求**完成**后连接已被池回收，探测那一刻它**不在连接表里**了。
> 这不是自检缺陷（采样式探测抓的是"正在发生的"外发），
> 而是判据要改成"连接**存活期间**探测"。详见 `accept_t1_13.check_standard_3c`。

> **T1-12 本轮范围**：桌面壳主进程（单实例锁 F8.3、Python 子进程托管、日志转发、
> TCP 探测）＋ 渲染层（统一信封客户端、N3.3 文案表单一口出、四要素闸口页、
> 三步操作页）。**界面只接 T1-11 已实通的 11 个端点**，其余 14 个端点
> （`/audio`、`/transcript`、`/review/accept`、术语库、模板、审计日志、
> `/system/selfcheck` 等）按后续轮次补齐。
>
> **验收方式说明**：Electron 界面无法在无图形环境下"点一遍"，所以
> `tools/accept_t1_12.py` 做的是**静态契约检查**（文案黑名单全量扫描、
> 四要素齐全、单实例锁位置、信封解包正确性…），并把**必须人眼看的
> 3 项**单列成「需人工复核」，**不混进通过数** ——
> 假绿比红更危险。

> **T1-11 本轮范围**：骨架 + **核心闭环**（11 个端点）—— 建会议 → 启动 →

### 转写引擎：先不装大件

`funasr` / `torch` 加起来几个 GB，**按施工卡要求不在 T1-05 阶段安装**。
适配器代码、契约测试、验收脚本都能在**没有 funasr** 的机器上跑通：

```bash
# 接口一致性 + 业务链条：离线夹具（tests/fixtures/asr/fake_engine.py）
pytest tests/unit/test_asr_funasr.py tests/contract/test_asr_contract.py -q
pytest tests/unit/test_fake_asr_engine.py -q     # 夹具自身的可信性

# 真实引擎：装好之后
pip install -e ".[asr]"                          # funasr + torch
# 按部署手册 §4 预先离线下载模型到 models/funasr/paraformer-zh/
pytest tests/contract -q -m real_model           # 否则自动 skip
```

**换引擎只改 `config/models.yaml` 的 `asr.provider`，不动任何 Python 代码**
（SAD 附录 C 第 6 条）：新引擎 = 新文件 + 在 `adapters/asr/__init__.py`
的 `_REGISTRY` 里注册一行。

### 关于密钥：装不装 `keyring` 的区别

| | 装了 `keyring` | 没装 |
|---|---|---|
| 后端 | Windows 凭据管理器 | `data/.master.key`（明文） |
| `secure` | `True` | `False` |
| 适用场景 | 正式部署（含涉密） | 仅开发/演示 |
| 额外产物 | 无 | `KEY_STORAGE_UNHARDENED.txt` 警示文件 |

程序会**如实标注**当前档位（`keystore.describe_key_source()`），
不会把明文存储伪装成安全方案。涉密部署请用
`load_or_create_key(data_dir, allow_file_fallback=False)` 强制要求安全后端。

## 建库与迁移

```bash
python tools/migrate.py            # 建库 / 升级到最新版本（幂等）
python tools/migrate.py --check    # 只检查版本，退出码 1 = 待迁移（可进 CI）

```

迁移文件放在 `src/mmwf/infra/migrations/`，命名 `NNN_描述.sql`，
版本号即 SQLite 的 `user_version`。新增一列/一张表就加一个新文件，
**不要改已发布的历史迁移**。

## 三条铁律（中日韩文本处理）

1. 所有文件 I/O 显式指定 `encoding="utf-8"`（Windows 默认 GBK，不指定必乱码）
2. 读 CSV 用 `utf-8-sig`（Excel 另存会带 BOM，会让首列变成 `\ufeffxxx`）
3. 正则处理中文不用 `\w`，用显式字符类

## 数据库五条铁律（T1-02 踩坑实录）

1. **`PRAGMA foreign_keys` 是每连接设置，SQLite 默认 OFF**。
   不显式打开，13 张表里所有 `FOREIGN KEY` 声明全是摆设、且**不报任何错**。
   本项目统一走 `infra/db.py:connect()`，并内置 `assert_pragmas()` 自检。
2. **不要用 `conn.executescript()` 执行迁移**。它会先隐式 COMMIT 掉外层事务，
   与我们的 `transaction()` 冲突，报 `cannot commit - no transaction is active`。
3. **切分 SQL 不要用 `sql.split(";")`**。`CREATE TRIGGER ... BEGIN ... END;`
   的正文里也有分号，朴素切分会把触发器劈开、报 `incomplete input`。
   用 `sqlite3.complete_statement()`——这是 SQLite 官方语句切分器。
4. **`AUTOINCREMENT` 只在 `INTEGER PRIMARY KEY` 上生效**，写成 `BIGINT` 会静默失效。
5. **WAL 模式会生成 `-wal` / `-shm` 附属文件**。加密、备份、搬家脚本必须一并处理，
   否则会"主库拷走了、最近事务还在 -wal 里"。

## 文件仓储与加密三条铁律（T1-03 踩坑实录）

1. **导出的 docx **不加密**，会话内的音频/转写/纪要**必须**加密。**
   顺手把导出件也加密，用户会拿到一个打不开的文件（SAD §11.2 明确要求导出件明文）。
   代码按 `export/` 目录名区分，见 `filestore.PLAINTEXT_AREAS`。
2. **临时明文（给 ffmpeg 用）必须放 `<store_root>/.tmp`，用完即删。**
   禁止放系统 `/tmp`：那里不受 `data/` 的目录权限与磁盘加密保护。
   `FileStore.plaintext()` 上下文管理器已保证异常路径也清理。
3. **`Path('/etc/passwd').is_absolute()` 在 Windows 上是 `False`。**
   只靠 `is_absolute()` 挡不住根路径——`/etc/passwd`、`\Windows\System32` 都会漏。
   必须额外拒绝前导 `/`、`\`，并做"解析后必须在 store_root 之内"的兜底检查。

## 审计日志四条铁律（T1-04 踩坑实录）

1. **触发器挡不住"直接改 .db 文件"，只有链式哈希能。**
   `audit_log_no_update/delete` 拦的是"用程序或 sqlite3 命令行顺手改一下"。
   但用十六进制编辑器改字节后重新打开，SQLite 根本不认为发生过 UPDATE，
   触发器形同不存在。**两者缺一不可**：只做触发器 = 假安全，只做哈希链 = 日常能顺手改。

2. **校验链时，`prev_hash` 要比对"上一行存储的 row_hash"，不能用重算值续链。**
   如果拿重算值当链的延续，被篡改的那一行的错误会"传染"给后面所有行，
   报出一串假警报。比对存储值时结论干净准确：**只有被改的那一行报错**。
   （这个 bug 在 T1-04 第一版实现里真实存在，被验收脚本抓出来了。）

3. **`DROP TABLE` 能绕过行级 DELETE 触发器。** SQLite 的 `BEFORE DELETE`
   只在行级 DELETE 语句上触发，DDL 不走这条路。实测确认的防护缺口，
   已用测试 `test_drop_table_is_NOT_blocked_documented_gap` 钉住，
   将来做无人值守巡检时需要补一条"结构与触发器是否还在"的检查。

4. **写前拦截，不要写后告警。** 审计一旦落盘就删不掉（触发器在那儿摆着），
   放进去了就永久在里面。`check_detail_safety()` 在写入前拒绝
   含 `text`/`原文` 等键名或超 256 字符的字符串。
   **但要注意别过度封禁**：最初把 `segments` 列为禁止键名，结果正常的
   `segments=428`（分段条数）被误拦 —— 拦住正常审计会逼调用方改键名绕过去，
   反而降低可信度。正确做法是"键名 + 值类型"双条件（`segments=[...]` 才拦）。

## 转写适配器五条铁律（T1-05 踩坑实录）

1. **`disable_update=True` 必须显式传，不传等于放弃离线。**
   FunASR 构造时会联网查版本；离线环境不是"退回本地"而是**卡住或报错**。
   这正是 F8.1「断网可运行」的破坏点。本项目还做了双保险：
   模型目录存在时把 `model` 传成本地路径，即使 `disable_update` 失效也不去 HuggingFace。
   验收脚本用"拦截 socket + 断言零联网尝试"来证伪——不是读代码说"我传了"。

2. **传了热词不等于生效，必须回读结果文本。**
   上游多个版本会**静默忽略** `hotword` 参数：不报错、不告警、当它没传。
   唯一可靠的判据是"结果文本里到底有没有把这些字写对"（`hit_hotwords`），
   而不是"引擎说它用了"。零命中时置 `hotwords_applied=False` 并产出
   `hotwords supplied but zero hit` 告警。
   **热词参数名还跨版本漂移**（`hotword`/`hotwords`/`hotword_list`），
   必须用 `inspect.signature` **探测**而不是猜，并把生效的参数名打进启动日志。

3. **"两种形状表示同一个概念"是 bug 温床。**
   第一版 `_normalize()` 产出中间字典，而 `hit_hotwords`/`detect_silent_failures`
   按 `TranscriptSegmentResult` 实现 —— 运行时直接
   `AttributeError: 'dict' object has no attribute 'text'`。
   改为**全程只用一种类型**后，这类错误在写代码时就看得见。
   同理：`AsrProvider` 用 `typing.Protocol` 而不是 ABC —— 加引擎只需新文件 + 注册，
   测试替身也不必继承基类（SAD 附录 C 第 6 条）。

4. **切分不是适配器的职责。**
   长音频整段喂进去会 OOM，但"怎么切"属于 T1-06（ingest）：
   它才知道块边界、重叠窗口、以及如何把多块结果拼回去。
   适配器只做安全限幅（`batch_size_s`）+ 超 1 小时给一句"应先经 ingest 切分"的提示。

5. **`confidence=None` 是"引擎没给"，不是"0 分"。**
   混成 0 会让整篇被标红，提示彻底失效。平均置信度只对"有置信度的段"求平均，
   一段都没有时返回 `None`，让上层走"整体降级为人工全检"这条分支。
   低置信占比的分母同样只用"有置信度的段"，否则会被 None 稀释成虚假的低比例。

## 音频接入五条铁律（T1-06 踩坑实录）

长音频必须切，这是 F1.2 的硬要求。**两条独立的上限逼着这么做**：
FunASR 整段喂长音频会 OOM（T1-05 卡），ffmpeg 处理超 4GB 的文件会变慢甚至失败
（32 位偏移上限）。切分参数（1800s 块 + 50s 重叠）放在 `config/models.yaml`
的 `asr` 段，**可热改**（N5.2），代码里只留兜底默认值。

1. **重叠区去重写在 `merger`，不写在切分里。**
   切分时只知道时间轴，不知道文字。而"前后两块在重叠区的文字是否相同"
   只有拿到转写文本才能判断 —— 引擎在边界断句不同、上下文不同，
   转出来几乎不会逐字一致。所以切分只管切，去重由
   `domain/ingest/planner.merge_overlapping_texts()` 做**最长公共后缀/前缀匹配**。
   用字符匹配而不是时间匹配：重叠区的时间戳来自两次独立解码，
   同一句话会漂移几十到几百毫秒，按时间切必切歪。

2. **去重必须保守：匹配不上就原样保留。**
   纪要场景下，"多一句"和"少一句"的严重性完全不对等。
   宁可留一点重复，也不能凭空删掉内容。每次判定都记进 `decisions`
   （`between`/`overlap_ms`/`deduped`/`matched_chars`/`reason`）——
   静默去重会让"为什么这句话没了"无法追查。
   回看窗口有上限（200 字），否则病态输入会退化成 O(n²)。

3. **`-ss` 放在 `-i` 之前，且用 `-t` 不用 `-to`。**
   前置 `-ss` 是快速定位（跳关键帧，不精确到帧），后置是精确但要从头解一遍。
   转写对精度要求不高，用前置——代价是切点漂几十毫秒，而重叠区正好覆盖这点漂移。
   `-t` 是时长、`-to` 是结束时间；`-ss` 前置时用 `-t` 语义无歧义。
   另外三个不能省的参数：`-nostdin`（作为服务运行时无终端，ffmpeg 会阻塞在 stdin）、
   `-y`（幂等重跑，否则卡在覆盖确认）、`-vn`（丢掉 m4a 里的封面图流）。

4. **音频统一转 16kHz 单声道，在切分时一次做完。**
   `-ac 1 -ar 16000 -c:a pcm_s16le` 是 ASR 的标准输入。
   不在这里转，引擎会用自己的重采样算法——**同一份音频在不同机器上结果会不同**，
   这是最难复现的一类问题。`-c:a` 显式指定编码器，不靠目标扩展名推断。

5. **`text=True` 是 `subprocess` 的陷阱。**
   ffmpeg 的 stderr 在某些编解码器下会混入非 UTF-8 字节，
   `text=True` 会直接抛 `UnicodeDecodeError`，**把真正的错误盖掉**。
   改用 `_decode(bytes)` 并 `errors="replace"`——排查信息里出现几个 `?` 可以接受，
   "拿不到错误信息"不可以。

> **另注：`from ... import MAX_FILE_BYTES` 是值拷贝。**
> `ingest.py` 最初这样导入 4GB 阈值，结果"改配置/改 planner **对 service 毫无影响**"，
> 验收脚本里那条"超大文件告警"断言看着跑过了，其实什么都没验到。
> 现在统一读 `planner.MAX_FILE_BYTES`（模块属性），并断言两处一致。
> 同理，`warnings[0]` 未必是你要找的那条——断言前先把内容打出来。

## 术语库三条铁律（T1-07 踩坑实录）

术语库（`config/glossary.csv` + `glossary_entry` 表）存在的理由是：
**ASR 一定会把人名、机构名、项目代号写错**，而热词注入有三个已知缺陷 ——
数量敏感（超限可能**整体静默失效**）、参数名随版本漂移、失败时**不报错**。
所以需要"热词注入"与"转写后回改"两条腿走路，缺一条都不够。

1. **替换前必须把「规范写法」也遮蔽起来 —— 光靠长度倒序不够。**
   施工卡给的用例是「张三」/「张三丰」，但它**不是**"两个别名互吃"的形状：

   ```
   「张三」  是别名（指向李四）
   「张三丰」是另一条术语的规范写法（没有别名）
   ```

   「张三丰」压根不在别名索引里，所以没有任何东西在跟「张三」比长度，
   `李四丰` 照样出现。解法是把规范写法也用占位符遮蔽，
   替换完再还原（`_mask_values`）。`build_alias_index` 因此还要把
   **没有别名的规范写法**登成恒等映射（`canonical -> canonical`），
   让 `apply_corrections` 能看见它们；恒等条目在替换循环里显式跳过，
   不产生"自己替换自己"的假命中。副作用是**幂等**变免费了：
   第一遍的产物是规范写法，第二遍会被保护起来。

2. **两道防线要分命名空间，否则互相吃掉占位符。**
   遮蔽分两趟（文件号一趟、规范写法一趟），各自一个 list、各自从 0 编号。
   都用 `\x00{0}\x00` 的话，还原时任一趟都会把对方的占位符认成自己的 ——
   实测把「中办就中办发〔2026〕1 号问张三丰」还原成了「张三丰问张三丰」。
   现在用 `\x00F{n}\x00` / `\x00C{n}\x00` 两个前缀，还原顺序也不再要紧。

3. **"保护"不能保护过头：别名覆盖的位置要让给别名。**
   有些条目的别名**包含自己的规范写法**（规范写法「某单位」、
   别名「某单位简称」）。无脑遮蔽规范写法，别名就再也匹配不上，
   该改的没改 —— 这是上面第 1 条修好之后立刻踩出来的回归。
   解法是遮蔽前先算别名的覆盖区间，落在别名里的位置不遮
   （`_mask_values(..., avoid=real_aliases)`）。
   **`avoid` 只能放真别名**（`alias != canonical`），
   把恒等条目也塞进去会造成"自己覆盖自己"，保护机制直接失效。

4. **文件号的正则要卡上界，还要排掉叙事助词与指代词。**
   最初写 `[^\s〔〕\[\]（）()]{2,20}` 配贪婪匹配，
   「中办印发了中办发〔2026〕1 号」整段被当成机关代字吞掉 ——
   `中办印发了` 也一起进了保护，别名替换自然碰不到它。
   机关代字实际长度 3–8 字，取 `{2,7}` 作上界，
   再排掉 `了的和与至于及在是为第据经由见称等此该本份次项上下前后就都也又还再`
   （公文代字绝不会包含这些字）。宁可略保守——
   多吞一个字只是"那一段没被回改"（原文照旧、不产生错误改写），
   少吞一个字却是文件号被拆开、年份被换成别的词。

5. **超限截断必须说清"后果"，而且优先级要按领域定。**
   施工卡原文是"避免超出引擎上限反而**全部失效**"，所以告警不能只写"已截断"——
   用户会当成性能优化而无所谓。必须点明"整体不生效"。
   截断顺序：`person/org` 在前、`term/codename` 在后 ——
   人名机构名最依赖热词引导，而"党组会"这种通用术语引擎本来就认得。

6. **命中数进审计，但只在真改了的时候写。**
   `detail` 里放 `op/hits/entries/aliases/chars_before/chars_after`：
   只记计数与**截断过的**别名，绝不记正文原文（部署手册 §6.2 红线）。
   命中 0 处不写审计 —— 每段都写一条"改了 0 处"会把链刷爆，
   反而淹没真正的修改。其余写操作（新建/停用/删除/导入/导出）
   各留一条，导入写**汇总一条**而不是逐条。

7. **别名冲突只报告，不静默裁决。**
   同一别名指向多个规范写法是**维护错误**。实现上用确定性策略
   （`on_conflict="stable"`，按 `(-len(canonical), canonical, entry_id)` 选），
   保证结果与录入顺序无关（否则换个 `ORDER BY` 就会输出不同的稿子，
   复核页的修改记录无法复现），同时 `detect_alias_conflicts()` 把冲突
   变成用户可见的告警。选错一条不可怕，**悄悄选错**才可怕。

> **另注：CSV 读取要先摘注释行再交给 `csv`。**
> `csv.DictReader` 把文件首行当表头，而交付模板（`config/glossary.csv`）
> 习惯在开头写用法说明。不先剥离的话表头会变成 `["# 用法说明"]`，
> 然后报"缺少必需列"——用户对着完全合规的文件莫名其妙。
> 编码固定 `utf-8-sig`（不剥 BOM 的话首列名变成 `\ufeffcategory`，
> 所有行都会因为"缺 category"被打回）；写出时也带 BOM，为的是 Excel 打开不乱码。
> 导入是 **upsert 不是同步**：绝不删库里已有条目，
> 否则用户拿一份只含 3 条的补丁文件导入就会静默清空术语库。

## 复核与记录稿五条铁律（T1-08 踩坑实录）

F2.1 明写**不设全文校对**。一份 3 小时会议上千段，全推给人工等于重听录音，
自动化就白做了。只把"机器自己都不确定"的段落挑出来，其余默认可用。
分流三条判据：低置信 / 异常 flag（静音、抢话）/ 残余噪声。

1. **`confidence=None` 是"引擎未提供"，不是"0 分"。**
   施工卡把它列为第一条坑，因为它是最会"写错了也看不出来"的一处：
   `None < 0.70` 在 Python 3 直接 `TypeError`（立刻暴露），
   但现实里更常见的写法是 `(seg.confidence or 0.0) < 0.70` ——
   它**不报错**，只是把每一段都判成低置信。用户看到的是
   "整篇都要人工核对"，没人会怀疑是代码写错了。
   必须写 `is not None`。验收脚本（标准 4）特意把两种写法
   都跑一遍并打印后果对照：正确写法 0/100 段送复核，
   错误写法 100/100 段送复核。**"引擎没提供置信度"这个整体降级
   由 `detect_silent_failures()` 报 `review gate degraded` 告警**（T1-05），
   分流规则本身不擅自扩大复核范围。

2. **异常 flag 是与置信度**独立**的第二条判据，不能合并。**
   `confidence` 是"引擎对整段音频有多确信"，它覆盖不了
   "两个人同时说话"：引擎可以非常确信自己听见了字（0.98），
   但那些字是叠在一起的，内容不可用。静音同理——引擎很确定
   "这里是静音"，但那段根本不该出现在正文里。
   这类错误靠分数发现不了，只能靠 flag。
   反过来，flag 判据必须走**白名单**（只有 `silence`/`overlap`）：
   `transcript_segment.flags` 将来会加各种信息性标记，
   若"有标记就送复核"，新增一个纯信息 flag 会静默地把复核量翻倍，
   而没人会想到是这里引起的。

3. **"待补充"不是"留空"。**
   元信息表空着格子，归档三个月后没人分得清是"这场会没有主持人"
   还是"我们没填"——留空是**沉默的谎言**。填「待补充」是主动声明
   这里有缺口，一眼可见，而且 `grep 待补充` 就能列出所有待补的记录稿。
   注意**只有元信息**用这个规则；正文段落不能因为"听不清"就填
   「待补充」（那会把可核查的原文替换成一句无信息量的占位），
   正文的空段标 `（空）`，听不清的段照常保留原文并进第三节待核对清单。

4. **记录稿要**递增留版本**，绝不覆盖。**
   每次生成写 `record/v{N+1}.md`，N 从"目录 ∪ manifest"的已有版本推。
   核对过程中有人改了正文、之后又重跑一次生成，覆盖会让
   "我核的是哪一版"无从回答。取并集而不是只看目录也有原因：
   目录看的是"真有什么文件"，manifest 看的是"登记过什么"——
   文件被外力删掉时，只有 manifest 还记得曾有过 v2，
   新版本号才能正确跳到 v3（否则会重写 v2，审计里两条 detail
   指向同一路径但内容不同，无法分辨）。
   `record/` 是加密区，多留几版的代价很小。

5. **记录稿正文要保留**全部**段落，包括待复核的那些。**
   待复核只是额外在第三节列出来提醒人去核，不能把正文里那一行抽走 ——
   抽走会让正文时间码出现空洞，使用者会以为是"那段时间没人说话"。
   记录稿的定位是"会议的完整记录"，少一段就是漏记；
   而"记要"（提炼、结论化）是 T1-09 之后 `extraction`/`minutes` 的职责，
   SAD §4 把 M07 的边界明写为**"不做纪要生成"**。

> **另注：`record_generate` 是新增的审计动作。**
> 施工卡 T1-04 给的 13 个动作里没有它，但 SAD §5.1 状态机的
> `reviewing -> record_ready` 必须有出处：记录稿是后续所有抽取与生成的
> **输入**，它若被人改动过，追溯出的问题会指向错误的方向。
> 已在 `infra/audit.py` 显式登记，并归入部署手册 §6.2「文稿修改记录」
> 核查项（不新增类别，最小核查项仍是 8 类）。
> `tests/unit/test_audit.py` 的白名单回归锁已同步更新 ——
> **新增动作必须显式登记 + 同步测试与文档**，这条纪律没有松动。

> **另注：测"阈值敏感性"的数据不能把中间带挖空。**
> 验收脚本标准 1 既要验"复核占比 < 20%"，也要演示"调严阈值会怎样"。
> 第一版造的数据是"合格段一律 0.93、低分一律 0.48"，
> 于是阈值 0.70 与 0.90 给出**完全一样**的占比（都是 1.7%），
> "阈值可热改"这条就没验到。修法是让置信度按真实分布铺开
> （0.94 为主，另有一批落在 0.71~0.89 之间），
> 调严后占比才从 1.7% 升到 4.3%。**造数据时挖空中间带，
> 会得出与真实系统相反的结论。**

## 公文版式八条铁律（T1-09 踩坑实录，第 8 条由 T1-10 回归补）

**这张卡是全项目坑最多的一张。** 原因不是 OOXML 难，而是它**只会静默出错**：
版式写错了 Word 照样打开，只是字不是那个字、表格缩进多两格。
`python-docx` 的高层 API 对中文排版覆盖极少，凡中文相关的属性
基本都要手写 OOXML。以下七条都是"看着没问题、解压一看是错的"。

1. **只设 `run.font.name` 中文不生效。**
   `w:rFonts` 有四个属性：`w:ascii`（西文）、`w:hAnsi`（西文扩展）、
   `w:eastAsia`（东亚）、`w:cs`（复杂文种）。python-docx 的
   `font.name = "仿宋_GB2312"` **只写 ascii 与 hAnsi**，中文走的
   `w:eastAsia` 完全没设 —— Word 于是回退到默认中文字体，
   你在 python-docx 里读回来还是"仿宋_GB2312"，查不出来。
   必须四个一起显式设。
   *附带*：`w:rFonts` 必须是 `w:rPr` 的**第一个子元素**（schema 要求），
   位置错了 Word 报"文档已损坏"；还要删掉 `w:asciiTheme` 之类的
   主题字体引用 —— 主题优先级**高于**直接属性，会覆盖你刚设的值。

2. **`w:ind` 的八个属性要整组清，漏一个就"穿透"。**
   `firstLineChars` / `firstLine` / `leftChars` / `left` /
   `rightChars` / `right` / `hangingChars` / `hanging`。
   表格缩进穿透（C15）的根因是**表格继承了正文的段落样式**：
   正文设了"首行缩进 2 字符"之后，单元格里每个字都跟着缩进 ——
   单元格本来就窄，文字被挤出边框，表格看着"破了个洞"。
   只清 `firstLine*` 而留着 `left*`，表格依然整体右移。

3. **首行缩进用 `firstLineChars`，但必须把 `firstLine` 显式清零。**
   两套属性同时在时，不同版本 Word 的处理不一致（有的以 Chars 为准，
   有的相加）。本项目统一**写 Chars、显式零绝对值**，让文档里
   只有一个真相。用 Chars 而不是固定磅值，是因为 GB/T 9704 说
   "2 字符"指的是**字符**：字号从三号改到小四时，物理宽度应当跟着变。

4. **遍历表格要给"每个单元格的每个段落"清零，不是 `paragraphs[0]`。**
   一个单元格里可能有多个段落（多行文字），只处理第一个是极常见的漏改。
   另外把对齐设成**左对齐**：正文若是两端对齐（`justify`），
   单元格里的短文本会被拉出难看的字间距。
   `table.autofit = False` 也要设 —— 自适应表格会按内容重算列宽，
   把残留缩进算进去，输出就不可复现了。

5. **固定行距是"每页 22 行"反推出来的，不能用多倍行距。**
   28.8 pt ÷ 20 = **576 twips**，且 `w:lineRule` 必须是 `exact`。
   多倍行距随字号变：正文里插一个 22pt 的标题就会把那一行撑开，
   每页行数不再是 22 —— GB/T 9704 的版心要求就废了。
   *另注*：28.8pt 不是"标准里写着 28.8"，而是"版心高 225mm ÷ 22 行"
   反算的结果。改每页行数就要重算，别照着抄。

6. **页码是"域"，python-docx 没有 API。**
   `PAGE` 必须写成三段：`fldChar(begin)` + `instrText>PAGE` +
   `fldChar(end)`（中间还可有 `separate`）。缺任何一段都不对：
   只写 instrText 是纯文本（插入删除内容后页码不会更新），
   只写 begin/end 是空域（显示空白）。页码在**页脚部件**
   （`word/footer*.xml`），不在 `document.xml` 里 —— 只查
   document.xml 会永远报"缺页码"。多 section 时还要
   `footer.is_linked_to_previous = False`，否则第二个 section
   的页脚继承第一个，域只会出现一次。

7. **`python-docx` 必须单点隔离，且校验要读原始 XML。**
   前者见「硬约束」里的 `_docx_backend.py` 说明。后者是方法论的坑：
   **python-docx 读不到的属性等于不存在**。它读回时走自己的对象模型，
   表格里残留的 `w:ind` 可能根本不暴露。所以从
   `tools/verify_docx_style.py` 到全部单元测试，一律
   **解压 → 读 XML → 逐项断言**。这也是部署手册 §7.5 给运维的
   第一步排障手段。

> **字体是商业资产，不能随包分发。**
> 方正小标宋简体 / 仿宋_GB2312 / 楷体_GB2312 都有版权（部署手册 §2.1）。
> 模板**只引用字体名**，二进制一个字节都不带。缺字体时按
> `FONT_FALLBACK` 链回退（如 仿宋_GB2312 → 仿宋 → 宋体），
> 并产生 **E5002 警告级**问题；`font_fallback_policy=fail` 时才升级为
> 阻断导出（**E5001** 用于"版式模板缺失"这一错误级场景，两者别混）。
> **检测走注册表** `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Fonts`
> ——这是部署手册 §2.2 认定的权威清单，不要靠扫字体目录猜。
> 非 Windows（无注册表）时**放行不报缺**：拿不到清单不等于字体不在，
> 把"不知道"报成"缺失"会让 Linux 上每次导出都刷一片假警告。

> **交付物不适用"留版本"策略。**
> C07 幂等键 `export:{meeting_id}:v{version}:{content_sha256[:16]}` ——
> 同键重复导出**覆盖同名文件**，而不是像 `record/` 那样另存新版本。
> 原因：`record/` 是过程稿（要能追溯"我上一版改了什么"），
> `export/` 是**交付物**（给外面看的，同一版本就该只有一个文件，
> 多出个 `-v1(1).docx` 会让人不知道该交哪份）。
> 另注 `export/` 属于 `PLAINTEXT_AREAS`（SAD §11.2）——
> 它**必须**不加密，因为 docx 是要交给 Word 打开的交付物。

> **`.doc` 转换独立进程，且缺 soffice 不算失败。**
> `soffice --headless --convert-to doc --outdir <dir> <docx>` 必须作为
> 独立进程调用（GPL 隔离，SAD §6/§7）。本机没有 soffice 时状态记
> **`skipped`** 而不是 error —— 一期的 `.doc` 是可选输出（`.docx` 才是），
> 把它算成失败会让"没装 LibreOffice"的机器永远验收不过。

> **★ 第 8 条（T1-10 全量回归时补）：序列化必须钉死 ZIP 时间戳。**
> 这条是**在 T1-10 全量回归里才暴露**的 T1-09 缺陷，而且是最阴的一类：
> 它**不确定复现**。
>
> `docx` 是 ZIP。python-docx 的 `doc.save()` 底层是 `zipfile.ZipFile`，
> 给每个条目写的 `ZipInfo.date_time` 是**当前本地时间**。于是
> "内容完全相同"的两次渲染，产出的字节**不一样**：
>
> ```
> word/document.xml  date=(2026,9,28,16,45,28) crc=ca5fecda
> word/document.xml  date=(2026,9,28,16,45,30) crc=ca5fecda
> #        ↑ 变了            ↑ 没变 —— 内容一致，只有时钟在动
> ```
>
> 而 `ExportService.export_docx` 判断「复用」用的正是
> **渲染字节的 sha256**（与 manifest 里已落盘文件的哈希比对）。
> 两者一旦跨秒，`reused` 就变成 `False`：重复导出会真的重写文件、
> 重登 manifest —— **C07 幂等形同虚设**，且导出的文件永远无法做
> 字节级校验（基准快照也没法字节对照）。
>
> *为什么以前没发现*：同一次测试里两次导出经常落在同一秒内，
> 哈希碰巧相等。用例越小越快越容易"过"，全量回归（1700+ 用例）
> 才把它抖出来 —— 这类缺陷靠"重跑一下"永远不会被抓住。
>
> **修法**：`domain/docx/_docx_backend.py` 提供 `save_bytes()`，
> 把 ZIP 重写成固定时间戳 `DETERMINISTIC_ZIP_DATETIME = (1980,1,1,0,0,0)`
> （ZIP 时间字段的起算点，不能再早）。`_docx_bytes` 一律走它。
> 收益是三件事：幂等真成立、基准快照可字节复现、
> `export/` 内"内容相同则字节相同"（可校验传输完整性）。
>
> **防回归**：`tests/unit/test_export_service.py` 的
> `test_docx_bytes_are_reproducible`（`sleep(1.1)` **强制跨秒**，
> 不依赖"跑得够慢"，所以是确定性的网）与
> `test_every_zip_entry_has_fixed_timestamp`。
> 两条都实测过"把实现改回旧写法必失败"。

## 编排六条铁律（T1-10 踩坑实录）

**这张卡的坑不在业务，在框架语义。** LangGraph 不报错、不回滚、
不告诉你写错了 —— 状态被悄悄丢掉、节点被悄悄重放，跑出来的结果
"看着挺正常"。以下六条全部经过实测（`tools/accept_t1_10.py` 逐条断言），
不是文档抄来的。

1. **`state_schema` 必须是 `TypedDict`，不能传裸 `dict`。**
   传 `dict` 时 LangGraph 走的是"整体替换"而不是"合并增量"——
   节点返回 `{"minutes_markdown": "..."}` 会把前面攒下的
   `topics` / `transcript` 全部**抹掉**，下一节点于是报"缺前置输入"。
   因为不抛异常，你会先怀疑是节点写错了，排查很久才发现是构图那行。
   *派生两个坑*：
   - `TypedDict(total=False)` 下，**首次 `invoke` 不能传空字典**，
     否则抛 `InvalidUpdateError: Must write to at least one of [...]`
     —— 必须传 `{"_gate_route": None, "errors": []}`（即
     `nodes/_base.py` 的 `INITIAL_STATE`）。
   - TypedDict 里**没声明的键会被静默丢弃**。想往状态里塞临时值，
     先去 `state.py` 加键，别指望 LangGraph 帮你留着。

2. **`interrupt()` 会把整个节点从头重放一遍。**
   所以一次完整运行里，**闸口节点恰好执行两次**，业务节点恰好一次。
   这不是 bug，是 checkpoint 的恢复语义（"回到中断前的指令边界重新跑"）。
   直接后果就是上表那条硬约束：**闸口节点必须是纯的**——
   凡是在闸口里写审计、落盘、发通知，都会**做两遍**。
   接线一律放到下游节点，或在闸口里通过 `_apply_decision` 只改状态。
   *要区分的情况*：载荷为空的**自动放行路径不会 interrupt**，
   那条路径上闸口只跑一次。所以"跑两次"是**人工确认**路径的特征。

3. **节点必须返回"状态增量"，空字典 = 不改动。**
   想看一个节点跑了没有，别在状态里埋计数器 ——
   状态会被检查点持久化并**在重放时一并复现**，计数器会把
   "重放"算成"又跑了一次"，得出错误结论。
   正确做法：把计数放在**图外面**的 dict（`runner.py` 与
   `accept_t1_10.py` 的 `counts` / `R` 都是这么做的）。

4. **`SqliteSaver` 连接一任务一个，且不能跨线程。**
   `sqlite3` 默认 `check_same_thread=True`，LangGraph 的检查点库
   在服务层会被多线程调用。必须按任务 id 分别建连接
   （`check_same_thread=False` 只是权宜，不解决并发写），
   并在任务结束时关闭。共用一个全局连接的后果是偶发
   `ProgrammingError: SQLite objects created in a thread...` ——
   单测跑不出来，上线才炸。

5. **`edit` 决策必须"注入后往下走"，绝不能"退回上游重跑"。**
   这是 SAD §5.3 区分 approve/reject/edit 三个决策的**唯一理由**，
   也是"降低返工"的关键：
   - `approve` → 原样继续（不重跑任何节点）；
   - `edit` → 用改后的载荷**覆盖状态**，从下游继续（不重跑，只重算下游）；
   - `reject` → 清掉当前节点产物，**只重跑被驳回的那一个节点**。
   如果 `edit` 走成 `redo`，用户改一个错别字就要重跑整条
   extract→generate→validate→assemble，而且**改完还可能被覆盖掉**。
   *连带坑*：每个闸口能改的字段**不一样**
   （`GATE_EDITABLE_FIELDS = {"G2": ("topics","resolutions","action_items"),
   "G3": ("minutes_markdown",)}`）。用一套扁平的白名单会让
   G3 能改 `topics` —— 那等于**绕过 G2 闸口**。

6. **自检重试是"1 + MAX_VALIDATE_RETRY"次，不是 1 次，也不是死循环。**
   `validate` 发现问题不通过时，`route_after_validate` 回 `generate`
   重试；重试**治不了数据问题**（缺 refs 就是缺 refs），
   于是烧掉 `MAX_VALIDATE_RETRY = 2` 次后走 `give_up` → `assemble`，
   **把问题清单带进正文成文**（U-ST-05：不静默丢弃）。
   *排查提示*：如果你看到 `generate` / `validate` 各跑 3 次，
   别急着当成图有 bug —— 那是 1 次正常 + 2 次重试，
   先去查 `edit` 载荷里的 `refs` 是不是空的。
   *另一个易混点*：记录稿为空时 `gate_g2` 的 `_payload_is_empty` 为真，
   记 **E4003（警告级）并自动放行**（不 interrupt、不重放），
   紧接着 `generate` 的 `NODE_REQUIRES` 抛
   `NodeInputError`（E9001）—— 这两个行为是**串起来**的，别单独解释。

> **闸口的三个决策在界面上的文案是固定的**（SAD §5.3）：
> `reject` = 「退回重做」，`edit` = 「改完继续」。
> 不要自己造词 —— 用户看不懂"驳回/编辑"这种开发术语，
> 而把 `edit` 说成"重做"会让人以为改动会被丢弃。

> **`_gate_route` 与 `_gate_rejects` 是内部状态键（下划线开头）。**
> `_gate_route` 承载条件边的路由结果，`_gate_rejects` 记连续 reject 次数
> （上限 `MAX_GATE_REJECTS = 3`，防止用户在闸口反复退回死循环）。
> 两者都不得暴露给界面层，也不得写进审计明细。

## API 三道门与五条铁律（T1-11 踩坑实录）

本服务**没有登录体系**——它是跟着 Electron 一起装在本机上的后台进程。
所以"谁能调我的接口"完全靠三道门（`main.py` + `api/deps.py`）：

| 门 | 做法 | 为什么缺一不可 |
|---|---|---|
| ① 只听回环 | 中间件查 `request.client.host` ∈ `{127.0.0.1, ::1, localhost}` | **查来源，不是查 bind**（见铁律 1） |
| ② 启动令牌 | `secrets.token_urlsafe(32)`，每次启动重生成 → `%LOCALAPPDATA%/mmwf/session.token` | 挡"本机上别的程序/别的网页"乱调 |
| ③ 关闭文档 | `docs_url=redoc_url=openapi_url=None` | 否则浏览器一开 `/docs` 就是一份可直接点着玩的接口列表 |

**五条铁律：**

1. **回环锁定必须查 `request.client.host`，不能靠 `bind` 地址。**
   `bind` 只决定"能不能连上"，而代理、端口转发、`curl --interface`
   都能绕过它。所以 `main.py` 的中间件查的是请求来源。
   *附带结论*：真把服务绑到 `0.0.0.0` 时，**唯一**挡住外部访问的就是
   这条中间件 —— 这也解释了为什么它必须在应用层而不是在部署脚本里。

2. **必须同时注册 `MmwfError` 和 `Exception` 两个异常处理器。**
   这是本卡最阴的坑：Starlette 的 `Exception` 兜底处理器
   **不会捕获 `Depends(...)` 里抛出的异常** —— 依赖在路由函数之前、
   在另一层调用栈里执行，异常不经过路由函数的 `try` 边界。
   只注册 `Exception` 时，`require_token` 抛的 E6001 会**原样冒出去**，
   用户看到 500 + 堆栈。（也是靠验收脚本才发现的，不是靠读文档。）

3. **统一 200 + 信封，不能"半半拉愣"。**
   只要有一个端点写成 `raise HTTPException(status_code=400)`，
   前端就得同时处理两种响应形态。所以入参校验失败也转成
   `E1001` + 200（用 `RequestValidationError` 处理器），
   **不 raise HTTPException**。判据是 `accept_t1_11.py` 附加 A：
   成功与失败的信封**键集合必须完全一致**。

4. **令牌比较必须 `secrets.compare_digest`，不能用 `==`。**
   字符串 `==` 在第一个不同字符处短路，耗时随"前多少位相同"变化，
   理论上可被逐位试探。本机场景风险低，但改成定长比较的成本是零。

5. **码表必须"按族扫前缀"自检，不能只数总数。**
   E3xxx（抽取与生成）整族 4 个码**一个都没登记**，而当时总数看着
   还有 23 条 —— 只数总数完全发现不了。`SchemaViolationError → E3002`
   从 T1-07 起就在施工文档里点名，代码也在抛，但码表就是漏了整族。
   **整族缺失是真实发生过的缺陷**，所以 `test_api.py::TestErrorTable`
   逐前缀扫 + 断言"没有表外的野码"。

> **关于施工卡里"用 `curl --interface` 模拟非回环"这条**：
> **照原样做测不出东西**，验收脚本改用了等效但真能触发的手段。
> 服务绑 `127.0.0.1` 时，`curl --interface 172.24.1.106`（源地址非回环）
> 连回环目的地址 → 内核直接 **rc=7 拒绝**，请求到不了应用层；
> `curl --interface 127.0.0.2` 能连上，但源地址**仍是回环**（整个
> 127/8 都是回环），中间件按设计放行。
> 真正有效的做法：临时把服务绑 `0.0.0.0`，用本机**真实网卡地址**去连 ——
> 服务端看到的就是非回环 IP。它还顺带覆盖了真正要防的场景
> （端口转发 / 别的机器从局域网访问），而 `curl --interface`
> 这个手法在真实攻击里并不存在。

> **`/docs` 关闭后返回的是 404，不是 401/403。** 别以为"关了"就等于
> "要授权"——FastAPI 把这三个路由整个摘掉，路径就是不存在。
> ⚠️ 而且**状态码必须是 404，不能是"200 + 信封"**：见下面铁律 9。

## API 复查实录（T1-11 Review，10 个真实缺陷）

施工卡交付后做了一轮代码复查。**验收脚本当时 8/8 全绿，而 10 个端点里
有 4 个完全不可用** —— 这是本节最该记住的一件事。

### 复查方法

不是靠读代码，是靠**跑**：写一次性探针脚本（`C:/tmp/probe*.py`）
用 `TestClient(app, raise_server_exceptions=False)` 把每个端点都**真的调一遍**，
打印返回的 `code` 与 `status`。第一个探针就把问题全暴露了：

```
✗ POST /api/v1/meetings/{id}/start            E9001
✗ POST /api/v1/meetings/{id}/gate/G2/decide   E4001
✗ POST /api/v1/meetings/{id}/gate/G3/decide   E4001
✗ POST /api/v1/meetings/{id}/export/undo      E1002
```

### 缺陷清单（按严重度）

| # | 缺陷 | 症状 | 根因 |
|---|---|---|---|
| 9 | `_runner()` 没传 `deps` | `/start` 恒定 E9001 | 节点退回 `get_settings()`，与 API **读写不同的数据目录** |
| 4 | `_runner()` 没传 `checkpoint_path` | 四个端点全 E9001 | 图无检查点 → `ValueError: No checkpointer set` |
| 5 | `with _require_meeting(...)` | `/start` 恒定 E9001 | 它返回 `dict`，不是上下文管理器 |
| 8 | `ALLOWED_PREV_STATES` 挡住 `created` | 每次 start 都在 review 抛错 | 从 API 建的会议状态恰好是 `created`，而流水线从不写它 |
| 6 | 文字稿导入不落 `segments.json` | `review` 报"转写分段不存在" | 两条进料口只接了一条 |
| 7 | `record_markdown` 混入元信息表 | **15 条自检问题，14 条误报** | 完整稿（给人看）被当成正文（给机器读） |
| 10 | `review` 幂等键漏 `record_markdown` | 改了记录稿"没反应" | 文字稿路上 `transcript=[]` 恒定不变 |
| 1 | 成功响应 `trace_id` 是 `null` | 前端要写两条分支 | 只有错误路径回填了 trace_id |
| 2 | 404/405 绕过信封 | 返回 `{"detail":"Not Found"}` | Starlette 路由层异常没注册处理器 |
| 3 | `export` 里吞掉 `MmwfError` | 丢 trace_id、重复全局处理器 | 端点里又包了一层 try/except |

### 新增铁律

6. **`Deps` 必须显式传 `settings`，否则 API 与流水线会用两份配置。**
   `Deps()` 字段默认全 `None`，各节点的 `_resolve()` 在
   `deps.settings is None` 时退回 `settings.get_settings()` ——
   那是**从磁盘重新加载**的一份，与 `create_app(cfg)` 那份**不是同一对象**。
   后果是**读写的不是同一个数据目录**。
   最阴的地方：**生产上不报错**（两处恰好都指向同一个 `data/`），
   只在测试 / 多实例 / 换了配置目录时炸，而症状（"转写分段不存在"）
   把排查方向引向数据本身，不是配置。
   → `routes._runner()` 必须 `GraphRunner(..., deps=Deps(settings=cfg), ...)`。

7. **"给人看的稿"与"给机器读的稿"必须分开。**
   记录稿完整版含元信息表与待核对清单，而 `extract` 把它当作
   "这次会议说了什么"的唯一输入 —— 实测一篇正常记录稿产出
   **15 条自检问题、14 条是误报**，而且因为 `route_after_validate`
   一看到 issues 就重试，**每篇纪要都会走满重试路径**再带噪音成文。
   → `record_markdown` 只放正文（`ReviewService.extract_body()`），
   完整稿仍在 `review_result.rel_path` 里，随时可读回。

8. **幂等键要覆盖"用户能改的输入"，否则改动会被静默吞掉。**
   文字稿导入路上 `transcript` 恒为空表，键里那一段从来没变过 →
   用户改了记录稿再点"重新生成"会**幂等命中**上一轮结果：
   不报错、不提示，就是"改了没反应"。→ 键里带上 `record_markdown`。

9. **关掉文档的路由必须返回真 404，不能被信封处理器接管。**
   `docs_url=None` 只做到"没有这页"，而保密探测脚本看的是
   **HTTP 状态码** —— 一个 `200` 会被记成"文档页开着"，
   这道门就成了摆设。所以 `StarletteHTTPException` 处理器里
   **显式放行 `/api/v1` 之外的路径**。
   两个契约的边界由"是不是 API 路径"来划，而不是靠例外名单。

10. **验收脚本必须有正向断言，而且要断言到"产物出来了"。**
    只测"错误路径都对"（没令牌会怎样、路径错了会怎样）**完全推不出**
    "正常用一次能走通"。第一版脚本 8/8 绿而 4 个端点全废，
    就是因为它**从来没走过一遍正常流程**。
    → `accept_t1_11.py` 附加 D：建会议 → start → G2 → G3 →

## API 复查实录 · 第二轮（把上面那条铁律真的执行了一遍）

### 新增缺陷

| # | 缺陷 | 症状 | 根因 |
|---|---|---|---|
| 11 | **`create_app()` 从不迁移数据库** | 全新安装第一次建会议 → `sqlite3.OperationalError: no such table: meeting` → E9001 | 迁移只在测试的 fixture 与 `tools/migrate.py` 里调；产品启动路径没调 |
| 12 | **`missing_inputs` 把"空列表"当"上游没跑"** | G2 approve 后恒定 E9001，**一整类会议拿不到纪要** | `resolutions=[]` 是正常抽取结论（记录稿里没有决议句），却被判成缺输入 |
| 13 | **`trace_id` 回填是死代码** | 成功响应 `trace_id` 恒为 `null` | 读 `response.body`，而端点是 `def` 返回 dict → Starlette 包成 `_AsyncLazyJSONResponse`（只有 `body_iterator`） |

### 已解决：缺陷 11（全新安装 = 每个用户的第一次使用）

`create_app()` 里补 `_migrate_once(cfg)`，用**库文件绝对路径**做缓存键。
缓存是必需的 —— `tests/unit/test_api.py` 每个用例建一次 app，
1800 多个用例各跑一次迁移会把回归时间拖垮。

这不是边角 case：**全新安装就是每一个用户的第一次使用**，
而且症状（"程序遇到一个未预期的问题"）把方向指向代码，
真相却是"数据库还没建"。

### 已解决：缺陷 12（"空"有两种含义）

`_base.missing_inputs` 现在区分：

```
字段不在状态里（None）        -> 缺（上游真的没跑）
空白字符串                    -> 缺（"看着非空、实则无用"）
空列表 + 产出方跑过了          -> **不缺**（"本次就是没有"）
空列表 + 产出方没跑过          -> 缺
```

判据不是字段名，是**产出方是否跑过**（反查 `NODE_OUTPUTS`，
再用该节点的 `NODE_REQUIRES` 或"其他产物非空"作证据）。

报错文案本身也有责任：原来写"这通常意味着图的连边顺序被改动了"，
把排查方向**引向图结构**，而真相是抽取结果本来就是空的。
这类"错误信息指错方向"比报错本身更耗时间。

### 已解决：缺陷 13（写了但一行都没执行的代码）

回填逻辑必须用 `response.body_iterator` 重读，而且**三种形态都要覆盖**：

| 形态 | 何时出现 |
|---|---|
| `bytes` | `_AsyncLazyJSONResponse` 收 dict/list |
| 异步生成器 | 同一个类收 `BaseModel` |
| 同步迭代器 | 一般的 `Response` |

⚠️ 生成器**已被消费**，读完必须把字节放回 `body_iterator`，
否则响应体凭空变空 —— 这个坑只在走生成器分支时出现，很隐蔽。

### 待办：缺陷 14（已缓解，未根治）

`_runner()` 每次新建 + `close()` 的设计有**结构性漏洞**：
`GraphRunner.app` 是**惰性编译**的，`_saver` 只在第一次访问 `.app`
时才创建。所以刚 new 出来、还没跑过的 runner，`close()` 是**空操作** ——
`GET /meetings/{id}` 和 `GET /meetings` 这两个"只想读一眼状态"的端点
完全没有释放连接，全靠 GC。

本次的处理是**缓解**（不是根治）：`build_router` 里加"每个会议一把
`threading.RLock`"，把同一会议的流水线操作串行化。跨会议仍并发，
不牺牲吞吐；而同会议并发推进本来也是不该允许的语义。

**根治方案**（留给 T1-13 或专门的并发卡）：让 `GraphRunner`
把 `_saver` 的创建提到 `__init__`（或给 `close()` 加"确保已创建再关"），
这样生命周期就与 runner 一致，不依赖 `.app` 被访问过。
本次没动它是因为它属于 **T1-10 的产物**，改它要连带复查
checkpoint / 幂等 / `run_counts` 三条链，超出本卡范围。

判断依据：**E6001 出现概率 0/30**（加锁前）vs **0/40**（加锁后），
未复现。所以"已缓解、未复现"，不冒认"已修复"。

### 已解决：缺陷 15（用户填错被报成"系统内部错误"）

**症状**：`POST /glossary` 传一个非法类别（`category: "not_a_category"`），
响应是 `200 + 信封`，但错误码 **E9001**（"程序遇到一个未预期的问题，
请把界面上的编号告诉技术人员"）。而用户只要把类别改成
「单位/人名/术语/代号」就好了。

**根因**：`GlossaryFormatError` **不是** `MmwfError` 的子类。
`@app.exception_handler(MmwfError)` 兜不住它，
于是掉进 `@app.exception_handler(Exception)` 那个兜底分支 ——
HTTP 状态码和信封形状**全都正确**，唯独错误码是 E9001。

**危害有两层**：① 用户被误导去"联系技术人员"；
② **E9001 这个信号被污染**（SAD §9.3 要求 E9 只用于真正的未预期故障，
将来真出内部错误时运维要在噪音里翻找）。

**修法**：路由层显式 `except GlossaryFormatError` → 翻成 E1001，
并给出面向行政人员的文案（点明能填什么）。

**发现方式**：`tools/accept_t1_14.py` 的附加 A。
**注**：只看 HTTP 状态码或"信封里有没有 ok 字段"的测试**全都抓不到它**。

### 已解决：缺陷 16（同一类异常，两个错误码）

**症状**：同一个端点、同一个异常类，两个输入得到两个不同的错误码：

```
POST /glossary {"category":"bad"}    → E1001 ✅
POST /glossary {"aliases": 12345}    → E9001 ❌
```

**根因**：`_build_entry` 里 `parse_aliases()` 与 `GlossaryEntry(...)`
构造**抛的是同一个异常类**，但第一版只把构造包进 `try`，
`parse_aliases()` 写在 `try` **外面** —— 它抛的异常直接冒到兜底处理器。

**为什么难发现**：两个分支的**代码看起来一模一样**，
报出来的错误码却不同。靠阅读几乎发现不了，是验收脚本对比两个用例才暴露的。

**修法**：把"所有可能抛 `GlossaryFormatError` 的调用"都放进同一个 `try`。
写 `try` 块的判据是"**哪些调用会抛这个异常**"，
而不是"哪一行看起来像在构造对象"。

**发现方式**：`tools/accept_t1_14.py` 的附加 A。

### 已解决：缺陷 17（`{'a': 1}` 静默变成一条别名 `('a',)`）

**症状**：`parse_aliases({'a': 1})` 返回 `('a',)` —— 遍历 dict 拿到的是**键**。
而 `parse_aliases(12345)` 抛裸 `TypeError`（→ 又被兜成 E9001）。

**为什么第二种更危险**：它**不报错**。一条别名 `'a'` 悄悄进了库，
将来在正文里几乎必然误匹配，且没有任何痕迹指向"它是从哪来的"。
而本函数的 docstring 恰好写了要防"垃圾静默入库"
（原本只防了 JSON 对象字符串那条路，**真正的 dict 对象**从另一个门进来了）。

**修法**：类型**白名单**（`str` / `list` / `tuple` / `set` / `frozenset`），
白名单外一律 `GlossaryFormatError`。
用白名单而不是"黑名单排除 int/float/dict" —— **黑名单永远漏**。

**发现方式**：`tools/accept_t1_14.py` 的附加 A（连带发现缺陷 15/16 同源）。

### 已解决：缺陷 18（裁决 D8 在响应里落空）

**症状**：`GET /system/fonts` 的响应**没有** `precheck_available` 键，
于是前端拿不到"这次探测到底可不可用"这个信息 ——
它只看到 `all_installed: false` + `missing: [5 个字体]`，
**根本无从分辨"真缺"与"查不了（无权限/非 Windows）"**。

而这正是裁决 D8 要防的：把 `unknown` 当 `missing` 报给用户，
**用户会去装一堆本来就装着的字体**（会浪费别人半天）。

**根因有两层**：
1. `build_check_result_json`（`font_check.py:356`）给的键是
   **`available`**，不是 `precheck_available`（同一个布尔值，不同名字）；
2. **端点的 docstring 写了"已带 `precheck_available`，原样透传"** ——
   这句话是错的，而实现照着它写就信了它，没去核对被调函数的返回值。

**修法（两层，缺一不可）**：
① 补 `precheck_available` 键（保留 `available` 不动，它是 T1-09 的既有拼法）；
② 探测不可用时**把 `detail` 的 status 全降级为 `unknown`、清空 `missing`、
`all_installed=False`** —— 光加 flag 让前端自己判断不够：
任何直接读 `missing` 的消费方（含将来的验收脚本、第三方集成）
都会得出错误结论。**字段内容本身就不该说谎。**

**教训**：docstring 也可能是错的。**引用被调函数的返回值时去核对它**，
别相信"上游注释说它给了这个字段"。

**发现方式**：`tools/accept_t1_14.py` 的标准 2。

### 收尾：附加 D 的"正向断言"改成进程内驱动（9/9 绿）

第二轮修完上面 4 个缺陷后，**附加 D（正常流程闭环）依然红**，
而且红法很怪：

```
✓ 前置：令牌文件与内存一致
✓ 前置：带令牌握手成功（实测 code=OK）   ← 同一个令牌、同一条 curl
✗ 建会议 -> code=E6001（会话已失效）
```

**同一个令牌，握手能过、建会议不能过** —— 这组合在产品代码里
不可能出现（两处走的是同一个 `require_token`）。逐层隔离后定位到
**不是产品问题**：

| 隔离手段 | 结果 |
|---|---|
| 服务端打印收到的 header | `X-MMWF-Token` 到服务端是**空串** |
| 脚本外单跑同一 `Backend.curl` 建会议（2/3/5 键全组合） | **全部成功** |
| 起专用 header 打印中间件 | 头正常到达、请求成功 |
| **进程内** `TestClient` 跑完整闭环 | **全绿** |

同一个调用链，进程外必红、进程内必绿 ⇒ 败在本机 **HTTP 传输环境**：
本机设了 `http_proxy`（`127.0.0.1:58045`），且沙箱会拦截本地 HTTP
（`Sandbox Intercept Info: Network intercepts: 172.19.0.1:<port>`），
两者都可能改写/吞掉请求头。

**结论与改法：这不是"绕过验收"，而是把断言放对位置。**

- **三道门（回环 / 令牌 / 文档 404）继续用真进程 curl** —— 那才是它们
  的真实语义（`request.client.host`、端口文件都只在真 socket 下成立）；
- **业务闭环改用进程内 `TestClient`** —— 仍走同一个 `create_app()`、
  同一套中间件、同一个路由器，只是不经 TCP，因而**确定性**。

改造过程中又踩了两个**测试基建**的坑（都已修，且都不是产品缺陷）：

1. 进程内 app 的 `verify_token()` → `token_path()` 是**每次请求时**现读
   `LOCALAPPDATA` 的（`deps.app_dir()` 无缓存）。只在建 app 时压环境变量
   不够，必须**每次请求**都把 `LOCALAPPDATA` 压到后端的 appdata，
   否则会去读本机真实目录下那份**不相干**的令牌 → 握手就 E6001。
2. 不能"一次请求开一个 `TestClient`"。反复短命开关 `with TestClient(...)`
   会让退出阶段的 `wait_shutdown` 和 anyio portal 抢生命周期，偶发抛
   `RuntimeError: This portal is not running`（三次连跑稳定出现一次）。
   改成**整个闭环共用一个 `TestClient`**（一次 lifespan），问题消失。

最终状态：**验收 9/9，连跑 6 次全绿（92 ✓ / 0 ✗ / 0 Traceback），
回归 1806 通过 / 0 失败。**

## T1-13 实录 · 合规自检（证明"无外发"，且证明这个证明有效）

### 一句话

给保密检查人员一个端点：`GET /system/selfcheck` —— 点一下就看到
"本程序没有对外发过任何连接"，而且这个结论是**主动探测**出来的、
**经得起反向验证**。

### 四项检查与数据来源

| # | 检查 | 真的去问什么 |
|---|---|---|
| ① | 网络行为 | `psutil.Process().net_connections()` —— 真数 socket，不是读配置 |
| ② | ASR 质量 | `transcript_segment.confidence` 最近样本 —— 真算均值 |
| ③ | 字体可用性 | 注册表（复用 T1-09 `font_check`）—— 真查字体装没装 |
| ④ | 审计链完整性 | `audit_log` 逐行重算哈希（复用 T1-04 `verify_chain`） |

### ★ 本轮最要紧的一条设计约束：判定只认**本进程**

**第一版踩的坑**：把"全机器所有进程的连接"也算进 `outbound_connections`。
实测本机（开着浏览器/更新器）有 **52 条**到 443 的连接 →
`outbound_connections = 52`、`verdict = fail`，而验收要求 `== 0`。

数字大只是表象。**真正的问题是语义错了**：

> 本项目的合规主张是"**我这个程序**不发外部请求"。
> 别进程连不连外网，与本程序毫无关系。

把它们算进来，等于"装了浏览器"就会让合规自检变红 ——
这种自检在真实机器上**永远过不了**，检查人员一眼就会判它是摆设。

**修正后的字段分工**：

| 字段 | 参与判定？ | 说明 |
|---|---|---|
| `outbound_connections` / `outbound_detail` / `listening_ports` | ✅ | **只统计本进程** —— "我没外发"的直接证据 |
| `machine_outbound_processes` | ❌ | 全机器上**别的进程**的连接，作现场信息（让检查人员理解"这台电脑本身是联网的"） |
| `scope` | —— | 自报 `own_process`，是"证明的是我自己"的凭据 |

顺带一个好处：**本进程**探测 (`psutil.Process()`) **不需要管理员权限**，
而全系统探测在 Windows 上可能需要 —— 判定走在永远可用的那条路上。

### `dns_queries_attempted` 如实报**不支持**

施工卡"常见坑"第 3 条明确要求：一期可报不支持，但**不能假装有**。
本项返回 `None`，**不是 0**。

**为什么不"试一把 patch 就报个数"**：打桩 `socket.getaddrinfo` 必须在
进程启动**极早期**装上；端点被调用时早期解析早就过去了，数出来必然是 0。
**一个恒为 0 的数字比 None 更危险** —— 它看起来像"已验证没有 DNS 查询"，
实际只是"没数到"。宁可给一个诚实的空缺。

### ★ 实测踩到的真问题：`httpx.get()` 完成后**探测不到**

照施工卡字面做验收 ③：`httpx.get("https://example.com")` 然后立刻自检
→ **检不出**。诊断后确认原因：

> httpx 的请求**完成**之后，连接被连接池收回/关闭，
> 探测那一刻它**已经不在连接表里**了。

这不是自检的缺陷 —— **采样式探测抓的是"正在发生的"外发**，
"历史上发过一次"要靠抓包或长期日志（那是 SEC-03 的活）。
但它说明**照字面执行施工卡会得到一个假失败**，所以判据要改对：
让连接**存活期间**探测（`connect_ex` 后立即查询即可见）。

这个发现直接影响了验收脚本的设计：③ 做成三重重反验证，
其中 ③-b（真 socket 注入后立即探测）是**最硬的一条证据** ——
它证明 `0` 是**探测得出的**，而不是**写死的**。

### 三档结论：`unsupported` 必须与 `fail` 分开

| verdict | 含义 |
|---|---|
| `pass` | 探测通过 |
| `fail` | 探测通过且**判定不合格**（如真有外发） |
| `unsupported` | **探测本身跑不了**（缺依赖 / 没权限 / 数据不足） |

把"测不了"混进 `fail` → 每台没装 psutil 的机器都报红；
混进 `pass` → 自检失去意义（测不了 = 通过了？）。
`overall` 因此有第三档 **`degraded`**（有 unsupported、但无 fail）。

### 一个新依赖，以及它为什么不破红线

`psutil>=6.0,<8`（`pyproject.toml` 的 `system` extra）。

**与"离线运行"红线不冲突**：psutil 是**纯本地**系统信息库，
只读内核/OS 暴露的进程与网络元数据，自身不发网络请求、不带遥测。
放它进来恰恰是为了**证明**本进程无外发 —— 它是"**检查工具**"，
不是"**被检查对象**"。

分层：psutil **只允许**出现在 `api/system.py`；已加入 `check_layers.py`
的 `FORBIDDEN_IN_DOMAIN`（领域层禁止 import）。

### ★ 本卡最重要的一条：缺陷 26 是**假缺口**

事前判断把它列为"疑似真缺陷"（理由：只按路径存在就复用很危险）。
**真跑探针之后翻案** —— 实现是"版本 + 内容哈希"双重判据，完全正确：

| 情形 | 操作 | reused | sha256 |
|:---|:---|:---|:---|
| A | 新增 `record/v2.md` | False | 变了 ✓ |
| **B ★** | **同 version=3，就地覆盖内容** | **False** | **变了 ✓** |
| C | 同内容连导两次 | True | 不变 ✓ |

情形 B 才是真正的软肋：**文件名相同、版本号相同，只有内容哈希不同**。
若实现里"路径在就复用"，B 会返回旧字节 → "改了稿、导出还是旧稿"且看不出来。
实测 B 正确 → **判据没问题**。

### 缺陷 14 的修法：`_app` 与 `_saver` 必须**一起**清

第一版只清 `_saver`，两种坏情况：
① 外部注入 `app` 时 `_saver` 恒为 None → `close()` **什么都没关**（连接泄漏）；
② `close()` 后 `_app` 仍非 None → 再访问拿到**已关连接的图** → 远处报
`Cannot operate on a closed database`。

正解：两者一起复位，并用 `_owns_app` 区分"图是不是我们的" ——
**连接永远归实例管，图只清自己编译的**（注入的 app 不能丢，否则调用方手里的引用失效）。
