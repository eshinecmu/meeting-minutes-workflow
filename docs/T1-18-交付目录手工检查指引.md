# T1-18 · 免安装交付目录 —— 手工检查指引

> 这份是给**人**看的：怎么启动、看什么、看到什么算对、出问题往哪查。
> 面向非技术背景，不需要命令行基础，但每一条都给了**可复现的判据**。
>
> 结论先给：**双击就能用**。之前"双击没反应"的根因已定位并修复，见 §5。

---

## 1. 交付目录在哪

```
<项目根>/dist/mmwf-portable/win-unpacked/
```

完整路径：

```
<项目目录>\dist\mmwf-portable\win-unpacked
```

**要双击的文件**：这个目录里的 `mmwf.exe`。

> ⚠️ 注意：`dist\win-unpacked\` 是同一版本的**早期副本**（多带了一个 Electron 自带的
> 欢迎页文件），检查请用 `dist\mmwf-portable\`。两个目录功能一致，
> 但 `mmwf-portable` 是干净的那一份。早期副本可以直接删掉。

### 目录结构（对照部署手册 §10 附录 A）

```
win-unpacked/
├── mmwf.exe            ← 双击这个
├── *.dll / *.pak / locales/ / icudtl.dat …   ← Electron 运行时（自带，无需安装）
└── resources/
    ├── app.asar        ← 界面与主进程代码
    ├── app/            ← 业务代码（Python）+ 运维脚本 app/tools/
    ├── config/         ← 配置（可改：app.yaml / models.yaml / extraction.yaml …）
    └── python/         ← 内嵌 Python 运行时（含全部依赖，目标机无需装 Python）
```

对应关系：部署手册里写的是 `C:/mmwf/{app, runtime, desktop, config, data}`，
本交付目录里 **`resources/` 就扮演 `C:/mmwf/` 的角色**：

| 部署手册 | 本交付目录 |
|:---|:---|
| `C:/mmwf/app` | `resources/app` |
| `C:/mmwf/runtime` | `resources/python` |
| `C:/mmwf/config` | `resources/config` |
| `C:/mmwf/data` | `resources/data`（**首次启动自动创建**） |
| `C:/mmwf/desktop/mmwf.exe` | `win-unpacked/mmwf.exe` |

## 2. 怎么启动

**双击 `mmwf.exe` 即可。** 不需要装 Python、不需要装 Node、不需要联网。

首次启动约 **2–5 秒**（要拉起内嵌 Python 后端并建库），之后会快一些。

## 3. 逐条检查清单

请按顺序做，每条都写了**预期结果**和**不对时的现象**。

| # | 操作 | 预期结果 | 不对时你会看到 |
|:--|:---|:---|:---|
| 1 | 双击 `mmwf.exe` | 出现窗口，标题栏写 **会议纪要工作台** | 什么都不出现（见 §5）；或出现 Electron 自带的欢迎页（说明交付目录拿错了，见 §1 的 ⚠️） |
| 2 | 看窗口顶部 | 一条三步导航：**① 投递音频　② 确认内容　③ 导出文档** | 一片空白 / 转圈不停 |
| 3 | 看窗口中间 | 一张 **「开始使用」** 卡片：操作人输入框 + **进入工作台** 按钮 | 卡片没出来 |
| 4 | 操作人填一个名字 → 点 **进入工作台** | 界面切到工作台（不再显示登录卡片） | 点击无反应 / 报错弹窗 |
| 5 | 关掉窗口 | 窗口消失；**任务管理器里不应残留 `mmwf.exe` 或 `python.exe`** | 残留进程（收尸失败） |
| 6 | 再双击一次 | 能正常再开（说明上一步的数据/端口已释放） | 提示"系统正由 XX 使用中"（单实例锁没释放） |

### 第 4 步之后可以顺手验的两件事

**① 数据确实落盘了**（在交付目录里找）：

```
win-unpacked\resources\data\mmwf.db          ← 业务库（含审计链）
win-unpacked\resources\data\logs\            ← 应用日志
```

**② 全程离线、无外发连接**（这条是保密要点，建议一定要做）。

先看这两个文件的内容，它们就是本次运行要用的端口和令牌：

```
C:/Users/<你的用户名>/AppData/Local/mmwf/port             ← 一行数字，就是端口
C:/Users/<你的用户名>/AppData/Local/mmwf/session.token    ← 一长串字符，就是令牌
```

把上面两个值填进下面这条命令（在任意命令行窗口执行即可）：

```
curl.exe -s -H "X-MMWF-Token: <令牌>" "http://127.0.0.1:<端口>/api/v1/system/selfcheck"
```

预期：返回的 JSON 里 **`outbound_connections` 为 0**，
且服务地址是 `127.0.0.1`（不是 `0.0.0.0`）。
这两个数是架构约束 C11「全程离线、只监听回环」的运行时证据。

## 4. 日志在哪（出问题先看这里）

| 文件 | 位置 | 说明 |
|:---|:---|:---|
| 后端日志 | `C:/Users/<你的用户名>/AppData/Local/mmwf/logs/backend.log` | 后端启动、建库、报错都在这里 |
| 握手文件 | 同上目录下的 `port`、`session.token` | 前端据此找到后端；**只放这两个**，业务数据不在这里 |
| 业务数据 | `<交付目录>\resources\data\` | 库、文件仓储、日志 |

**注意**：`backend.log` 里的路径含会议 id 这类信息，按你们的保密要求
**不要直接外发**，需要时先脱敏。

## 5. 为什么之前"双击没反应"（根因与修复）

这一段建议原样留在验收记录里 —— 它解释了本版本为什么必须改启动参数。

### 现象

双击 `mmwf.exe` 后**什么都没发生**，也没有任何提示。日志里是：

```
ERROR:gpu_process_host.cc(997)] GPU process exited unexpectedly: exit_code=-1073741819
FATAL:gpu_data_manager_impl_private.cc(448)] GPU process isn't usable. Goodbye.
```

`-1073741819` 就是 `0xC0000005`（访问冲突），随后 Electron **主进程直接退出**。

### 根因（这一条和第一版判断**不一样**，是实测更正过的）

第一版只判断到"GPU 子进程崩了"，于是打了 `disable-gpu` 一串开关。**不够。**
用 DevTools 协议直接问渲染进程要 DOM 之后才看清：

| 启动参数 | 进程活着 | **界面真的渲染出来** |
|:---|:---:|:---:|
| 不加参数 | ✗ 直接退出 | ✗ |
| `--disable-gpu` / `+compositing` / `+swiftshader` | ✗ 直接退出 | ✗ |
| `--disable-software-rasterizer`（第一版用的） | ✗ 直接退出 | ✗ |
| `--disable-gpu-sandbox` | **✓ 活着** | **✗ 卡死** |
| `--in-process-gpu` | **✓ 活着** | **✗ 卡死** |
| `--no-sandbox` | ✓ 活着 | ✓ 渲染 |
| `--disable-gpu-sandbox` + 渲染层沙箱关闭 | ✓ 活着 | **✓ 渲染** |

⚠️ 关键在第 4、5 行：**进程活着、窗口也在（任务管理器里有标题），
但界面从来没渲染过** —— 渲染进程连 HTML 都没解析（页面标题为空）。
**只看进程数会得出"已经修好了"的错误结论。**

真正的根因是：**本机（以及同类受管办公机 / 虚拟桌面）上，
Chromium 的 Windows 沙箱无法初始化**，GPU 子进程与渲染子进程都起不来。
所以关掉 GPU 沙箱只能让主进程不自杀，界面依然是死的；
必须再放开**渲染层**沙箱，页面才真正渲染。

### 采用的修复（以及安全取舍，请留意）

```js
// src/desktop/main.js
app.disableHardwareAcceleration();
app.commandLine.appendSwitch('disable-gpu');
app.commandLine.appendSwitch('disable-gpu-compositing');
app.commandLine.appendSwitch('disable-gpu-sandbox');   // 让主进程不再自杀
// 窗口：webPreferences.sandbox = false                 // 让渲染层真的能起来
```

**为什么不用 `--no-sandbox`**：那一个开关会把**所有**子进程
（含网络服务、utility 进程）的沙箱一起关掉。
本项目只需要放开**这一个窗口的渲染层**，网络栈只连 127.0.0.1 回环、
页面只加载本地打包文件，没有理由把网络服务那层也一起关。
**能窄就不宽。**

**代价（必须让保密/运维知道，不能含糊）**：
本版本默认关闭了 **GPU 子进程沙箱** 与 **渲染层沙箱**。
在能正常初始化沙箱的机器上可以恢复严格模式：

| 环境变量 | 作用 |
|:---|:---|
| `MMWF_STRICT_SANDBOX=1` | 恢复沙箱（只应在**沙箱能用的机器**上用，否则界面又会是空白） |
| `MMWF_ENABLE_GPU=1` | 恢复硬件加速（本界面是纯表单，没有收益，不建议） |

> 判断依据：本应用的界面是**纯表单**（投递 / 确认 / 闸口 / 导出），
> 没有 3D、没有 WebGL、没有远程内容。硬件加速在这里没有收益，
> 却引入了一条"启动即死且无提示"的失败路径。

## 6. 已知限制（不影响本次检查，但要知道）

1. **本机没有部署本地大模型**，所以"确认内容"里的**智能提取走的是兜底实现**，
   不是大模型抽取。二期接入本地模型后才会启用真提取（T2-01 引擎已就绪，
   默认不启用，不影响一期行为）。
2. **`resources/data` 与程序在同一个交付目录里。**
   换版本时请**只替换 `resources/app`、`resources/app.asar`、`resources/python`、`resources/config`，
   不要动 `resources/data`** —— 那里面是业务库和审计链，删了不可恢复。
   建议正式部署前先把 `data` 目录单独备份一份。
3. 交付物是**目录**，不是安装包（部署手册 §9.2 交付物 1 就是这么定的：
   内网办公机装"安装程序"反而多一道审批）。
4. `mmwf.exe` **未做代码签名**（本机没有证书）。内网分发请按部署手册 §9.1
   的哈希清单流程自行校验。

## 7. 一句话结论

窗口能出来、三步导航和「开始使用」卡片能显示、填操作人后能进工作台、
关闭后进程能收干净、自检接口 `outbound_connections` 为 0 —— 这五条过了，
一期交付目录就算通过手工检查。
