## 1. 目标

把 SAD §9.1 里**底层服务已完全就绪、只差 HTTP 接线**的 10 个端点补齐。
本卡**不新造领域逻辑**，只做三件事：接线、参数校验、信封。

`/review/accept`、`POST /meetings/{id}/audio`）**预置 repository 层地基** ——

## 2. 关键骨架

### 2.1 A 档：字体预检（1 行接线，但要处理降级）

```python
@router.get("/system/fonts")
def system_fonts():
    """字体可用性预检（F5.7 / R7 / SAD §12.4）。"""
    svc = _export_service_global()          # 注意：不绑会议
    return env.ok(svc.system_fonts_payload())
```

**⚠️ 这里有个不能想当然的点**：`/system/fonts` 是**系统级**端点，
但现有的 `_export_service(meeting_id)` 是**按会议**构造的
（`ExportService` 需要 `FileStore` 定位 manifest）。

本卡的解法：**用一个独立的、不绑会议的探测入口**。
`ExportService.font_report()` 只依赖 `self.font_policy`，不碰 filestore ——
所以直接走 `domain.docx.font_check.check_fonts(policy=...)`，
不构造 service。理由：为了查字体而假装有一个会议，是把系统级端点
错误地耦合到会议生命周期上。

```python
from mmwf.domain.docx.font_check import build_check_result_json, check_fonts

@router.get("/system/fonts")
def system_fonts():
    # 不传 policy：用 check_fonts 的默认 POLICY_WARN。
    return env.ok(build_check_result_json(check_fonts()))
```

**⚠️ 已核对（写进卡里免得实现时又去找）**：
`check_fonts(fonts=None, *, policy=POLICY_WARN, installed=None)` ——
`policy` **有默认值**，`fonts` 为 `None` 时自动走 `required_fonts()`
（读 `domain/docx` 的样式表，不读 `settings`）。
实测 `settings.py` 里**没有** `font_policy` 配置项（只有
`provider: str = "docx_exporter"`），所以**不要**去写
`cfg.docx.font_policy` —— 那个属性不存在，会 AttributeError。
`ExportService` 的 `font_policy` 是构造参数（默认同 `POLICY_WARN`），
不是从 `Settings` 读的。

**必须标注降级**：字体探测在非 Windows / 无权限时可能得到 `UNKNOWN`
而不是 `MISSING`（见 `font_check.STATUS_UNKNOWN`）。响应里要能区分
"确认没装"和"查不出来"——**不能把 `UNKNOWN` 当成 `MISSING` 报给用户**，
否则用户会去装一个本来就装着的字体。

### 2.2 A 档：审计检索（AUD-07）

```python
@router.get("/audit/logs")
def audit_logs(
    from_ts: str | None = None, to_ts: str | None = None,
    operator: str | None = None, action: str | None = None,
    target_type: str | None = None, target_id: str | None = None,
    result: str | None = None, limit: int = 200, offset: int = 0,
):
    """审计日志检索（F8.2 / F8.7，AUD-07：按时间/人员/类型检索）。"""
    q = AuditQuery(
        from_ts=from_ts, to_ts=to_ts, operator=operator, action=action,
        target_type=target_type, target_id=target_id, result=result,
        limit=max(1, min(int(limit), 1000)), offset=max(0, int(offset)),
    )
    records = audit.query(db_path, q)
    return env.ok({"total": len(records), "records": [r.to_dict() for r in records]})
```

**⚠️ `total` 的语义要写清楚**：这里是**本页条数**，不是全库总数。
`audit.query()` 的 `LIMIT` 直接作用于 SQL，拿不到真实总数。
要么改 `audit.query` 加一次 `COUNT(*)`，要么把字段名改成 `returned`。

**本卡裁决**：字段名用 `returned`（本页条数）+ 额外给 `has_more`
（`len(records) == limit` 即可能还有）。理由：**不为了一个好听的字段名
去改 T1-04 的既有 API**；而且 `limit` 语义下 `total` 本就是错的，
叫 `returned` 是**诚实的命名**。若后续需要真实总数，另开卡在 `audit.py`
加 `count_query(db_path, q)`。

**⚠️ 上限必须是硬编码的**：`limit` 不设上限等于给了一个"把整库拉进内存"
的接口。1000 是本卡定的天花板。

### 2.3 A 档：审计报告导出（AUD-06）

```python
@router.post("/audit/export")
def export_audit(payload: dict[str, Any] = Body(default={})):
    """生成审计报告（F8.7，AUD-06：报告含完整性校验结论）。

    ⚠️ **返回 JSON，不落文件**。理由见下方裁决。
    """
    report = audit.build_report(
        db_path,
        from_ts=payload.get("from_ts"),
        to_ts=payload.get("to_ts"),
    )
    return env.ok(report, "审计报告已生成")
```

**关键裁决：为什么不写文件？**

SAD §11.5 说"提供 `POST /audit/export` 生成可提交保密检查的审计报告"。
"可提交"暗示一份**文件**。但本卡判定**返回结构化 JSON**，理由三条：

1. **落盘位置无处可放**。`filestore.PLAINTEXT_AREAS = {"export"}` 只有
   `export/` 是明文区，而它是**按会议**组织的
   （`data/store/{meeting_id}/export/`）。审计报告不属于任何会议。
   硬塞进某个会议目录会让"审计报告在哪"这个问题没法回答。
2. **`export/` 有一条别处没有的红线**（见 `export.py` 模块文档）：
   它是 data 目录里唯一不加密的地方，**绝不允许**把非最终交付物放进去。
   审计报告是敏感的（含全部操作记录），放明文区是**违规**。
3. **前端要的是字段，不是文件**。保密检查要的是"完整性校验结论"，
   那是个字段（`integrity.result`）。给 JSON 前端可以自己渲染成任何格式；
   给文件反而逼前端去解析。

**那"可提交的报告"怎么办？** —— JSON 里已含全部要素，
Electron 侧导出成用户指定路径的文件是**前端的事**（用户本来就该选
存到哪里）。服务端落一份不知道放哪、不该放明文、还可能被遗忘删掉的
副本，是负资产。

**⚠️ 完整性失败时必须把 `action_required` 显眼带出**：
`build_report` 在 `chain.ok == False` 时会塞一句
"立即停止使用本系统、封存设备，上报保密机构"。
端点**必须原样透传这个字段**，且 `message` 也要改口径 ——
这时回"审计报告已生成"是**误导**。

```python
    if report["integrity"]["result"] != "pass":
        return env.ok(report, "审计链完整性校验未通过，请立即按报告中的处置要求执行")
    return env.ok(report, "审计报告已生成")
```

### 2.4 B 档：术语库（7 个端点）

**服务构造**：现有 `routes.py` 的 `_glossary_service()` 若未注入 `audit`，
写操作会打 warning 且**不留痕** —— 而 `glossary_change` 是
`MINIMUM_CHECK_ITEM_ACTIONS` 里"术语库/模板变更"这一类的唯一动作。
**不留痕 = AUD-08 缺项**。构造时必须带 `AuditLogger(db_path)` 与 `operator`。

```python
def _glossary(operator: str = "system"):
    from mmwf.app.services.glossary import make_glossary_service
    return make_glossary_service(cfg, db_path=db_path, audit=AuditLogger(db_path),
                                 operator=operator)
```

**⚠️ `entry_id` 生成规则必须先定死**：`GlossaryRepository.upsert()` 说
自己是 upsert，但 `GlossaryEntry.entry_id` 是主键、且表上有
`UNIQUE (category, canonical)`。两套唯一性并存意味着：
**同一个 `(category, canonical)` 带不同 `entry_id` 进来会撞 UNIQUE 约束**。

裁决：`POST /glossary` 若未给 `entry_id`，由服务端**确定性生成**
`f"{category}:{canonical}"`（不随机）。理由：
- 确定性 → 重复 POST 同一条术语自然幂等（正是 upsert 的语义），
  而随机 id 会制造出"同一术语两条记录、其中一条更新另一条"的脏数据；
- 可读 → 审计里 `target_id` 直接能看懂。

`PUT /glossary/{entry_id}` 的 `entry_id` **以路径为准**，body 里的
`entry_id` 忽略（避免"路径说 A、body 说 B"的歧义）。

**`POST /glossary/import`**：`GlossaryService.import_file(path)` 收的是
**文件路径**。本卡裁决走 **JSON body 传 CSV 文本**而不是 multipart 上传：

```python
@router.post("/glossary/import")
def import_glossary(payload: dict[str, Any] = Body(...)):
    """批量导入术语（F7.1）。body: {"csv_text": "...", "filename": "x.csv"}
    或 {"path": "D:/x.csv"}（本机路径，前端已读好文件时用）。
    """
```

理由：Electron 是**本机程序**，文件已经在本地磁盘上，让前端把
整份 CSV 塞进 multipart 再传到本机另一个端口，是纯粹的无谓拷贝；
而且 multipart 会引入 `python-multipart` 依赖（`check_deps` 不管，
但每多一个依赖就多一份离线打包与保密审查的负担）。

**两条路都要支持**，因为前端两种场景都会遇到：
- `path`：用户用系统文件对话框选了本机文件 → 直接给路径；
- `csv_text`：文件内容已在内存（比如从剪贴板粘贴）→ 直接给内容。

`csv_text` 走 `tempfile` 落一个**受控临时文件**再交给 `import_file`
（因为 `import_csv` 收的是路径），用完**立即删除**（finally）。
**⚠️ 临时文件不能放系统 `/tmp`** —— 术语库可能含单位专有名词，
这与 `filestore.plaintext()` 的既有约定一致，落 `data_dir/.tmp`。

**`GET /glossary/export`**：同理，**返回 CSV 文本**而不是写文件到
未知位置。`export_file(path)` 也收路径，落临时文件 → 读回 → 删。

**响应里必须带 `warnings`**：`import_csv` 返回的 `ImportReport`
有 `problems` 字段（格式问题清单）。**导入"成功"但有 3 行被跳过**
是最容易被忽略的情况 —— 只报 `created: 7` 而不报 `problems: 3`，
用户会以为全导进去了。`ImportReport.to_dict()` 已含 `problems`，
端点必须**原样带出**。

## 4. 常见坑

### 坑 1：`/system/fonts` 不要假装有会议

`ExportService` 是按会议构造的（要 `FileStore`）。为了查字体造一个假
会议，会把系统级端点焊到会议生命周期上 —— 用户还没建会议时这个端点
就废了。**直接走 `font_check.check_fonts()`**（`policy` 用默认值，
`font_policy` **不在** `Settings` 里 —— 别去读 `cfg.docx.font_policy`，
那个属性不存在）。

### 坑 2：`check_layers.py` 的文本黑名单会咬人

`API_LAYER_PATTERNS` 扫 API 层**源码文本**里的字面量 `0.0.0.0`
和 `http://localhost`。在 docstring / 注释里写这两个串（哪怕是在解释
"我们不用它们"）**一样会被判违规**。T1-13 已经踩过一次。
本卡的 `/system/fonts` 与审计端点**不涉及地址**，但写注释时别顺手举反例。

### 坑 3：`AuditQuery` 是 dataclass，字段是**类属性默认值**

`AuditQuery` 的字段写成类级默认值（`from_ts: str | None = None`），
不是 `@dataclass(frozen=True)` 的部分字段。构造时**只用关键字**
（`AuditQuery(operator="x")`），位置参数会静默错位。

### 坑 4：`limit` 与 `offset` 的边界

`audit.query` 里 `limit=None` 会走 `elif q.offset:` 分支 → `LIMIT -1`。
而端点若把 `limit=0` 传进去（`min(int(limit),1000)` 得 0），
SQL 的 `LIMIT 0` 返回空 → `has_more` 计算也失效。
**`limit` 必须夹到 `>= 1`**。

### 坑 5：术语库临时文件不能进系统 `/tmp`

术语库含单位专有名词。落 `data_dir/.tmp`，`finally` 里删。
与 `filestore.plaintext()` 的既有约定一致（那里的注释解释了为什么）。

### 坑 6：`entry_id` 的确定性生成**必须与表约束对齐**

表上有 `UNIQUE (category, canonical)`，而 `entry_id` 是主键。
若随机生成 id、用户重复 POST 同一条，会**撞 UNIQUE 抛 IntegrityError**
（而不是优雅 upsert）。确定性 id（`f"{category}:{canonical}"`）
让重复 POST 自然幂等。

⚠️ 但 `canonical` 可能含 `:`（如"关于：XX 事项"）→ 拼出的 id 有歧义。
**不解析 id 反推 category/canonical**（永远从库里查），
id 只当不透明主键用。若可读性有要求，用 `_clip` 截断 + 哈希后缀。

### 坑 7：`ImportReport.problems` 里的内容**不能进审计 detail**

`audit.check_detail_safety()` 会拒绝某些键名（天然装正文的词）。
导入的问题清单里可能含术语原文，写审计时必须只写**条数**
（`len(report.problems)`，`GlossaryService._log_change` 已经是这么做的），
不要把清单本身塞进 `detail`。

### 坑 8：pytest 的判定方式（本机特有）

WorkBuddy 的 `sitecustomize.py` 批量删除守卫会在 atexit 抛
`SystemExit: 1`，**吞掉最后的 `N passed` 行**。
必须用 `--junit-xml=<path>` 落文件再解析。前台跑会被 SIGTERM，
用 `run_in_background=true`。**不要用 `--basetemp=C:/tmp/...`**。

### ★ 实施阶段抓到的四个真缺陷（本卡新增，全部已在代码里修掉）

这四条**都不是**施工时预想到的，是写完代码、跑验收脚本时才暴露出来的。
它们有一个共同特征：**HTTP 状态码是对的（200）、信封形状是对的，
所以只看"跑通了没"的测试全绿**——错误藏在字段名、异常类型、
以及"同一类错误走了两条不同分支"里。记下来是因为下一次极可能再犯。

### 坑 9：`build_check_result_json` **没有** `precheck_available` 键

它给的是 `available`（`font_check.py:359`：
`{"available": report.precheck_available, ...}`）。

后果：裁决 D8（"`UNKNOWN` 必须与 `MISSING` 区分"）**在响应里落空** ——
前端只看到 `all_installed=false` + `missing=[5 个字体]`，
根本无从分辨"真缺"与"查不了（无权限/非 Windows）"。
而这个区别是**会让人白装半天字体**的。

更隐蔽的是：写代码时我照着**端点 docstring 的原文**
（"`build_check_result_json` 已带 `precheck_available`，原样透传"）
就信了，没去核对被调函数的返回值 —— **docstring 说了谎，
而我相信了它**。

**修法（两层，缺一不可）**：
1. 补 `payload["precheck_available"]`（保留 `available` 不动，它是 T1-09
   的既有拼法，对外已有消费者）；
2. 探测不可用时**把 `detail` 里的 status 全降级为 `unknown`、
   清空 `missing`、`all_installed=False`** —— 光加个 flag 让前端自己判断
   是不够的：任何直接读 `missing` 的消费方（含将来的验收脚本、
   第三方集成）都会得出错误结论。**字段内容本身就不该说谎。**

### 坑 10：`GlossaryFormatError` 不是 `MmwfError` 子类

`@app.exception_handler(MmwfError)` **兜不住**它，它会掉进
`@app.exception_handler(Exception)` 那个兜底分支 →
响应仍是 `200 + 信封`，但**错误码是 E9001（内部错误）**。

用户输错一个类别，看到的却是"程序遇到一个未预期的问题，
请把界面上的编号告诉技术人员"。危害有两层：
① 用户被误导（他只要把类别改成「单位/人名/术语/代号」就好了）；
② **E9001 这个信号被污染** —— SAD §9.3 要求 E9 只用于真正的未预期故障，
将来真出内部错误时，运维会在噪音里翻找。

**修法**：在路由层显式 `except GlossaryFormatError` → 翻成 E1001。
这个类名要**显式 import**（不能靠兜底），并在注释里写明为什么。

### 坑 11：★ 同一类异常，抛在 `try` 内 vs `try` 外，错误码完全不同

这是本卡**最难靠阅读发现**的一条。

`_build_entry` 里 `parse_aliases()` 与 `GlossaryEntry(...)` 构造
**抛的是同一个异常类**（`GlossaryFormatError`）。第一版把
`parse_aliases()` 写在 `try` **外面**、只把构造包进去，于是：

```
POST /glossary {"category":"bad"}          → E1001 ✅（构造在 try 内）
POST /glossary {"aliases": 12345}          → E9001 ❌（parse_aliases 在 try 外）
```

两个分支**代码看起来一模一样**，报出来的码却不同。
验收脚本一红才发现。

**修法**：把"所有可能抛 `GlossaryFormatError` 的调用"都放进同一个 `try`。
写 `try` 块的**判据是"哪些调用会抛这个异常"**，
而不是"哪一行看起来像在'构造对象'"。

### 坑 12：`parse_aliases()` 对非字符串/非序列输入会**静默出错**

原实现只有 `isinstance(raw, str)` 一个判断，然后直接 `for a in raw:`：

| 输入 | 原行为 | 危害 |
|---|---|---|
| `12345` | `TypeError: 'int' object is not iterable` | 冒到路由层 → **E9001**（输入问题被报成系统故障） |
| `{'a': 1}` | **静默返回 `('a',)`** | 遍历 dict 拿到的是**键** → 垃圾别名悄悄入库 |

第二种更危险：它**不报错**。而本函数 docstring 里恰好写了要防
"垃圾静默入库"（原本只防了 JSON 对象那条路，dict **对象本身**
从另一个门进来了）。

**修法**：类型**白名单**（`str` / `list` / `tuple` / `set` / `frozenset`），
白名单外一律 `GlossaryFormatError`。用白名单而不是
"黑名单排除 int/float/dict" —— **黑名单永远漏**。

### 坑 13：验收脚本自身的三个断言陷阱（写本脚本时踩的）

| 陷阱 | 现象 | 正解 |
|---|---|---|
| 假设 `data.report` | 端点**平铺**返回报告（`data` 就是报告），断言全红、误以为端点坏了 | 先读端点确认形状；平铺是对的，多套一层反而破坏 `data` 语义一致性 |
| `meeting_create` 当作审计动作 | `AuditLogger.log()` 抛 `AuditError`（未登记动作），脚本崩 | 动作名必须取自 `infra/audit.ACTIONS`；脚本用 `export`/`import_text` |
| 统计"新增文件"时把 WAL 算进去 | `mmwf.db-wal` / `mmwf.db-shm` 被当成端点落的文件，断言永远为假 | 排除 SQLite 边车（`.db-wal` / `.db-shm`）与业务无关 |
| 断言"文案里没有『缺』字" | 正确文案是"**不可作为『字体缺失』的依据**"，含『缺』但在**否定**它 | 判据换成"**没有点名任何具体字体**" |

**教训**：验收脚本和产品代码要**同等对待**。
断言比实现更严 = 断言写错了，不是实现有问题 —— 但反过来说，
**四条里有一条（`meeting_create`）确实帮我发现了产品的动作登记约束**，
所以宁可写严、再去核对，也不要写松了什么都不查。

## 5. 边界与设计裁决汇总

| # | 裁决 | 依据 |
|:---|:---|:---|
| D1 | `PUT`/`DELETE /glossary/{entry_id}` 走路径参数，不走 body | DELETE 带 body 会被客户端/网关丢弃 |
| D2 | `/audit/export` 返回 JSON，不落文件 | `export/` 是明文区且按会议组织，审计报告两者都不满足 |
| D3 | 审计检索字段名用 `returned` 而非 `total` | `total` 在本页语义下是错的命名；不为改名去动 T1-04 |
| D4 | `/glossary/import` 支持 `path` 与 `csv_text` 两条路，不用 multipart | 本机程序无需二次拷贝；少一个依赖 |
| D5 | `entry_id` 确定性生成 `f"{category}:{canonical}"` | 与表 UNIQUE 约束对齐，重复 POST 自然幂等 |
| D6 | `/system/fonts` 直连 `check_fonts()`，不构造 ExportService | 系统级端点不该耦合会议生命周期 |
| D7 | `limit` 天花板 1000，下限 1 | 无上限 = 把整库拉进内存的接口 |
| D8 | `UNKNOWN` 与 `MISSING` 必须可区分 | 混淆会让用户去装本来就装着的字体 |
