## 0. 阅读指引

本文档是**施工基线**。凡本文档已明确的技术决策（技术栈、版本号、目录结构、接口签名、错误码、状态机流转），施工阶段**不得擅自变更**。确需变更时，须走「附录 D 变更控制流程」，并在本文档修订记录中登记。

阅读顺序建议：

1. 先读 §1（需求澄清）与 §2（架构选型），理解"为什么这么设计"。
2. 再读 §3—§8，建立整体结构认知。
3. 施工时以 §9（数据模型）、§10（接口契约）、§11（核心算法）为逐条对照依据。
4. `02-开发施工文档` 提供可直接照做的任务卡，是日常使用频率最高的文档。

## 1. 需求澄清（Phase 1 产出）

按方法论要求，先锁定 6 个必答问题。下列答案**基于 PRD 已明确的内容反推得出**，无需再向需求方额外确认；标注"⚠️ 需确认"的两项为本文档的合理推断，已在上游 PRD 交底会中作为待确认项列出。

| # | 必答问题 | 结论 | 依据 |
|:---|:---|:---|:---|
| 01 | **产品形态** | **本地桌面图形应用 + 本地后台服务**（同一安装包内），非 Web、非 SaaS、非 CLI 工具 | PRD §2.3「不做在线/云端服务」；§4.6 F6.7「提供简单的本地界面…不要求使用者接触命令行」；N3.1 |
| 02 | **运行环境** | **纯本地 / 涉密内网单机运行，全程离线**。一期单机部署；二期如一个科室 3—5 人共享，在同一台内网服务器上以"本机回环 + 强制鉴权"方式提供 | PRD §1.4；N4.2；N1.4；§8.2 |
| 03 | **项目规模** | **完整产品，但分两期交付**。一期 = 流水线打通与版式落地（可独立交付使用）；二期 = 纪要生成引擎与人工闸口 | PRD §8.1、§8.2、§8.3 |
| 04 | **数据方案** | **本机 SQLite（业务元数据与结构化数据）+ 本机文件系统（音频、中间产物、导出文件），敏感数据静态加密**。无云存储、无外部数据库 | PRD §6「结构化数据与渲染文本分离存储」；N4.1；N4.4；F8.4 |
| 05 | **前后端分工** | **前后端分离（同一进程内的本地分离）**：Python 后台服务（FastAPI）负责全部业务与模型调用；桌面壳（Electron）承载界面向本地服务发起 HTTP 请求。**不采用单体全栈模板渲染** | F6.7；N3.1；§7「界面：本地图形界面」 |
| 06 | **扩展预期** | **必须可扩展**：① 识别引擎、本地大模型、导出器均为可替换适配器；② 纪要模板库、术语库可外部增删而无需改代码；③ 二期在既有状态机上追加节点而非重构 | N5.2；PRD §7「架构原则」；§4.3 F3.11 |

### 1.1 六问之外的两个关键推断（⚠️ 需确认）

| 项 | 本文档推断 | 说明 |
|:---|:---|:---|
| A | 一期 UI 采用 **Electron + 原生 HTML/CSS/JS**，不引入 React/Vue 等前端框架 | 界面只有"投递 / 确认 / 导出"三类操作（F6.7），页面数预计 ≤ 12 个，引框架属过度设计。若后期界面复杂度显著上升，再引入框架并重构前端层，后台接口不变 |
| B | 服务鉴权采用 **本机回环 + 一次性启动令牌（token）**，一期不做多用户账号体系，但**预留账号表与权限字段** | 一期为单机单人（N1.4），做完整账号体系是浪费；但保密要求（F8.3）需按"操作人"留痕，故审计日志必须记录操作人，二期接账号表即可 |

## 2. 架构选型（Phase 2 产出）

### 2.1 三个候选方案对比

| 维度 | 方案 A：单体桌面应用（Electron 内嵌 Python 子进程，无独立服务层） | 方案 B：本地服务分离 + 显式状态机编排（**推荐**） | 方案 C：低代码工作流平台（Dify 类）+ 本地模型 | 
|:---|:---|:---|:---|
| 架构模式 | 单体全栈，UI 层直接调用 Python 函数（IPC） | 分层架构（表现层 / 应用编排层 / 领域层 / 适配层 / 基础设施层）+ 显式状态机 | 可视化工作流 + 自定义节点 |
| 技术栈 | Electron + Python（child_process RPC）+ SQLite | Electron + FastAPI(本地回环) + LangGraph 状态机 + SQLite + 适配器层 | Dify（自托管）+ Ollama + FunASR 微服务 |
| 开发速度 | ⭐⭐⭐⭐（前期快） | ⭐⭐⭐（前期慢，后期快） | ⭐⭐⭐⭐⭐（搭积木最快） |
| 可维护性 | ⭐⭐（UI 与业务强耦合） | ⭐⭐⭐⭐⭐（层间契约清晰、模块可独立测试） | ⭐⭐（业务逻辑沉在平台配置里，无法版本化、无法单测） |
| 扩展性 | ⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐（受平台节点能力限制） |
| 离线可控性 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐（Dify 本体依赖较重重，含较多联网校验组件，与 N4.4 冲突） |
| 与 PRD 契合度 | 中 | **高** | 低 |
| 适用场景 | 原型验证、单人小工具 | **本项目：长期维护、需过保密检查、需审计追溯** | 快速验证想法 |

### 2.2 推荐方案：B（本地服务分离 + 显式状态机编排）

**推荐理由：**

1. **人工闸口必须落在编排层，而不是提示词层。** PRD §4.4 设计要点明确要求"闸口机制必须实现在编排层而非提示词层"，且"中断时序列化完整状态、恢复时重建状态"。方案 C 的低代码平台虽有"人工审批节点"，但其状态是不可编程、不可单测的黑盒，无法满足 F6.3「须区分有检查点与精确恢复，副作用节点必须设计幂等键」这一级控制粒度。方案 B 用 LangGraph 的显式状态机 + 持久化检查点，把中断点、分支、重试、幂等键全部变成可测试的一等公民。

2. **合规审计要求业务逻辑可版本化、可追溯。** F8.2/F8.8 要求操作日志完整、中间版本留存。方案 C 的业务定义躺在平台数据库的 JSON 里，既不能 git diff，也不能单元测试；方案 B 的业务逻辑是源码，可评审、可回滚、可写测试。

3. **离线可控性。** N4.4 要求"不使用需联网校验的组件"。Dify 本体依赖较重且历史上存在首次运行联网校验行为，会给保密检测带来额外说明成本。方案 B 的全部组件（FastAPI、LangGraph、FunASR、python-docx、SQLite、Ollama）均为纯离线可运行且许可宽松。

**为什么不选方案 A（单体）：** 痛点在"四个断点"，本质是流程编排问题。若 UI 层直接同步调用 Python 函数，那么"跑到一半停下来等人确认"这件事在代码里就没有落脚点——只能靠阻塞式等待或把状态塞进 UI state，前者浪费资源，后者无法断点续跑。方案 A 在一期看似够用，到二期实现 G2/G3 闸口时必然重构，属于把技术债前置。

**为什么不选方案 C（低代码）：** 见上述理由 1、2、3。方案 C 唯一优势是搭建快，但其"快"只体现在 Demo 阶段；本项目一期就要过保密检测、二期要做质量影子验收，后期维护成本远高于省下的那点搭建时间。这与 PRD §7 注明的"不应盲目引入通用数据编排引擎…属于过度设计"（本处指数据工程型引擎）以及调研 §2.4 的结论一致。

### 2.3 架构模式定级

采用 **DDD 轻量版 + 分层架构**：

- **不是完整 DDD**：本项目领域规则集中在"纪要生成引擎"一处，其余为用户流程编排，不存在大量聚合根与领域事件。做完整 DDD（聚合、值对象、领域事件、仓储模式全套）属过度设计。
- **是 DDD 轻量版**：① 领域层与适配层严格分离（识别引擎、大模型、导出器都是可替换接口）；② 核心业务规则（结构抽取、粒度控制、溯源绑定、版式映射）集中在领域层且不依赖任何框架；③ 其余部分采用朴素的"应用服务 + 数据访问对象"模式。
- **分层边界强制**：领域层不得 import 任何 FastAPI / SQLite / 网络库。此约束由 §14「反模式与强制约束」中的静态检查脚本兜底。

### 3.2 五大能力环节 → 模块映射（回答"哪一环自研"）

## 4. 模块划分与职责

采用「包 = 模块」的强映射，共 12 个业务模块，分属四层。每个模块职责单一、对外只暴露一个 `__init__.py` 中的门面对象。

| 编号 | 模块 | 所属层 | 职责（一句话） | 明确不做 |
|:---|:---|:---|:---|:---|
| M01 | `presentation` | 表现层 | Electron 界面与本地服务通信 | 不含任何业务规则 |
| M02 | `api` | 应用层 | FastAPI 路由、请求校验、令牌鉴权 | 不写业务逻辑，只做参数转换 |
| M03 | `graph` | 应用层 | LangGraph 状态机定义、闸口中断、断点续跑 | 不含领域规则 |
| M04 | `checkpoint` | 应用层 | 检查点持久化、状态序列化与重建 | 不判断业务合法性 |
| M05 | `audit` | 应用层 | 审计日志写入、检索、导出 | 日志不可被普通使用者改写 |
| M06 | `ingest` | 应用层 | 音频接入、格式校验、时长探测、切分 | 不做识别 |
| M07 | `review` | 应用层 | 低置信分流、逐段校对、记录稿生成 | 不做纪要生成 |
| M08 | `extraction` | 领域层 | 分块分层、结构化抽取、模式约束 | 不做版式 |
| M09 | `minutes` | 领域层 | 公文结构模板、语体对齐、粒度控制、结构→Markdown | 不做 docx |
| M10 | `grounding` | 领域层 | 结论→来源片段绑定、溯源可跳转 | 不做 UI 跳转实现 |
| M11 | `docx` | 领域层 | 版式映射规则、样式补丁、编号、字体预检 | 不实现完整格式转换 |
| M12 | `glossary` | 领域层 | 术语库存储、匹配、热词导出 | 不做识别调用 |

**依赖方向（强制单向）**：

```
presentation ──HTTP──► api ──► graph ──► {ingest, review, extraction, minutes, docx, grounding, glossary}
                                                                          │
                                                                          ▼
                                                              {checkpoint, audit, adapters, infra}
```

**禁止**：领域层（M08–M12）import `fastapi`、`sqlite3`、`httpx`、`torch`、`funasr`、`ollama`。领域层只依赖标准库与纯算法依赖（如 `python-docx` 仅允许出现在 M11，且须经 `DocxWriter` 抽象隔离）。

```
              │     ┌────────▼─────────┐
              │     │ archived         │  归档 + 审计报告
              │     └────────┬─────────┘
              │              │
              │     ┌────────▼─────────┐
              └────►│     failed       │  终态（可人工重跑）
                    └──────────────────┘
```

### 5.2 状态定义表

| 状态 | 中文界面名 | 是否终态 | 是否闸口 | 可重入 |
|:---|:---|:---|:---|:---|
| `created` | 已接收 | 否 | 否 | 是 |
| `ingest_pending` | 正在检查音频 | 否 | 否 | 是 |
| `transcribing` | 正在转写 | 否 | 否 | 是 |
| `transcript_ready` | 转写完成 | 否 | 否 | 是 |
| `reviewing` | 待复核 | 否 | 否 | 是 |
| `record_ready` | 记录稿已生成 | 否 | 否 | 是 |
| `extracting` | 正在梳理议题 | 否 | 否 | 是 |
| `G2_awaiting` | **待确认议题** | 否 | **是** | 是 |
| `generating` | 正在起草纪要 | 否 | 否 | 是 |
| `validating` | 正在自检 | 否 | 否 | 是 |
| `assembling` | 正在成文 | 否 | 否 | 是 |
| `G3_awaiting` | **待审定纪要** | 否 | **是** | 是 |
| `exporting` | 正在导出 | 否 | 否 | 是 |
| `archived` | 已完成 | **是** | 否 | 否 |
| `failed` | 处理失败 | **是** | 否 | 是（人工重跑） |

### 5.3 闸口中断与恢复契约

```python
# app/graph/interrupts.py
from dataclasses import dataclass
from typing import Literal

Decision = Literal["approve", "reject", "edit"]

@dataclass(frozen=True)
class InterruptPoint:
    node_id: str            # "G2" / "G3"
    checkpoint_id: str      # 检查点主键，恢复时凭此重建
    payload: dict           # 送审内容（议题数组 / 纪要草稿）
    risk: str               # "high" / "medium"
    evidence: list[dict]     # 每条结论的来源片段与时间戳

@dataclass(frozen=True)
class ResumeDecision:
    decision: Decision
    edited_payload: dict | None   # decision == "edit" 时必填
    operator: str
    comment: str | None = None
```

**恢复语义（必须区分三种情况）**：

| 决策 | 语义 | 状态迁移 | 是否重跑已完成节点 |
|:---|:---|:---|:---|
| `approve` | 读取检查点状态，原样继续 | G2 → generating | **否** |
| `reject` | 清除当前节点产物，状态置"已驳回"，退回上游重规划节点 | G2 → extracting | 仅重跑被驳回节点 |
| `edit` | 用修改后的 payload 注入状态，重新进入下游 | G2 → generating（携带 edited_payload） | **否**（这是降返工的关键） |

> **`reject` 与 `edit` 的界面对照**（N3.3）：`reject` 按钮文案为「**退回重做**」，`edit` 按钮文案为「**改完继续**」——必须让使用者直观感知"改完继续"不用整篇重来。

### 5.4 幂等键设计

凡产生**副作用**的节点（导出文件、写归档、发通知、写审计）必须携带幂等键。键的构造规则：

```python
# 幂等键 = sha256(f"{task_id}:{node_id}:{node_input_hash}")[:32]
# node_input_hash 为该节点输入的关键字段规范化 JSON 的哈希
def make_idempotency_key(task_id: str, node_id: str, node_input: dict) -> str:
    payload = json.dumps(node_input, sort_keys=True, ensure_ascii=False, separators=(",", ":"))
    raw = f"{task_id}:{node_id}:{hashlib.sha256(payload.encode()).hexdigest()}"
    return hashlib.sha256(raw.encode()).hexdigest()[:32]
```

| 节点 | 幂等键构成 | 防重效果 |
|:---|:---|:---|
| `exporting` | `task_id:exporting:纪要内容哈希` | 同一份内容重复导出不会产生两份文件，返回已存在文件路径 |
| `archive` | `task_id:archive:最终产物哈希` | 重复归档不产生重复条目 |
| `notifier` | `task_id:notify:接收方` | 同任务不重复通知 |

幂等键写入 `idempotency_record` 表（见 §9.4），唯一约束，冲突时返回既有结果而非报错。

## 6. 分层设计约定

### 6.1 各层输入输出契约

| 层 | 输入 | 输出 | 禁止 |
|:---|:---|:---|:---|
| 表现层 | 用户操作事件 | HTTP 请求 | 直接读文件、直接调模型 |
| 应用层 `api` | HTTP 请求（已鉴权） | HTTP 响应（统一信封） | 直接写 SQL、直接调适配器 |
| 应用层 `graph` | 任务状态 + 决策 | 新任务状态 | 硬编码领域规则 |
| 领域层 | 纯数据结构（dataclass/dict） | 纯数据结构 | I/O、框架 import、网络 |
| 适配层 | 领域层定义的请求对象 | 领域层定义的响应对象 | 反向依赖上层 |
| 基础设施层 | 通用读写请求 | 通用读写结果 | 包含业务判断 |

### 6.2 跨层数据传递

跨层一律使用 **不可变 dataclass**（`@dataclass(frozen=True)`），不使用裸 dict 跨层传递。理由：中文字段名容易拼错且 IDE 无法校验，dataclass 提供类型检查与自动补全。

**例外**：`payload` / `edited_payload` 这类需要直接序列化给 LLM 或前端的内容允许使用 dict，但必须经 `pydantic` 模型校验后才能进入领域层。

### 6.3 统一响应信封

```python
# api/envelope.py
@dataclass
class ApiResponse:
    ok: bool
    code: str                  # 业务错误码，见 §12
    message: str               # 面向使用者的中文提示（N3.3）
    data: Any | None = None
    trace_id: str | None = None
```

所有 HTTP 响应（含 4xx/5xx）均返回 200 状态码 + 信封体内的 `ok/code`。理由：Electron 前端只需处理一种响应形态；HTTP 状态码仅用于表达"服务不可达"这类传输层故障。

## 10. 核心算法设计

### 10.1 分块分层抽取（环节③的一半）

```
输入：转写稿全文（可能上万字）
输出：结构化议题/决议候选

Step 1  分块：按语义边界（说话人切换、话题转折词、长静音）切块
        目标 1000—2000 字，块间重叠 200 字（PRD F3.2 / 调研 §4.3）

Step 2  逐块抽取（可并行）：每块固定抽取 6 个维度
        发言人 / 议题 / 结论性意见 / 议定事项(含责任人、时限) / 待办事项 / 需领导决策事项

Step 3  块间归并：
        - 议题按语义相似度聚类（同一议题跨块合并）
        - 重复议定事项去重（同一事项在多块出现时合并并合并 source_refs）
        - 处理重叠区：同一文本在相邻块都被抽到时，保留信息量更大的一条

Step 4  全局补全：
        - 检查模板要求的必填要素是否齐备，缺失项显式标记为"待补充"
        - 不编造缺失内容（红旗项：无依据编造）
```

**块间归并的相似度阈值**：`0.82`（余弦，基于本地 embedding 或字符 n-gram Jaccard）。低于阈值视为不同议题；高于阈值合并。该阈值写入 `config/extraction.yaml` 可调（N5.2）。

**为什么不用"整篇喂给模型"**：调研数据——简单分块在 68% 的复杂文档上无法保持上下文关系；非接地实现幻觉率 27%。超长上下文窗口不解决"中间遗忘"。此项为**强制约束**，写进 §14。

### 10.2 模式约束输出（环节③的另一半）

```python
# domain/extraction/schemas.py
from pydantic import BaseModel, Field
from typing import Literal

class ResolutionSchema(BaseModel):
    content: str = Field(..., min_length=1, description="议定事项内容")
    owner: str = Field(default="暂无", description="责任人；确无责任人时必须填『暂无』")
    deadline: str | None = Field(default=None, description="时限，无则 null")
    source_quote: str = Field(..., description="原文片段，须逐字摘自转写稿")
    source_start_ms: int
    source_end_ms: int

class TopicSchema(BaseModel):
    name: str = Field(..., max_length=30)
    discussion: str
    readings: list[str] = Field(default_factory=list)  # 公文语体标签
    resolutions: list[ResolutionSchema] = Field(default_factory=list)
    action_items: list[ActionItemSchema] = Field(default_factory=list)
    pending_decisions: list[PendingDecisionSchema] = Field(default_factory=list)

class MinutesSchema(BaseModel):
    title: str
    meeting_time: str
    location: str
    host: str
    attendees: list[str]
    recorder: str
    topics: list[TopicSchema]
    schema_version: Literal["1.0"] = "1.0"
```

**约束实现**：Ollama 侧使用 `format` 参数传入 JSON Schema（本地方案中这是唯一能保证结构合规又完全离线的路径）。生成后**必须**再过 `MinutesSchema.model_validate()` 校验层——因为约束解码保证模式合规，**不保证业务逻辑正确**（PRD F3.4 明确要求校验层）。

**校验不通过的处理**：不是简单重试，而是把 pydantic 的报错信息回注给模型，最多重试 2 次；仍失败则落到 `validating` 状态并输出问题清单送人工（不静默降级）。

### 10.3 溯源绑定（Grounding）

每条结论必须挂载 `source_refs`，其构造过程：

```python
def bind_grounding(claim: str, segments: list[Segment]) -> list[SourceRef]:
    """
    1. 用 source_quote 在转写稿中做精确匹配（容忍标点差异）
    2. 精确匹配失败时退化为模糊匹配（滑动窗口 + 编辑距离），
       但模糊匹配命中的 confidence 必须降级并在界面标注
    3. 完全匹配不到 → 该结论标记 ungrounded，禁止进入最终定稿
    """
```

**硬规则**：`ungrounded` 的结论**不得出现在最终纪要中**。这是 V4（溯源性）与红线项 4 的技术保障。校验器 `Validator.check_grounding()` 在 `validating` 状态强制执行。

### 10.4 粒度控制规则（可枚举，纯工程手段）

调研 §4.5 结论：规则后处理"确定性最强但只能处理可枚举的规则"。粒度控制恰是可枚举的：

| 规则 | 判定 | 处理 |
|:---|:---|:---|
| 责任人为空 | `owner` 字段为空或空白 | 强制填 `暂无`（**不是省略**，F3.7） |
| 一条决议含多个事项 | 单条 `content` 中出现"并""以及""同时"且长度 > 60 字 | 拆分为多条，各自继承 `source_refs` |
| 待办误判为普通陈述 | `action_item` 无明确动词或无时间词 | 降级为 `pending_decision` 或移出，并在问题清单中标注 |
| 时限模糊 | `deadline` 为"尽快""近期"等 | 保留原文但标注"时限待明确"，进问题清单 |
| 事项重复 | 两条 `content` 相似度 > 0.9 | 合并，`source_refs` 取并集 |

## 11. 安全与合规设计

### 11.1 离线保障（F8.1）

| 措施 | 实现 |
|:---|:---|
| 无外网依赖 | 全部依赖离线 wheel；模型权重离线导入；不使用任何需联网校验的组件 |
| 服务仅回环 | Uvicorn 绑定 `127.0.0.1`，端口随机；`host` 硬编码不允许配置为 `0.0.0.0`（一期） |
| 令牌鉴权 | 启动生成一次性 token 写入 `%LOCALAPPDATA%/mmwf/session.token`（权限 600），Electron 壳读取后携于请求头 |
| 网络行为自检 | `/system/selfcheck` 主动探测：枚举本进程 socket 连接、检查是否有非回环连接、统计 DNS 解析尝试次数 |
| 进程级防护 | 启动时对环境做一次扫描，若检测到代理环境变量（`HTTP_PROXY` 等）指向外网，告警并要求确认 |

### 11.2 数据加密（N4.1 / F8.4）

| 数据 | 加密方式 |
|:---|:---|
| 音频原件与片段 | AES-256-GCM，密钥由操作系统凭据管理器（Windows Credential Manager）保管 |
| 转写稿与结构化数据 | 同上 |
| 导出文件 | 明文（需交付给人），但存放目录受访问控制 |
| 数据库敏感字段 | `meeting.host/attendees`、`resolution.content` 等应用层加密 |

### 11.3 访问控制（F8.3）

一期实现"单机单会话"：

```
启动 → 检查是否已有活动会话
  ├─ 无 → 创建会话，记录 operator，启动服务
  └─ 有 → 提示"系统正由 {operator} 使用中"，拒绝第二实例
处理涉密会议期间（classification == 'state_secret'）→ 锁定登录通道
```

不允许同一设备同一时间两个账号在线。`operator` 来自启动时的操作人选择（一期为下拉+手输，不做密码），写入审计日志。

### 11.4 密级提示与拦截（F8.5）

- 投递音频时弹出确认：「本次会议内容是否已确认密级与使用授权？」——**不代替定密决策**，只做提示与留痕。
- 导出时再次确认：「本文件已按 {classification} 管理，请确认流转范围。」
- 所有提示动作写入审计日志。

### 11.5 审计链（F8.2 / F8.7 / R9）

- 日志表**只允许 INSERT**：应用层不提供 UPDATE/DELETE 接口；SQLite 层通过触发器阻止 `UPDATE`/`DELETE`。
- 链式哈希防篡改（见 §8.3）。
- 提供 `POST /audit/export` 生成可提交保密检查的审计报告（含完整性校验结果）。
- 日志保留期默认 3 年，可在配置中调整。

**实施前置**：需提前与使用单位保密工作机构对齐核查项清单（风险 R9）。本文档建议的最小核查项集：登录记录、音频导入记录、导出记录、纪要内容修改记录、闸口审批记录。

### 12.1 性能设计

| 指标 | 目标 | 设计手段 |
|:---|:---|:---|
| 2 小时音频无独显转写 | ≤ 2 小时 | 选 Paraformer-Large（220M，1—2GB 显存，无 GPU 时 i7 约 9s/92s 音频）；CPU 档位可串行分块处理，显示进度 |
| 2 小时音频有独显转写 | ≤ 30 分钟 | GPU 档位，块级并行 |
| 纪要生成 | ≤ 10 分钟 | 分块并行抽取（调研 §4.3 数据：并行可降约 63% 耗时） |
| 导出 | ≤ 10 秒 | 结构转换与样式注入均为纯本地计算 |
| 前端响应 | 交互 < 200ms | 长任务全部异步 + 轮询/SSE 进度推送 |

**进度反馈**：所有长任务必须通过 `GET /meetings/{id}` 的 `progress` 字段暴露细粒度进度（当前块序号 / 总块数 / 已耗时 / 预估剩余），避免使用者以为死机。

### 12.2 可用性设计（N3.x）

- **三步操作**：投递音频 → 确认闸口 → 导出文档。任何额外步骤都需论证。
- **术语替换表**（N3.3 强制）：

| 工程术语 | 界面文案 |
|:---|:---|
| 人工闸口 / HITL | 待确认事项 |
| 中间产物 | 文稿 |
| 检查点 / checkpoint | （不出现，内部概念） |
| 溯源 / grounding | 查看原文出处 |
| schema 校验 | 格式检查 |
| 幂等 | （不出现） |

- **内嵌指引**：每个闸口界面顶部有折叠式说明「这一步在做什么、为什么要您确认、不确认会怎样」。

### 12.3 可维护性设计（N5.x）

- **配置外置**：`config/` 下 `models.yaml`、`extraction.yaml`、`thresholds.yaml`、`glossary.csv`、`templates/*.yaml` 均可热改，无需改代码。
- **质量自检**（N5.3）：内置 ASR 质量自检，检测四类异常：
  1. 平均置信度异常偏低（< 0.85）
  2. 低置信段落占比异常偏高（> 15%）
  3. **时间戳与文本长度错位**（上游静默失效的典型症状）
  4. 热词命中率为 0（术语库非空但完全未命中 → 怀疑热词参数被忽略）
  任一触发即告警并要求人工抽样核对。这直接对应风险 R2。
- **适配器可替换**：新增识别引擎 = 实现 `AsrProvider` 协议 + 注册，不改动上层。

### 附录 C：新增识别引擎的标准步骤

1. 在 `adapters/asr/` 下新建 `<engine>.py`
2. 实现 `AsrProvider` 协议的四个方法：`available()` / `warmup()` / `transcribe(path, hotwords) -> TranscriptResult` / `health_check()`
3. 在 `adapters/asr/__init__.py` 注册
4. 在 `config/models.yaml` 中把 `asr.provider` 指向新引擎名
5. 跑 `tests/adapters/test_asr_contract.py`（对全部 provider 参数化的接口一致性测试）
6. **不得**修改上层任何代码——若需修改，说明接口抽象有缺陷，应改接口而非打补丁
