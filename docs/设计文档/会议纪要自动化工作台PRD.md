## 1. 背景与问题定义

### 1.1 现状

目标用户的高频工作是会议记录与纪要撰写，当前依赖一条手工断点式流程：

1. 用录音笔录音，并用其自带语音转文字功能生成文字稿
2. 用 AI 审核文字稿，形成「会议记录.md」
3. 调用 AI 撰写「会议纪要.md」
4. 修改通过后转为 .doc，提交领导审定

该流程在工程上等价于一条处理链路被拆成四个人工跳转点，每次跳转都需要人工复制粘贴并重建上下文。

### 1.2 痛点与根因

| 痛点 | 用户表述 | 根因诊断 | 性质 |
|---|---|---|---|
| 痛点① | 工具来回调用，比较浪费时间 | 流程未编排，数据靠人工搬运，存在 4 个断点 | 纯工程问题，可完全消除 |
| 痛点② | 纪要质量不高，重点环节需要反复 | ① 公文文书结构映射缺位，需每次手工注入；② 粒度控制失效，议定事项不逐条、待办误判 | 产品空白 + 机制缺位，需自建并配合人工闸口 |

**关键澄清**：痛点②的根因**不是**语音识别准确率。主流商用与开源方案的中文识别率已达 95%—98%，剩余误差主要影响人名、数字、机构名，会被下游模型当作事实全盘接受。真正缺失的是"从会议记录到公文式纪要"的语义转换能力，以及把人工复核从"整篇重写"降级为"逐条修正"的机制。

### 1.3 为什么不采购现成产品

调研覆盖商业产品、离线硬件、党政专用系统、开源生态四条路线，结论是：

- **商业产品**：一键出纪要已是标配，但无任何产品支持党政机关纪要文书结构，也无产品支持 GB/T 9704—2012 公文格式自动成文；公文结构必须由使用者在每次调用时手工写进提示词。
- **离线硬件设备**：解决了合规问题，但无公文版式成文能力，且无集中管理与审计能力。
- **党政专用离线系统**：产品定义贴合场景，但价格未公开、需按项目立项，且同样不解决公文版式自动成文。
- **开源生态**：链路可完整拼接，五个能力环节中四个已有成熟实现（含严格遵循公文格式的导出组件），**唯一空白的是"记录 → 纪要"环节**。

因此本项目的定位不是"从零造轮子"，而是**复用四环、自研一环、并补齐人工闸口与一条命令跑完的编排能力**。

### 1.4 合规前置约束

本项目须在以下合规前提下设计：

1. 若会议内容涉及国家秘密，使用任何联网 AI 工具均属法规明文禁止（依据《保守国家秘密法》第二十九条、第三十一条）；自建本地/内网离线系统是合规必需，不是技术偏好。
2. 密级由内容与定密程序决定，不由载体形态决定。会议若涉密，录音自形成起即为国家秘密载体，其所有派生产物继承同一密级。
3. "工作秘密"（不属于国家秘密但泄露后会造成一定不利影响的事项）同样受法定保护要求约束，**"非国家秘密"不等于"可上传公有云"**。
4. 本地部署不等于自动合规。若处理国家秘密，系统须按最高密级实施分级保护、经检查合格后使用，设备须为合规涉密设备，承接厂商须具备保密资质。
5. 私有化部署必须做访问控制与安全加固，否则风险只是从云端转移到自有机房。

**产品形态结论**：本系统必须是**纯本地/内网运行、全程离线、数据不出设备边界**的工具。

## 2. 产品定位与目标

### 2.1 一句话定位

面向党政机关行政办公人员的**离线会议纪要自动化工作台**：把录音音频文件放进去，产出一份结构合规、可溯源、可逐条校订的公文式会议纪要，并直接导出符合公文格式的 .docx。

### 2.2 产品目标

| 目标 | 衡量指标 | 目标值 |
|---|---|---|
| 消除流程摩擦 | 人工操作步数 | 从 4 次工具切换降至 1 次投递 + 2 次确认 |
| 压缩处理时长 | 单份 2 小时会议从音频到 docx | 从约 2—3 小时人工投入降至 20 分钟以内（不含精度提升） |
| 降低返工率 | 纪要成稿的返工轮次 | 从 3 轮以上降至 1 轮以内 |
| 保证合规可审计 | 数据外发行为 | 0 次（全程离线） |
| 格式一次到位 | 导出文档版式返工 | 0 次（版式由代码保证，不由模型生成） |

### 2.3 明确不做什么（范围边界）

- **不做在线/云端服务**：不提供任何联网能力，不做多租户 SaaS。
- **不替代录音笔**：音频采集仍由现有硬件完成，本系统从"已有音频文件"开始。
- **不做语音合成、不做会议视频处理**。
- **不做自动定密判断**：密级判定是使用者的法定职责，系统只做合规提示与拦截，不代替定密决策。
- **一期不做说话人分离**：多人重叠发言与远场录音下当前技术准确率不足，发言人归属错误是比错字更严重的事故，列为可选增强项。

## 3. 目标用户与使用场景

### 3.1 用户画像

| 角色 | 描述 | 核心诉求 | 技术背景 |
|---|---|---|---|
| 主要用户：文秘/办公室人员 | 承担会议记录与纪要撰写，日处理 1—3 场会议 | 少操作、快出稿、少返工 | 熟悉 Office 办公软件，不具备编程能力 |
| 次要用户：审核人/分管领导 | 审定纪要成稿 | 快速看清议定事项与责任分工，能追到原话出处 | 仅使用 Word |
| 管理角色：保密工作责任人 | 落实保密责任制、配合检查 | 操作留痕可导出、权限可控 | 不直接使用本系统 |

### 3.2 核心使用场景

**场景一：常规办公会（1 小时以内，非涉密）**
投递音频 → 系统自动转写 → 使用者复核低置信段落 → 系统生成议题与决议草稿 → 使用者逐条确认 → 导出 docx 提交。

**场景二：长时专题会（2—5 小时，含专业术语）**
投递音频 → 系统分块处理并自动注入本单位术语表（机构名、领导姓名、业务术语）→ 使用者分议题复核 → 逐条修正决议事项 → 导出。

**场景三：涉密会议（内网环境）**
全程在涉密内网设备运行，音频不上传、结果不外发，操作日志留存备查。

**场景四：历史稿改造（无音频，仅有文字稿）**
直接投递已有文字稿，跳过转写环节，从审核环节进入流程。

## 4. 功能需求

需求优先级定义：**P0** = 一期必须交付，缺则不可用；**P1** = 一期应交付，影响体验与质量；**P2** = 二期或增强项。

### 4.1 模块一：音频接入与转写（P0）

| 编号 | 需求描述 | 优先级 |
|---|---|---|
| F1.1 | 支持批量投递音频文件，支持常见格式（wav/mp3/m4a 等）；提供"投递文件夹"与"手动选择文件"两种入口 | P0 |
| F1.2 | 自动识别音频时长并给出处理预估；对超长音频自动切分处理，避免截断或失败（商用方案普遍存在 60 分钟上限，本系统须突破） | P0 |
| F1.3 | 本地语音识别，输出带标点、带时间戳的文字稿；识别引擎须支持中文会议场景优化 | P0 |
| F1.4 | **术语表注入（热词）**：支持维护本单位术语库（机构名、领导姓名与职务、业务术语、项目代号），转写时自动修正专有名词 | P0 |
| F1.5 | 输出每段的识别置信度，低置信段落自动标记待复核 | P0 |
| F1.6 | 支持手动导入已有文字稿（跳过转写，直接进入审核环节） | P0 |
| F1.7 | 音频与转写稿本地归档，支持按会议、日期检索，支持点击文字跳转对应音频位置回听 | P1 |
| F1.8 | 说话人分离（可选增强）：给出"谁在何时发言"的时间轴标记；须明确标注置信度并允许人工改判 | P2 |

**设计要点**：识别引擎的选型需遵循调研结论——中文会议场景应避开已公示停服风险的模型，优先选择支持热词注入、支持字级时间戳、生产验证充分的方案。同时须注意部分开源工具链存在"参数静默失效"缺陷（不报错但悄悄降低质量），因此**系统必须实现自动化的识别质量自检**，对异常低置信比例主动告警。

### 4.2 模块二：会议记录审核（P0）

| 编号 | 需求描述 | 优先级 |
|---|---|---|
| F2.1 | **不设全文人工校对**：默认只把低置信段落、静音异常段、多人重叠段高亮送人工，其余自动通过 | P0 |
| F2.2 | 提供逐段校对界面，支持就地编辑、标记已核对、批量接受 | P0 |
| F2.3 | 生成结构化「会议记录.md」，含元信息区（会议名称、时间、地点、主持人、参会人、记录人）与正文区 | P0 |
| F2.4 | 元信息支持从会议通知或用历史模板自动填充，允许人工修改 | P1 |
| F2.5 | 记录稿版本留存，保留每次修改的前后版本以便回溯 | P1 |

### 4.3 模块三：纪要生成引擎（P0，本项目核心）

这是唯一需要自研的核心环节，也是产品壁垒所在。

| 编号 | 需求描述 | 优先级 |
|---|---|---|
| F3.1 | **公文结构模板库**：内置党政机关常见纪要文书结构（党组会、专题会、协调会、工作例会等），每类模板定义固定要素与层级 | P0 |
| F3.2 | **分块分层处理**：对长文稿按语义分块（建议 1000—2000 字、含重叠区），先逐块结构化抽取，再合并为全局输出；**不得采用"整篇喂给模型"的方式** | P0 |
| F3.3 | **结构化抽取维度固定**：每块固定抽取【发言人/议题/结论性意见/议定事项/待办事项（含责任人、时限）/需领导决策事项】，确保各块输出维度一致 | P0 |
| F3.4 | **模式约束输出**：用模式定义（schema）约束模型输出，实现"结构由模型负责、版式由代码负责"；必须附带校验层，因模式合规不等于业务逻辑正确 | P0 |
| F3.5 | **溯源标注**：纪要每条结论挂载来源片段与时间戳，点击可跳转原文，使核验成本从"重读全文"降为"点开出处" | P0 |
| F3.6 | **公文语体对齐**：内置公文常用表述库（如"会议认为/会议指出/会议强调/会议要求"的层级递进）与禁用表述规则 | P0 |
| F3.7 | **粒度控制**：议定事项逐条罗列、责任到人、时限明确；无责任人时填"暂无"而非省略 | P0 |
| F3.8 | **输出后置校验**：自动检查必填要素完整性、数字与人名一致性、敏感表述筛查，输出问题清单 | P0 |
| F3.9 | 支持基于本单位历史纪要文件的示例对齐（少样本），提升文风贴合度 | P1 |
| F3.10 | 支持按议题拆分生成（而非全文统一总结），每个议题独立成节 | P1 |
| F3.11 | 支持纪要模板的可视化编辑与版本管理 | P2 |

**设计要点**：本模块的技术路径为"分块分层 + 结构化抽取 + 模式约束 + 接地溯源"四件事的组合，而非依赖单一更强模型。调研数据表明，无分层处理的简单分块在 68% 的复杂文档上无法保持上下文关系，非接地实现的幻觉率可达 27%，因此这四项均不可省略。同时须注意：**自建不会自动消除质量问题**，上游识别质量与下游生成质量必须解耦，通过带置信度的结构化中间产物衔接。

### 4.4 模块四：人工确认闸口（P0）

闸口设计遵循"不处处暂停、只在高风险环节暂停"的原则。

| 编号 | 闸口 | 是否设置 | 设计说明 | 优先级 |
|---|---|---|---|---|
| G1 | 转写稿预检 | 不设全文校对 | 改为"低置信标注 + 抽样复核"，仅可疑段落送人工 | P0 |
| G2 | **议题抽取确认** | **必设，最高优先级** | 风险最高（错则下游全错）且位置最上游（是所有后续步骤的输入），是性价比最高的一道闸 | P0 |
| G3 | 纪要成稿审定 | 必设 | 符合公文必经审批的制度属性 | P0 |
| G4 | 导出定稿 | 不设 | 改为自动执行 + 事后可撤销，避免无效等待 | P0 |

**闸口交互设计的强制要求（降低返工率的关键）**：

| 编号 | 需求描述 | 优先级 |
|---|---|---|
| F4.1 | 人工界面对每条待确认项提供**三种操作：批准 / 驳回 / 编辑**。**"编辑后继续"是把"整篇打回重做"降级为"逐条修正"的关键机制，必须实现** | P0 |
| F4.2 | 每条待确认项展示四要素：原始内容、系统抽取结果、风险评级、抽取依据（来源片段与时间戳） | P0 |
| F4.3 | 提供版本差异对比视图（系统生成版 vs 人工修改版），避免重复审阅已通过内容 | P0 |
| F4.4 | 对低置信项做视觉区分，支持"只显示待确认项"过滤 | P0 |
| F4.5 | 审批动作写入审计日志，记录谁、何时、做了什么决定，支持导出 | P0 |
| F4.6 | 审批超时采取"自动拒绝"（安全默认），不自动通过；并监控审批延迟，超过阈值提示流程设计问题 | P1 |

**设计要点**：闸口机制必须实现在**编排层**而非提示词层。调研明确指出不应在提示词里要求模型"发现不对就停下来"，因为模型对执行拓扑没有物理认知。正确做法是在流程编排中设置确定性中断点，中断时序列化完整状态、恢复时重建状态。

### 4.5 模块五：公文版式导出（P0）

| 编号 | 需求描述 | 优先级 |
|---|---|---|
| F5.1 | 支持一键将纪要 Markdown 导出为符合公文格式的 .docx | P0 |
| F5.2 | 版式须严格对齐 GB/T 9704—2012《党政机关公文格式》：封面标题、各级标题、正文、表格、页码的字体字号规范 | P0 |
| F5.3 | 正文首行缩进两字符；**表格段落零缩进，不被正文缩进规则穿透**（实操中最常见的坑） | P0 |
| F5.4 | 表格全边框、单元格独立对齐、表格上方自动插入表号表名、表格后自动插入空段落 | P0 |
| F5.5 | 标题按中文规范自动编号（1 / 1.1 / 1.2.1） | P0 |
| F5.6 | 中英文之间自动加空格、英文引号自动转中文引号、多重空格压缩 | P1 |
| F5.7 | 支持引用本单位自定义参考模板，以控制页边距、行距、页码等版式项 | P0 |
| F5.8 | 支持导出 .doc 格式（兼容领导方旧版 Office 环境） | P0 |
| F5.9 | 支持导出 PDF 版本用于留档 | P1 |
| F5.10 | 支持公文固定要件（版头、发文字号、落款、成文日期）的占位符注入 | P1 |

**设计要点**：采用"结构转换与样式修正解耦"的架构——先由成熟转换器完成 markdown 到 docx 的结构转换，再通过文档处理库注入中文排版样式补丁。不自行实现完整格式转换。字体须在目标机可用（公文常用商业字体在机关机器通常已安装），系统须在导出前做字体可用性预检并提示回退风险。

### 4.6 模块六：流水线编排（P0）

| 编号 | 需求描述 | 优先级 |
|---|---|---|
| F6.1 | 一次触发走完全程：音频投递后自动串起转写 → 审核 → 抽取 → 生成 → 校验 → 导出 → 归档 | P0 |
| F6.2 | 支持在 G2、G3 闸口暂停等待人工确认，确认后从断点继续（状态恢复，不重新执行已完成环节） | P0 |
| F6.3 | 支持断点续跑与失败重试；**须区分"有检查点"与"精确恢复"**——凡涉及导出文件、发送通知等副作用的节点必须设计幂等键，避免重复执行 | P0 |
| F6.4 | 单份任务全流程状态可视：当前处于哪一环节、已完成哪些、卡在哪一闸口、等待谁确认 | P0 |
| F6.5 | 支持批量排队处理多个会议的音频 | P1 |
| F6.6 | 支持任务取消，取消后已完成环节的中间产物保留 | P1 |
| F6.7 | 提供简单的本地界面（投递、确认、导出三类操作），不要求使用者接触命令行 | P0 |

### 4.7 模块七：术语库与模板库管理（P1）

| 编号 | 需求描述 | 优先级 |
|---|---|---|
| F7.1 | 术语库维护：支持批量导入本单位机构名、人名职务、业务术语、项目代号 | P1 |
| F7.2 | 纪要模板库维护：支持新增、编辑、复制、版本管理 | P1 |

| 编号 | 需求描述 | 优先级 |
|---|---|---|
| F8.1 | **全程离线**：系统不发起任何外网连接；提供网络行为自检报告证明无外发 | P0 |

| F8.3 | **访问控制**：账号权限分级，涉密会议处理期间锁定登录通道，同一设备同一时间仅一个账号在线 | P0 |
| F8.4 | **数据不出边界**：音频、文字稿、纪要、术语库全部本地加密存储，无任何外传通道 | P0 |

| F8.8 | 中间版本留存：保留 AI 输入与输出的各中间版本（文字稿 → 记录.md → 纪要.md → 导出文档），便于回溯比对 | P0 |

### 5.1 性能需求

| 编号 | 需求 | 指标 |
|---|---|---|
| N1.1 | 转写性能 | 2 小时音频在无独立显卡办公机上应在 2 小时内完成；有入门独显时应在 30 分钟内完成 |
| N1.2 | 生成性能 | 单份纪要生成（含分块分层处理）应在 10 分钟内完成 |
| N1.3 | 导出性能 | 单份公文 docx 导出应在 10 秒内完成 |

### 5.2 硬件门槛

系统应能在事业单位常见办公设备上运行。语音识别环节应选择轻量模型（参数量百兆级、显存需求 1—2GB 级），使无独立显卡的办公台式机也能完成转写。纪要生成环节对硬件要求较高，需按本单位设备条件在"本地模型规格"与"生成质量"之间做取舍并明示给使用者。

### 5.3 可用性需求

| 编号 | 需求 |
|---|---|
| N3.1 | 使用者无需接触命令行，所有操作通过图形界面完成 |
| N3.2 | 核心操作不超过三步：投递音频、确认闸口、导出文档 |
| N3.3 | 术语应使用办公人员熟悉的表述，避免工程术语直接暴露（如用"待确认事项"而非"人工闸口"、"文稿"而非"中间产物"） |
| N3.4 | 提供内嵌操作指引，关键界面给出"这一步在做什么、为什么要确认"的说明 |

### 5.4 安全需求

| 编号 | 需求 |
|---|---|
| N4.1 | 所有数据传输与存储加密 |
| N4.2 | 默认不开放任何网络端口；如内网多机访问，须强制鉴权并禁止匿名访问 |
| N4.3 | 部署实施方须具备相应保密资质（涉密场景）；系统交付须附安全加固说明 |
| N4.4 | 模型权重与依赖组件全部离线导入，不使用需联网校验的组件 |

| 编号 | 需求 |

| N5.4 | 交付时附完整部署文档与故障排查手册 |

## 6. 数据模型（核心实体）

```
会议（Meeting）
├── 基本信息：会议名称、时间、地点、主持人、参会人、列席人、记录人
├── 密级标记：公开 / 内部 / 工作秘密 / 国家秘密（由使用者确认）
├── 音频文件（可多个）
├── 转写稿（Transcript）
│   ├── 分段文本 + 时间戳 + 置信度 + 说话人标记（可选）
│   └── 审核状态
├── 会议记录（Minutes Record）
│   └── 结构化元信息 + 正文 + 版本历史
├── 议题集合（Topics）
│   └── 每个议题：议题名、讨论要点、来源片段引用、确认状态
├── 议定事项集合（Resolutions）
│   └── 每项：事项内容、责任人、时限、来源片段引用、确认状态
├── 待办事项集合（Action Items）
│   └── 每项：任务、责任人、截止时间、确认状态
├── 待决策事项集合（Pending Decisions）
├── 会议纪要（Meeting Minutes）
│   └── 结构化数据 + 渲染后 Markdown + 版本历史
└── 导出文件（Word / PDF / 归档）

术语库（Glossary）
├── 机构名 / 人名职务 / 业务术语 / 项目代号
└── 类别标记 + 启停状态

纪要模板（Template）
├── 适用会议类型
├── 固定要素定义
└── 版本历史

审计日志（Audit Log）
└── 时间 + 操作人 + 操作类型 + 对象 + 结果
```

**关键设计说明**：结构化数据与渲染文本分离存储。结构由模型生成、版式由模板渲染，二者解耦后，修改版式无需重新调用模型，修改内容也无需重新排版。

## 7. 技术选型建议

> 以下为基于调研结论的建议方向，具体组件在实施阶段确定。选型须以"离线可用、许可宽松、可自行接管维护"为第一原则。

| 能力环节 | 建议方向 | 选型理由 |
|---|---|---|
| 语音识别 | 中文专用轻量识别方案，须支持热词注入与字级时间戳 | 中文会议场景识别效果优于通用多语言方案；硬件门槛低（百兆级参数、1—2GB 显存即可）；**须避开已公示停服风险的模型** |
| 说话人分离 | 一期不做；二期如做，选已与识别环节集成度高的方案 | 内网环境下模型授权申请构成流程障碍；远场多人场景准确率尚不足 |
| 本地大模型 | 通过本地模型运行环境部署中文通用模型（建议 7B—32B 量化档位） | 一键部署、免环境配置；档位按设备条件取舍 |
| 结构化输出 | 采用支持模式约束的解码方式 | 在生成阶段即保证结构合规，免去重试，综合成本最低 |
| 流程编排 | 一期低代码编排；如需精细控制人工中断点，采用显式状态机框架 + 持久化检查点 | 低代码适合快速落地；显式状态机使分支、重试、人工中断点可直接表达 |
| 文档转换 | 成熟文档转换器负责结构转换 + 文档处理库注入中文版式补丁 | "结构转换"与"样式修正"解耦，不自行实现完整转换 |
| 公文版式 | 复用已有严格遵循公文格式的开源导出组件 + 自定义参考模板 | 该组件已完整实现公文版式映射，可直接复用；自定义模板承载页边距、行距、页码 |
| 界面 | 本地图形界面，提供投递、确认、导出三类操作 | 使用者为非技术背景 |

**架构原则**：五大环节中，转写、审核、导出、编排四环直接复用成熟组件；**自研投入集中于"纪要生成引擎"与"人工确认闸口"两处**。

## 8. 里程碑规划

### 8.1 分期策略

**核心原则：分两期实施，不要一上来就做全自动全链路。** 一期只做环节最少、收益确定、风险最低的部分；二期再引入生成能力，并用真实历史纪要做对比验收，达标后才上线。

### 8.2 一期：流水线打通与版式落地

| 阶段 | 交付内容 | 验收要点 |
|---|---|---|
| 一期-1 | 音频接入、转写引擎部署、术语表注入、带置信度标注的文字稿输出 | 2 小时音频可在目标机型完成转写；术语表命中率可验证；低置信段落标记准确 |
| 一期-2 | 会议记录审核界面、结构化记录稿生成、工作台界面搭建 | 使用者可完成"投递 → 复核 → 得到记录稿"闭环，全程无需命令行 |
| 一期-3 | 公文版式导出、自定义参考模板、.doc 与 .docx 双格式支持 | 导出文档版式符合 GB/T 9704—2012；字体预检提示可用 |
| 一期-4 | 流水线编排、审计日志、访问控制、合规自检 | 一次触发走完全程；操作日志可导出；无任何外网连接 |

**一期交付价值**：消除痛点①（工具来回调用），并解决"公文版式反复排版"问题。**一期不含纪要正文自动生成**，纪要撰写仍由 AI 辅助加人工完成，但输入已是干净的结构化记录稿，且产出的版式一次到位。

### 8.3 二期：纪要生成引擎与人工闸口

| 阶段 | 交付内容 | 验收要点 |
|---|---|---|
| 二期-1 | 分块分层处理引擎、结构化抽取维度固定、模式约束输出 | 上万字文稿不丢关键信息；输出结构 100% 合规 |
| 二期-2 | 公文结构模板库、公文语体对齐、粒度控制 | 纪要文书结构符合党政机关体例；议定事项逐条、责任到人 |
| 二期-3 | 人工确认闸口（议题确认、成稿审定）、三种操作与差异对比 | 支持"编辑后继续"；返工粒度从整篇降为逐条 |
| 二期-4 | 溯源标注、输出后置校验、上线前影子模式验证 | 每条结论可跳转原文；校验清单可用；与人工纪要的一致率达标 |

**二期上线门槛（必须满足才可放开使用）**：用本单位真实历史纪要做对比验收，系统生成稿与人工定稿的结构完整度、要素齐备度达标后，方可正式启用。建议先以"影子模式"运行——系统生成但不交付，人工照常撰写，事后比对差异；当一致率稳定在较高水平且分歧多为"系统更保守"时，再逐步放开自主权。

## 9. 验收标准

### 9.1 功能验收

| 编号 | 验收项 | 通过标准 |
|---|---|---|
| V1 | 音频到转写稿 | 2 小时音频在目标机型成功转写，含标点与时间戳，术语表内专有名词正确 |
| V2 | 转写稿到记录稿 | 一键生成结构化会议记录.md，元信息完整，低置信段落已标记 |
| V3 | 记录稿到纪要 | 生成的纪要含全部必备要素（题名、时间地点、参会人员、议题、议定事项、责任分工），议题与决议逐条呈现 |
| V4 | 溯源性 | 随机抽 10 条结论，均可点击跳转到转写稿对应位置，且内容对得上 |
| V5 | 闸口交互 | 议题确认界面支持批准/驳回/编辑三态，编辑后可继续而非重跑 |
| V6 | 版式导出 | 导出 .docx 的字体、字号、行距、缩进、页码符合 GB/T 9704—2012；表格不被正文缩进穿透 |
| V7 | 一次触发全程 | 投递音频后，除两次人工确认外无需任何额外操作即可得到导出文档 |
| V8 | 审计留痕 | 操作日志完整记录全流程动作，可导出 |
| V9 | 离线验证 | 断网环境下全流程可用；网络行为自检无任何外发连接 |

### 9.2 质量验收

| 编号 | 验收项 | 通过标准 |
|---|---|---|
| Q1 | 要素齐备率 | 系统生成纪要的必备要素齐备率达到约定阈值 |
| Q2 | 返工轮次 | 单份纪要人工返工轮次下降至 1 轮以内 |
| Q3 | 处理时长 | 单份 2 小时会议从音频到 docx 的人工投入降至 20 分钟以内 |
| Q4 | 事实准确率 | 人名、数字、机构名等关键信息的准确率达到约定阈值，且所有关键信息均可溯源 |
| Q5 | 无编造内容 | 抽检内容中不存在转写稿中无依据的陈述 |

### 9.3 不通过即不可交付的红线项

1. 存在任何外网连接或数据外发通道
2. 操作日志不可用或可被普通使用者篡改
3. 导出文档版式不符合公文格式规范
4. 结论无法溯源到原始文稿
5. 关键信息（人名、数字、决议）存在无依据的编造内容

| R9 | 保密检查无法通过操作日志核查 | 高 | 日志设计以"可导出、可核查、不可篡改"为首要目标，须提前与本单位保密工作机构对齐核查项 |

## 11. 附录

### 附录 A：本 PRD 的关键决策依据

| 决策 | 依据 |
|---|---|
| 必须本地离线运行 | 涉密或工作秘密内容使用联网 AI 属法规明文禁止；本地部署是合规必需 |
| 自建而非采购 | 现有产品无一支持党政机关纪要文书结构；党政专用系统价格与采购周期不可控；开源组件已可覆盖四环 |
| 自研集中在纪要生成引擎 | 该环节是市面所有产品与开源项目的共同空白，也是唯一的真正壁垒 |
| 分块分层而非整篇处理 | 超长上下文窗口无法解决信息丢失与重点漂移；实测显示简单分块在复杂文档上保持上下文关系的失败率高达 68% |
| 模式约束而非自由文本生成 | 将文体结构变成可编程契约，在生成阶段避免格式返工 |
| 议题确认设为最高优先级闸口 | 该环节风险最高且位置最上游，错了则下游全错 |
| 闸口必须支持"编辑后继续" | 这是把"整篇打回重做"降级为"逐条修正"的关键机制 |
| 分期实施、二期设上线门槛 | 自建不自动消除质量问题；须以真实历史纪要对比验收后才放开 |
| 一期不做说话人分离 | 远场多人场景当前准确率不足，发言人归属错误是比错字更严重的事故 |

### 附录 B：术语说明（面向非技术使用者）

| 术语 | 通俗解释 |
|---|---|
| 分块分层处理 | 长文稿不整篇交给系统，而是分成若干段分别提炼要点，再汇总成完整纪要，避免漏掉重点 |
| 模式约束 | 事先规定好纪要必须有哪些栏目，系统只能按这个格式填，不能自由发挥导致结构跑偏 |
| 溯源 | 纪要里每一条结论都能点回到录音转写文字里的原话位置，领导质疑时可以马上定位 |
| 人工确认闸口 | 流程中必须停下来由人确认的关卡。只设在关键处，不是每一步都停 |
| 编辑后继续 | 确认时可以直接改，改完接着往下走，不用整篇重来 |
| 影子模式 | 先让系统生成但不交付，人工照常写，事后比对差异，用来检验系统靠不靠谱 |
| 热词注入 | 事先告诉系统本单位的机构名、领导姓名、专业词汇，转写时就不容易认错 |
| 幂等 | 同一个操作重复执行不会产生重复结果（比如不会导出两份文件、发两次通知） |
