## 0. 这套文档解决什么问题

上游 PRD 回答了"做什么"（功能需求、验收标准、里程碑），但没有回答"怎么做"——技术栈选什么、状态机怎么设计、模块怎么切、接口签名是什么、施工顺序怎么排、每个模块的坑在哪。

这套文档补齐的就是这一层：**把 PRD 的"要什么"翻译成工程师能直接动手的"怎么建"**。

**质量承诺**：读完这套文档后，工程师应当能够——
- 知道每一步该写哪个文件、写什么内容、怎么验证
- 知道哪些地方是坑（本文档的坑全部来自实际工程实践与调研证据，不是想象）
- 知道哪些设计**不能改**以及为什么不能改

### 2.1 Phase 1：需求澄清（6 个必答问题）

| # | 问题 | 结论 |

| 01 | 产品形态 | 本地桌面图形应用 + 本地后台服务（同一安装包内） |
| 02 | 运行环境 | 纯本地 / 涉密内网单机运行，全程离线 |
| 03 | 项目规模 | 完整产品，分两期交付（一期可独立使用） |
| 04 | 数据方案 | 本机 SQLite + 本机文件系统，敏感数据静态加密 |
| 05 | 前后端分工 | 前后端分离（Electron 界面 + 本地 FastAPI 服务） |

### 2.2 Phase 2：架构选型（三方案对比结论）

| 维度 | 方案 A 单体桌面 | **方案 B 服务分离+状态机（选定）** | 方案 C 低代码平台 |
|:---|:---|:---|:---|
| 架构模式 | 单体全栈 | 分层 + 显式状态机 | 可视化工作流 |
| 开发速度 | ⭐⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| 可维护性 | ⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐ |
| 扩展性 | ⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐ |
| 离线可控性 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐ |
| 与 PRD 契合度 | 中 | **高** | 低 |

**选定方案 B，三条理由：**
1. 人工闸口必须落在编排层（PRD §4.4 明确要求），只有显式状态机能做到"中断序列化状态 + 恢复重建状态 + 幂等键可控"。
2. 合规审计要求业务逻辑可版本化、可追溯；低代码平台的业务定义躺在平台数据库里，无法 git diff、无法单测。
3. 离线可控性：Dify 类平台依赖较重且含联网校验组件，与"不使用需联网校验的组件"冲突。

**架构模式定级**：DDD 轻量版 + 分层架构（不是完整 DDD——领域规则集中在一处，做全套聚合/事件属过度设计）。

### 2.4 Phase 4：架构 Prompt（十项收敛）

> 这一节就是"可直接用于编码的架构 Prompt"。把它整段交给 AI 或交给新加入的工程师，都能得到一致的理解。

```markdown
## 1. 项目背景
党政机关行政办公人员高频处理会议记录与纪要，现流程靠人工在四个工具间搬运数据，
耗时且质量不稳。本项目把"音频投递 → 转写 → 记录 → 纪要 → 公文 docx"串成一条
离线的自动化流水线，只在两个高风险环节停下来等人确认。

## 2. 目标用户
党政机关/事业单位的文秘、办公室、综合管理岗人员（非技术背景，熟悉 Office，
不具备编程能力）。次要用户是审核纪要的领导（只用 Word）。管理角色是保密工作
责任人（不直接使用系统，但要看审计日志）。

## 3. 核心需求（按优先级）
1. 本地离线完成音频转写，输出带时间戳与置信度的文字稿（P0）
2. 不设全文校对，只把低置信段落送人工复核（P0）
3. 自研"记录 → 公文式纪要"的语义转换引擎（P0，本项目核心壁垒）
4. 人工闸口支持批准/驳回/编辑三态，"编辑后继续"不得重跑已完成环节（P0）
5. 导出符合 GB/T 9704—2012 的公文 docx，表格零缩进不被正文穿透（P0）
6. 全程离线、操作留痕、数据加密、审计不可篡改（P0，不可裁剪）

## 4. 架构设定
产品形态：本地桌面应用（Electron）+ 本地后台服务（FastAPI）
架构模式：分层架构 + DDD 轻量版 + LangGraph 显式状态机
运行环境：纯本地/涉密内网单机，全程离线，服务仅监听 127.0.0.1

## 5. 技术约束（锁定版本）
Python 3.11.9 ｜ FastAPI 0.115.x ｜ LangGraph 0.2.x ｜ SQLite 3.45.x
Pydantic 2.9.x ｜ SQLAlchemy Core 2.0.x ｜ python-docx 1.1.x
FunASR 1.1.x（Paraformer-Large，禁用 SenseVoice）
Ollama 0.3.x + Qwen2.5 7B/14B/32B 量化档
Electron 30.x ｜ ffmpeg 6.x（独立进程）
公文版式：内联移植 minerior/md2docx 的映射逻辑（非黑盒调用）

## 6. 非功能需求
性能：2小时音频无独显≤2小时转写；生成≤10分钟；导出≤10秒
安全：全程离线（0 次外发）、AES-256-GCM 静态加密、审计链式哈希防篡改
可用性：三步操作走完（投递/确认/导出），界面不出现工程术语
可维护性：配置外置可热改；适配器可替换不改上层；内置 ASR 质量自检
兼容性：Windows 10+ / 信创 OS；wav/mp3/m4a/wma/amr；Word 2010+ 可打开

## 7. 实施计划
一期（8—9周）：流水线打通 + 版式落地。不含纪要自动生成。
  T1-01 配置中心 → T1-02 数据模型 → T1-03 文件仓储加密 → T1-04 审计日志
  → T1-05 转写适配器 → T1-06 音频切分 → T1-07 术语库 → T1-08 复核与记录稿
  → T1-09 版式导出 → T1-10 流水线编排 → T1-11 API → T1-12 界面 → T1-13 合规自检
二期（6—8周 + 影子期）：纪要生成引擎 + 人工闸口。
  T2-01 抽取引擎 → T2-02 模板与语体 → T2-03 闸口三态 → T2-04 后置校验
  → T2-05 影子模式（≥20 份真实纪要，达标才上线）

## 8. 输出要求
每个模块交付时必须包含：
① 代码（符合本文档目录结构与分层约束）
② 对应单元测试（领域层覆盖率 ≥85%）
③ 一段中文说明：这个模块做什么、关键设计取舍是什么
④ 该模块的验收命令与预期输出

## 9. 验收标准
功能：PRD §9.1 的 V1—V9 全部通过
质量：PRD §9.2 的 Q1—Q5 全部达标（影子模式验收）
红线（一票否决）：存在外网连接 / 审计可被篡改 / 版式不合规 /
结论无法溯源 / 存在无依据编造内容 —— 任一不通过即不交付

## 10. 限制条件（不要做什么）
① 不要把整篇转写稿一次性喂给模型，必须分块分层
② 不要用自由文本生成纪要再解析，必须模式约束 + 校验层
③ 不要引入 SenseVoice、Whisper-large-v3、任何云 SDK、任何遥测组件
④ 不要让模型"发现不对就停下来"，中断点必须写在状态机里
⑤ 不要把 edit 与 reject 混用——edit 不得重跑已完成节点
⑥ 不要自行实现完整的 markdown→docx 格式转换
⑦ 不要过度设计：域名规则集中一处，不做完整 DDD 的聚合与领域事件
⑧ 不要把工程术语暴露到界面上
⑨ 不要在提示词层解决质量问题，提示词 + 规则后处理是主路径，不上微调
⑩ 不要在非受控环境处理真实会议数据
```

## 3. 一页纸速览（开工前读这一页）

### 3.1 这是什么

一个**离线**的会议纪要自动化工作台。把录音音频投进去，产出符合公文格式的会议纪要 Word 文档。

### 3.2 关键约束（记不住别的，记住这几条）

| # | 约束 | 为什么 |
|:---|:---|:---|
| 1 | **全程离线**，服务只监听 `127.0.0.1` | 涉密内容用联网 AI 是法规明文禁止，不是技术偏好 |
| 2 | **分块分层**处理长文稿 | 整篇喂给模型在 68% 的复杂文档上会丢上下文关系 |
| 3 | **模式约束 + 校验层**，不生成自由文本再解析 | 结构由模型负责、版式由代码负责 |
| 4 | **无溯源不得定稿** | 红线项：结论无法溯源即不可交付 |
| 5 | **"改完继续"不重跑已完成环节** | 这是把"整篇打回"降为"逐条修正"的关键，混用则痛点价值归零 |
| 6 | **表格零缩进** | 公文版式实操最高频的坑 |
| 7 | **审计日志只 INSERT + 链式哈希** | 保密检查会问"日志能不能被改" |
| 8 | **责任人缺失填「暂无」，不是省略** | 公文体要求逐条、责任到人 |

### 3.3 五环中哪一环要自研

| 环节 | 处理方式 |
|:---|:---|
| ① 语音转写 | **复用** FunASR / Paraformer-Large |
| ② 转写稿审核 | **复用** + 轻量增强（置信度分流、术语匹配） |
| ③ 记录 → 纪要 | **★ 自研**（唯一需要从零构建的环节，也是产品壁垒） |
| ④ 版式成文 | **复用** md2docx 映射逻辑 + 自研补丁 |
| ⑤ 流水线编排 | **复用** LangGraph + 自研图定义与闸口 |

## 5. 本套文档的设计取向说明

写这套文档时做了几个刻意的取舍，说明如下：

**1. 明确写了"不要做什么"。**
每份文档都有"限制条件""反模式""禁止清单"章节，且数量不少于正面要求。原因：只说"要做什么"，AI 和新人都容易自由发挥；说清"不要做什么"，才能收敛到同一套架构。

**2. 代码骨架写到能看出意图，但没写成完整实现。**
骨架展示了关键 API 的用法、参数怎么传、坑在哪（比如 `w:eastAsia` 必须设、`disable_update=True` 必须传）。但没写完整实现——因为完整实现会掩盖设计意图，且有经验的工程师按骨架写会更快。

**3. "常见坑"全部来自实际工程实践。**
不是想象的坑，是踩过的：SQLite 外键默认关闭、python-docx 中文必须设 `w:eastAsia`、Windows venv 是 `Scripts/` 不是 `bin/`、PowerShell 脚本含中文必须存 UTF-8 带 BOM、FunASR 热词参数在某些版本被静默忽略。

**4. 性能与质量指标都给了数字，但标注了"须与使用单位约定"。**
给了参考阈值（要素齐备率 ≥95% 等），同时明确说明这些最终要与使用单位约定。这避免了两个极端：完全不给数字（无法验收）和把数字写死（脱离实际）。

**5. 合规部分写得比技术部分更"啰嗦"。**
因为这块出问题的代价是法律责任，不是返工。所有合规表述都标注了依据来源，且刻意区分了"法律明文要求"与"实践要求"。
